FOUND IN PASSING — NOT FIXED, REPORTED WITH THE EVIDENCE
─────────────────────────────────────────────────────────

None of these blocked the run and none was worked around; a one-line change to
unblock would have been named, and there was none to make.

(i) `svrn corpus list` NEVER LISTS AN INSTALLED CORPUS — for any corpus, not
    just this one. `cmd_corpus_list` (`sovereign-cli-llm/src/corpus_cmd/
    inventory.rs:18-29`) is six hard-coded `println!`s of built-in recipe ids
    and reads no index directory at all, while `corpus --help` describes it as
    "List installed and available corpora". So D1's step-4 wording ("appears in
    `sovereign corpus list`") is unsatisfiable BY THAT VERB, and the installed
    reading was taken from `installed_indexes()`-fed gossip and from the query
    instead. Pre-existing and unrelated to the collector.

(ii) `nodes=0` ON A MERGE THAT USED ONE SHARD — B7's mis-report, first seen
    LIVE. `RecoveryOutcome::Recovered.shards_covered` is `participants.len()`,
    the number the merge was ASKED for, not the number it resolved. On a
    single-node fold every completion carries `provenance.host: Server::Local`,
    which `fold_coverage_for` deliberately does not put in `nodes` (it is the
    donor describing ITS machine), so `participants` is empty by construction
    and the success line reads `chunks=813 nodes=0`. The merge was correct —
    `merge_participants` always collects the LOCAL shard first
    (`shard_manager.rs:494-516`), which is why `expected=1` was satisfied. The
    number in the log is still derived from the request rather than from what
    happened (ARCH §18.1).

(iii) THE `total_shards` GUARD WAS DARK HERE TOO, AND FOR A NEW REASON. B7
    reading 3 established the stamp is scoped to `ExtractorConfig::
    WikipediaJsonl`. This recipe IS `wikipedia_jsonl` and it STILL went
    unstamped, twice:

      WARN ingest: could not enumerate canonical shards — total_shards left
      unstamped corpus=cw5g-d1 error=Extraction error: Failed to read ZIP TOC
      at …/cw5g-proof.jsonl: invalid Zip archive

    The stamp path assumes a ZIP even when the extractor is reading a plain
    `.jsonl`. Harmless on the fold path — `merge_from_fold_coverage` arms
    `expected_partitions` from the handoff's own verified-donor count and never
    consults `total_shards` — and the resulting `total_shards: None` in the meta
    above is that WARN's consequence, visible. It widens B7 reading 3's finding:
    the guard is dark not only for non-Wikipedia recipes but for a Wikipedia
    recipe over a non-ZIP source.

(iv) THE REFUSAL TEXT TEACHES A PAYLOAD THE PARSER REJECTS. Two spellings of
     one vocabulary in one file (ARCH §10.6), and the wrong one is on the
     failure path where a stuck submitter reads it:

       ingest_executor.rs:189   "kind": "hf-file"|"jsonl-shard"|"jsonl-range"
       ingest_executor.rs:463   "kind": {"enum": ["HfFile","JsonlShard","JsonlRange"]}
       ingest_executor.rs:485   "unit": {"kind": "JsonlRange", "value": {...}}

     `WorkUnit` is `#[serde(tag = "kind", content = "value")]` with no
     `rename_all` (`commonwealth-core/src/knowledge.rs:316-318`), so PascalCase
     is what parses. This units file uses the schema's spelling and was accepted
     first try; a submitter following the ERROR would be refused again, and the
     refusal is silent at the donor.

(v) TWO CORPORA WITH DIFFERENT IDS SHARE ONE `canonical_fingerprint` — B5's
    corpus clause, corroborated live rather than in a fixture:

      cw5g-proof   next_chunk_id=814  ebae85630ca70ab1…c994540
      cw5g-d1      next_chunk_id=814  ebae85630ca70ab1…c994540

    Correct for a content hash — the chunk sets genuinely are identical — and
    that is the point B5 makes: the fingerprint carries NO information about
    which handoff produced the corpus or whether it is complete. B5's fixture
    showed a 2-of-3 and a 2-of-2 agreeing; this shows two separately-merged
    corpora on different days agreeing. B5 stays open and this is one more
    reason to close it.
