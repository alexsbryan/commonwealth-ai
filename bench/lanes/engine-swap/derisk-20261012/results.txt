What the run caught, worth recording because it changes how arm (c) is read:
THE PLANNER'S -ot IS NOT THE PLANNER'S CONFIGURATION WITHOUT ITS -ts.
Measured, first `-ot` alone, then `-ot` + `-ts`: alone it decoded 2.93 and
4.08 tok/s (runs 1-2, n=3 each) — about 4x SLOWER than upstream, a result
that would have read as "the planner is disastrous". llama.cpp derives its
per-layer device map from `tensor_split` ALONE (llama-model.cpp:1466,
`upper_bound(splits, 0..n_devices)`) and never from `-ot`; an `-ot` with no
matching `-ts` leaves the map on upstream's cut, a layer straddles the two
placements, and on this hybrid that is the fused-GDN hazard plan.rs:583-606
already documents. With `dev_layer_tensor_split` (15.5,18.5 over n_layer+1
units) the same placement runs at parity. Any future comparison of `-ot`
against a split must carry the matching `-ts` or it measures a broken
configuration, not the planner.

The link: LAN 192.168.1.11/24, no tunnel, RDMA never negotiated (TCP
throughout, so GGML_RPC_NO_RDMA was not needed). Load 12.7-23.5 s per arm,
run to run, with no separation between arms — load success, not load time,
is what the row asks about and what these numbers support.

The Mac's peer serves TWO devices: RPC0 with the GPU's memory and RPC1 with
0 bytes (Metal emulates virtual devices; ggml-metal.cpp:960-995, and the
second reports nothing — llama-server says "device RPC1 did not report
memory"). Left in the list, llama.cpp's split hands RPC1 3.4 GiB of model and
the first decode reads a tensor from a device holding none (ggml-rpc.cpp:522,
"Remote RPC server crashed"), which on this link took the peer's process
down with it. Every arm names `-dev RPC0,Vulkan0` for that reason: it is a
property of the peer, not of any placement, and holding it fixed is what
makes the three arms comparable. d4_peer.py reports the real/phantom split
(devices 1/2) so the next run sees it before loading anything.
