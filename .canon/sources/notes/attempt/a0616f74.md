# Phase 3a atlas-resolve smoke test on brothers_karamazov (3 sections: sec_0001, sec_0004, sec_0008) produced 20 Entity atoms + 9 Event atoms…

Phase 3a atlas-resolve smoke test on brothers_karamazov (3 sections: sec_0001, sec_0004, sec_0008) produced 20 Entity atoms + 9 Event atoms + 8 Involves edges. The wiring works; the resolution rules are demonstrably too conservative on real Brothers Karamazov data. Two concrete findings:

1. Mixed-encoding source text defeats token/Levenshtein rules.
Model output carries a mix of Latin + Cyrillic characters mid-word: `Fyodor Karamазов` (С+ascii) vs `Fyodor Pavlovich Karamazov` (all ascii). Rule 3 requires ≥2 shared tokens of len≥3 after case-fold, but `Karamазов` ≠ `Karamazov` byte-wise. Rule 2 Levenshtein runs on raw chars, so a single Cyrillic-for-Latin substitution counts as an edit. Net: these should-merge pairs stay distinct. Same pattern for `Miюsova`/`Miusova`, `Adelаїda`/`Adelaida`, `Mityа`/`Mitya`.

Fix candidates for a later pass:
  a. Unicode-fold before token/Levenshtein compare (NFKD + strip marks + map confusables like С↔C, а↔a, о↔o).
  b. Source-text pre-processor that normalises Karamazov_BR RTF-style Cyrillic transliteration artifacts before the model sees them.
  c. Add a 3rd looser merge rule: cosine ≥ 0.95 on description embedding AND shared first token. Catches "Fyodor Karamазов" ↔ "Fyodor Pavlovich Karamazov" via the "fyodor" overlap + semantic similarity.

Recommendation: land (a) first — it is deterministic and fixes a broad class of Russian-novel text issues. (b) is per-corpus pre-processing work. (c) risks false-positive merges on "Alexei Fyodorovich" family members.

2. One-token shared-name merges need their own rule.
`Zossima` (0007) and `Father Zossima` (0014) do not merge: rule 3 sees 1 shared token (`zossima`), below the min-2 threshold; rule 2 Levenshtein is 7 (insert "Father "); rule 1 alias match fires only if the sketch listed the alias. A separate rule — 1 shared token of length ≥5 AND description cosine ≥ 0.85 — would handle title+name cases (Father X, Mother Y, Doctor Z, Professor W, Sister S) without loosening the Ivan/Ilya guard.

3. Orphan event participants drop silently.
Events from sec_0001 came out with `participants = []` because their sketch participant names (`Fyodor Pavlovitch Karamazов`) did not match any introduced entity by case-folded exact name. The resolver dropped them with a `debug!` but not a `warn!` and not a surfaced statistic. Better: surface the drop count in the atlas-resolve CLI output + save to schema_validation.json as a diagnostic bucket.

None of this blocks Step 3b (states/relations/claims resolution) — Step 3b also takes the canonical entity IDs and inherits the same conservatism. But once Step 3b lands and the first real full-corpus run happens, expect these rules to be the first tuning target.
