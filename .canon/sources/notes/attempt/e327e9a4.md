THE SCORING HARNESS HAS TWO SEPARATE INSTABILITIES, NOT ONE. CONCURRENCY EXPLAINS THE RUN-TO-RUN CHURN AND `--concurrency 1` FIXES IT COMPLETELY. IT DOES NOT EXPLAIN THE SCALE EFFECT, WHICH SURVIVED EVERY HYPOTHESIS TESTED. Established 2026-08-03; refines note 255a1819, whose "remaining candidate is batch composition" is now REFUTED for the scale half.

(1) RUN-TO-RUN CHURN = CONCURRENCY. SOLVED.
  --concurrency 4: two identical runs (same adapter, items, seed, temp 0.0) agree on only 178/217 items (82.0%).
  --concurrency 1: two identical runs agree 172/172 (100.0%).
  USE `--concurrency 1` FOR ANY RUN WHOSE NUMBER WILL BE COMPARED TO ANOTHER. It costs ~2x wall (220 items: 309s vs 146s; full card: 52min vs 23min) and buys exact reproducibility.

(2) SCALE EFFECT = UNEXPLAINED. DO NOT RE-DERIVE THESE; THEY ARE ALL DEAD.
  The effect: arm A free-decode, well-formed markup rate
      per_subset  20 (220 items):  105/217, 70/217, 105/217, 102/217   (32-48%)
      per_subset 200 (2200 items):   1/2186, 1/2186, 2/2186            (~0.1%)
  The 220 items are a VERIFIED SUBSET of the 2,200 (217/217 id overlap), and the SAME items that are always well-formed at 220 are malformed at 2,200.

  REFUTED, each with the measurement that killed it:
  * CONCURRENCY / BATCH COMPOSITION. Full card at --concurrency 1 = 2/2186 (0.1%), vs 1/2186 at --concurrency 4. Identical per-item outcomes between the two full runs, same single success at position 2175. Concurrency changes nothing at scale.
  * POSITIONAL DRIFT / SERVER STATE ACCUMULATING. Conditioned on the 133 items capable of well-formed output (WF in >=1 subset run), the full run is 0% well-formed in EVERY 250-position bucket INCLUDING 0-249 (n=19). Flat from the start. NOTE: an unconditioned "0/100 per chunk" plot looks like proof of this but is not -- only 2 of 68 always-capable items fall in the first 100 positions, so a 0/100 chunk is expected either way. Condition on capability or the plot lies.
  * PROMPT-PREFIX / DOCUMENT REUSE ACROSS NEIGHBOURS. Consecutive same-document requests: 0.0% at per_subset=20, 0.1% at per_subset=200. Documents essentially never repeat back-to-back at either scale.
  * DIFFERENT PROMPTS. `load_items` has no truncation and no per_subset-dependent processing; `build_prompt(doc, claim)` is pure. Prompts for a given id are identical by construction.
  * DIFFERENT WEIGHTS. All TEN converted adapter GGUFs across every run share one md5 (327a4478...).
  * DIFFERENT PROTOCOL / RUNTIME. summary.json protocol blocks identical (max_tokens 2560, temp 0.0, enable_thinking false, seed 17); same server banner, same Vulkan device, same /lib64/libllama.so.0.
  * RUN-TO-RUN CHANCE. The full card reproduced EXACTLY -- 1/2186, identical failure counts -- five hours apart, and again under conc-1.

  WHAT IS ACTUALLY KNOWN. Well-formedness is largely ITEM-determined: across 4 subset runs, 84 items are never well-formed and 68 always are (bimodal, not binomial). At 2,200 items even the "always" group collapses to 1/68. At full scale the run is DETERMINISTIC regardless of concurrency; at 220 it is variable under conc-4 and deterministic under conc-1.

WHY THIS WAS STOPPED, AND WHY THAT IS SAFE. `--grammar` neutralises it for the shipping path: 2,186/2,186 well-formed at BOTH scales, and verdicts agree 90.5% between 220 and 2,200. The instability lives in FREE-DECODE format only, which no shipping protocol uses. Chasing the mechanism further has no end-user impact. If it must be reopened, the untried instrument is capturing the exact HTTP request bodies for one capable item in both a 220 and a 2,200 run and diffing them -- that separates client-side from server-side once and for all.
