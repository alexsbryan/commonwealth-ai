THE CLOUD PROBE OVERWROTE ITS OWN FIRST ARM — run name did not identify the hardware. FIXED 2026-08-05, but the A100's raw run dir was already lost.

WHAT HAPPENED. `cmd_probe`'s default was `NAME=${NAME:-probe-4b-cloud-m$micro}` — identical for every GPU — and `cmd_fetch` rsyncs the pod's `runs/` into a FLAT `~/dev/train-env/runs/`. Probing the A6000 after the A100 wrote `probe-4b-cloud-m1` a second time, silently replacing the A100's summary.json, steps.jsonl, train.log and adapter. Detected only by checking `summary.json.environment.gpu` after the second fetch and finding "NVIDIA RTX A6000" where the A100's data should have been.

COST: the A100's raw artifacts are gone. The NUMBERS survived only because they were written to note 0449bd7d at the time of measurement — which is the argument for writing notes at the moment of the decision rather than at session end.

THE FIX. `name` now includes a gpu slug resolved from the ledger row this pod already wrote, plus the vast id (unique by construction even if the lookup misses):
  probe-4b-m1-a100-sxm4-46854795
  probe-4b-m1-rtx-a6000-46857925
Verified both resolve distinctly against the real ledger.

THE GENERAL SHAPE, worth carrying: a comparison harness whose arms collide on one output path cannot compare anything, and the collision is SILENT because rsync overwrite is a success. §7.5 — identity from essence: the essence of a probe run is (recipe, hardware, instance), and the name carried only the recipe.

RELATED TRAP, not yet hit: `cmd_fetch` pulls the whole `runs/` tree, so any future run reusing a name on the POD would collide there too before it ever reaches the local side.
