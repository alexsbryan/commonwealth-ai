How to write/run chaos UI tests against the desktop chat surface, including the pageerror watcher and known categories

The desktop chat surface has a chaos test suite at `sovereign/crates/sovereign-desktop/tests/e2e/specs/chat-chaos.spec.ts` that probes the FSM + UI with unexpected event sequences. These tests are invariant-style, not behavioural — they assert "the surface doesn't break", not "X behaves exactly like Y".

Why: chaos tests catch a class of bugs the happy-path tests miss — protocol violations, race conditions, malformed payloads, stuck states. Example: the chaos suite found that `MESSAGE_REFINED` arriving mid-stream would clobber partial content (the FSM only guarded conversationId, not streamingMessageId). Fix landed in chat.machine.ts and is now pinned by both vitest + Playwright.

How to apply when adding chaos tests:
- Probe ONE unexpected scenario per test. State the chaos in the test name.
- Assert *invariants*, not exact behaviours: no uncaught exceptions, UI returns to interactive, follow-up turn still works, message list isn't corrupted. The pageerror watcher in `tests/e2e/fixtures/test-base.ts` auto-fails any test where an uncaught JS error fires — so most chaos tests don't even need explicit error assertions.
- For tests that legitimately expect page errors (rare), opt out via `testInfo.annotations.push({ type: "allow-page-errors" })`.
- The `__sovereign_test__.emit(eventName, payload)` API drives Tauri events directly — use it to inject malformed/duplicate/out-of-order events.
- For perceived-latency assertions, measure inside the page via performance.now(), not on the Playwright side. Playwright's IPC overhead under parallel-worker load can spike to 200ms+ and pollute the budget.

Known chaos categories covered:
- out-of-order events (chunks/completes for unknown ids, refinement for stale conversation)
- duplicate events (double complete, re-fired backend-ready)
- malformed payloads (empty chunks, 50KB single chunk, unicode-heavy)
- user-input chaos (Send-spam, Stop-spam)
- bridge failures (never-resolves, raw-string rejection)
- race conditions (Stop during preparing, rapid conversation toggling, refinement mid-stream, late chunks for old turn)
- end-to-end fuzz (barrage of all of the above + recovery to normal turn)

When chaos finds a bug: fix the FSM/handler, add a unit test in `chat.machine.test.ts` that pins the corrected behaviour at the state-machine level, and leave the e2e chaos test in place as a regression guard at the integration level.
