# Every plan file under ~/.claude/plans/ includes Context + four alignment sections (extends / removes / restraint / could this be less).…

Every plan file under ~/.claude/plans/ includes Context + four alignment sections (extends / removes / restraint / could this be less). Pre-code, structurally enforced via PreToolUse hook on ExitPlanMode.

Every plan written to `~/.claude/plans/` for non-trivial work
must include all five of these H2 sections, in order, before
calling `ExitPlanMode`:

```
## Context
<why this change — the problem, what prompted it, the intended outcome>

## What this extends
<existing files / functions / patterns this builds on. Forces visibility-of-existing.>

## What this removes
<files / functions / dead code being deleted. Forces engagement with deletion.>

## Restraint patterns
<which inquiries / ARCH_PRINCIPLES sections govern the touched files. Forces engagement with norms.>

## Could this be done with less?
<smallest viable shape. Honest answer: when the answer is "no, this
is the minimum," say so explicitly with reasoning.>
```

Other sections (Architecture, Verification, Open questions, etc.)
are fine and encouraged — these five are the *required* core.

Why:

The vision-text behind this rule (2026-05-08 session): "the
plan-stage explicit alignment justification is the highest-leverage
mechanism" because once code is generated, path-of-least-resistance
behaviors have already kicked in. Forcing the four questions upstream
of any code is where alignment is cheapest. The four questions map
onto four sprawl categories the system tends to accumulate.

The hook at `.claude/hooks/validate-plan.sh` runs
`sovereign plan validate` on the most recent plan file and **blocks
ExitPlanMode** (exit 2) when sections are missing. That's structural
enforcement; this memory is the cultural reinforcement so the
sections show up the first time, not after a rejected ExitPlanMode.

How to apply:

- Trigger: any plan file written via the harness's plan-mode
  flow. Rule of thumb: any task that warrants entering plan mode
  warrants the five sections.
- Skip when: trivial work (typo fix, single-line rename,
  <50-line edit). For these, plan mode usually isn't entered
  anyway, so the rule self-skips.
- Phrasing: be substantive in each section. "Could this be done
  with less? — no" is fine *if* followed by why the current shape
  is the minimum. "What this removes? — nothing" is fine *if*
  followed by acknowledgement that the change is purely additive.
  Empty / placeholder content fails the spirit even when the
  validator passes.
- Order matters: Context first frames everything; the four
  alignment questions follow in the listed order so they read as
  a checklist before getting into Architecture / Verification.
- Template: `~/.claude/plans/_TEMPLATE.md` (created with this
  rule) — copy when seeding a fresh plan.
- Validator: `sovereign plan validate <plan.md>` — exits 1
  with a missing-section list to stderr if anything's absent.
  Used by the PreToolUse hook to gate ExitPlanMode.
