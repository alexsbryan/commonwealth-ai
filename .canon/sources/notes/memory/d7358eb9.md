# Gold-standard for ambiguous classification/parsing/routing in this repo is the embed-router centroid pattern, NOT hardcoded…

Gold-standard for ambiguous classification/parsing/routing in this repo is the embed-router centroid pattern, NOT hardcoded keyword/substring lists. Keyword matching works in-sample, fails out-of-sample.

When classifying or routing ambiguous text (column header → entity type, query → intent, query → scope, etc.), do NOT use hardcoded keyword / substring matching. It works on the examples in front of you and almost never generalizes out of sample.

The user's standard (2026-05-30): the embed router is the gold standard. Pattern lives in `sovereign-core/src/router_embed.rs` (k=1 NN intent router) and `sovereign-core/src/scope_classifier.rs` (binary centroid classifier — the cleanest template):

1. Baked, diverse, bench-disjoint exemplars per class (not paraphrases of your test cases — that just coaches to the bench).
2. Embed each exemplar (normalize) → sum → normalize → per-class centroid.
3. At query time: embed the input, cosine vs each centroid, classify by absolute gate (`sim >= min_sim`, so no-signal inputs don't drift into a class) + margin gate (winner beats runner-up by `min_margin`, so noise doesn't flip borderline cases). Tune both empirically on a harness.

The offender flagged: `corpus-engine/src/extractors/column_aware.rs` — `ColumnHeaderMap::classify` substring-matches headers against `employee` / `counterparty` / `manager` / … . Works on Enron + the synthetic corp-sheets corpus, but won't survive real headers ("Cpty", "Resp. Party", "Beneficial Owner", "DRI", "PIC"). Why: the header space is unbounded; a finite keyword list can't cover it. Adding synonyms is the trap, not the fix.

Why: generalization is the whole point of these verticals (Enron is a forcing function, not the destination — [[project-enron-substrate-push-plan]]). A classifier that only works on the curated corpus is worse than useless — it hides the gap.

How to apply: for the column_aware fix (task tracked) mirror `scope_classifier`: a `HeaderClassifier` with Person/Org/Place centroids, `EmbedFn`-driven (reuse the daemon `/v1/embeddings` `EmbedFn` builder in `sovereign-cli-llm/src/enrich_cmd/inference_client.rs`), abstain+margin gates tuned on the corp-sheets `diagnose` harness, keyword map kept only as a no-embed fallback. Watch the trap everywhere, not just here: any `match`/`contains` over a finite vocabulary doing semantic classification is suspect.

Also note: the synthetic corp-sheets corpus itself must avoid the dual trap — exemplars/gold that only mirror the corpus headers prove nothing. Test generalization on novel headers the classifier never saw.

LANDED + validated (2026-05-30). `HeaderClassifier` shipped in `corpus-engine/src/extractors/column_aware.rs`, wired into `sovereign enrich sheets-ingest` (keyword map = `--keyword` fallback). Result vs keyword on the corp-sheets harness: coverage 30/45 → 44/45; the cryptic-header probe (`Cpty`/`DRI`/`Resp. Party` → OOV gold Vanguard/Tobias) goes 0 → fully caught. A 4th abstain centroid (None-tagged, exemplars like "status/category/level/ticker") makes non-entity columns classify as non-entity and abstain — the no-keyword way to drop Status/Category/Level noise (23% → 3/85 residual). A value-SHAPE filter (`is_name_shaped`: drop >6-word prose + digit-dominant cells) kills footnotes/dates/numbers. Margin is the discriminator (entity cols commit ≥0.08; noise sits ambiguous), `min_margin` env-tunable, default 0.05.

Relapse caught by the user (2026-06-07). While fixing the Lebanon-essay misroute I correctly replaced the `needs_current_info` keyword classifier (`router.rs` — substring `"today"` in "history of Lebanon from antiquity to today" → forced ACTION/external-search → refusal) with a binary embed centroid (`current_info_classifier.rs`, mirrors `scope_classifier`). Then, IN THE SAME CHANGE, I added a NEW `requests_long_form()` substring list ("exhaustive"/"keep writing"/…) to scale the response budget — the exact anti-pattern, one function over. The user: *"Why are we doing string matching heuristics again??"* Lesson: the trap re-appears mid-fix; audit your own diff for it before building, not just the legacy code. Resolution: deleted the keyword detector; the response-length budget is driven by the explicit setting (`InferenceConfig.max_tokens`, the desktop "Response length" knob) — the server was hardcoding `InferenceConfig::default()` (2048) and ignoring config, so the fix was to read `[inference] max_tokens`, NOT to sniff the message. Note the discriminator: literal control-token stripping (`<tool_code>`, `<think>`) is NOT this trap — it's mechanical removal of a fixed protocol token, not semantic classification of free-form text.

Two anti-coaching disciplines that caught real bugs (reuse):
1. Audit exemplars for gold/corpus leakage. I'd put "Globex Inc" (a gold entity!) and corpus-echo values ("open, closed", "cloud", "finance, engineering") into the exemplars — direct coaching. Fix: exemplars use only fictional, corpus-disjoint names/values.
2. Validate uncoached by RE-DECOUPLING + re-measuring. After de-coaching the exemplars, coverage HELD at 44/45 → the generalization is real, not memorized. If it had dropped, the win was coaching. Always test on OOV headers (`Cpty`/`DRI`) that appear in no exemplar — that's the load-bearing proof.
