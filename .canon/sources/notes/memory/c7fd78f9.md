When a unit of work wraps (feature shipped, refactor landed, bug fixed), proactively offer a conventional-commit-style message — even when the user hasn't asked to commit

When a body of work wraps in this project — feature shipped,
refactor landed, bug closed, doc set updated — proactively
propose a conventional-commit-style summary message before the
user has to ask. The user has signed up for this and uses the
practice as both (a) a concision exercise that reveals what was
*actually* done and (b) a signal the archaeology eval can
corroborate via its `keyword_present` witness check.

Why:

1. The user explicitly requested this on 2026-05-08 alongside
   adopting conventional-commits + ≥10-word subjects as a soft
   commit-hygiene nudge.
2. The archaeology eval's keyword witnesses fail on commits like
   "cleannn" / "sassy foundation" — substantive subjects keep
   the eval calibrated and lift principle-inquiry scores from
   ~80% into the 90s without code change.
3. Distilling 3 hours of work into one sentence is a forcing
   function for the human writing the commit. Doing the
   distillation and offering it as a starting point is concretely
   helpful, not busywork.

How to apply:

- Trigger: a "unit of work" finished. Heuristic — at least
  one of: (a) the user wrote "ship it" / "looks good" /
  "we're done"; (b) all tasks for the named feature are
  `completed`; (c) tests pass + no open follow-up; (d) the user
  asked for a summary or PR description.

- Don't trigger for: minor in-place edits, exploratory
  research, ongoing iteration mid-feature, documentation-only
  passes < ~50 lines.

- Format: conventional-commits with a substantive subject:
  ```
  <type>(<scope>): <subject — at least 10 words, present tense, names the why>

  <optional body — bullet points or one paragraph on rationale,
  trade-offs, and any deferred follow-up>
  ```
  Common types: `feat`, `refactor`, `fix`, `perf`, `docs`,
  `test`, `chore`. Scopes match crate or subsystem
  (`archaeology`, `eval`, `drift`, `knowledge_view`,
  `runtime`, etc.).

- Tone: the subject names the *why* the change happened,
  not the *what* (the diff already says what). "feat(eval):
  add witness checks so archaeology output is mechanically
  re-verifiable" beats "feat: add witness check module".

- Offer, don't auto-commit. Phrase it as "here's a draft
  commit message — adjust before committing." Never run
  `git commit` unprompted; this is about the message, not the
  action.

- One message per body of work, not per file change. If the
  session genuinely spanned multiple bodies (e.g. shipped a
  feature *and* fixed an unrelated bug), offer two — flag the
  separation explicitly so the user can land them as separate
  commits.

This is a session-end ritual, not a session-start one.
