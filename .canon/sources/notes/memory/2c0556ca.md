# Before non-trivial work in commonwealth-ai, read ARCH_PRINCIPLES.md to apply the codified SOLID / SICP / glassbox / docs-as-invariant…

Before non-trivial work in commonwealth-ai, read ARCH_PRINCIPLES.md to apply the codified SOLID / SICP / glassbox / docs-as-invariant discipline the user established after the first major refactor pass.

Read `~/dev/commonwealth-ai/ARCH_PRINCIPLES.md` at the start of every session that involves writing, reviewing, or refactoring code in this workspace. Pair it with the `SYSTEM_OVERVIEW.md` read already called for in CLAUDE.md — one tells you what the system *is*, the other tells you how it's *built*.

Why: The file is the distilled learnings from a comprehensive refactor pass the user and I did together. It encodes the exact failure modes this codebase keeps falling into — silent `SYSTEM_OVERVIEW.md` drift, stringly-typed dispatch scattered across files, 2000-line accretion files doing five jobs, embedded strings masquerading as code, cross-workspace dep version skew, runtime-only privacy checks, opaque decisions with no tracing. Each §-numbered section cites a real incident we fixed. Missing a principle on the next wave of work means repeating a bug we already wrote the cure for. The user commissioned the doc specifically so future engineers (me included) wouldn't muck up the system "as badly in the next go around" — their exact words.

How to apply:

1. Session start. Before editing anything, read ARCH_PRINCIPLES.md once (alongside SYSTEM_OVERVIEW.md). The file is scannable in 10 minutes.
2. Pattern choices at the keyboard. When any of these questions come up in the course of work — "should I split this file?", "should this be an enum or a `&str`?", "should this trait grow or stay narrow?", "does this invariant deserve a test or just a comment?", "where does this template string belong?", "is this behaviour worth a `tracing::debug!`?" — cross-reference the relevant § number before deciding. The principle usually ends the debate.
3. Review. If a diff under review violates a numbered principle, call it out with the § reference. Silent violations are how principles rot into aspirations.
4. Updating the doc. If a new failure pattern emerges, add a section per §17 of the file itself — *from a real incident, specific, actionable*. Don't generalise SOLID/SICP abstractly; the whole point is that every rule is grounded in this codebase.
