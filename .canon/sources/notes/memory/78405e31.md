When a bug surfaces in a workflow, fix at the product-resilience level (a user-visible rough edge to smooth) instead of patching the specific reproduction

When the user reports a bug or a workflow that broke, the default instinct is
to fix the exact reproduction — patch the symptom, get the use case
unblocked, move on. That's whack-a-mole. The right framework: the user is
the first person experiencing this product, and every issue they hit is a
data point about a rough edge in the product itself. Fix at that level, not
at the specific-bug level.

Concrete example from the wikipedia-canonical-sync work (2026-04-29):

- Whack-a-mole instinct: RuggedFox has a stranded 17/38 canonical and
  Alex's MacBook has a healthier one. Quick fix: rsync the canonical over,
  document the procedure.
- Product-level instinct (what the user prompted): the daemon should
  have an identity for shared artifacts (a fingerprint), so peers can
  compare states and self-heal without manual intervention. That led to:
  canonical_fingerprint, gossiped catalog enrichment, pull RPC,
  auto-trigger in `auto_recover`. The specific RuggedFox case got fixed as
  a side effect of the right product design.

Why: Treating each bug as a one-off patch lets workflows degrade
piecemeal — every fix is an individual scar, the product never gets
better, and the next user (or this user, six months from now) hits a
neighbouring failure. Treating them as product-resilience signals
compounds: each fix removes a class of failures and the next analogous
issue often doesn't surface at all.

How to apply:

1. When a bug report comes in, ask "what would the product need to do for
   this never to happen?" before "what's the minimum patch?"
2. Especially when the symptom is "this got janky" or "this doesn't
   self-heal" — those are diagnostic of a missing product-level mechanism,
   not a missing line of code.
3. If the right answer is genuinely a one-line fix, that's fine. But state
   the product-level diagnosis first ("the daemon's invariant is X, this
   bug means we violated it because Y") so we know whether it actually is
   a one-off.
4. When a one-off patch IS the right call, name it explicitly so it
   doesn't masquerade as architecture.

The user is doing the work of applying the product to a real problem. We
do them a disservice if we patch their symptom and leave the product the
same shape.
