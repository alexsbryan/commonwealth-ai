When capturing inference output for post-mortem debugging, strip thinking tags first and persist the stripped content — not the raw head

When a thinking-capable model (Qwen3, DeepSeek R1, o1-family) fails to parse, the diagnostic signal is the substring AFTER `</think>`. The `<think>` preamble is reasoning noise. Do not bump response-head caps to work around a 1 KB limit — that just keeps more of the wrong bytes.

Why: In one enrichment-pipeline session I hit the same pattern four times (Phase 1, Phase 3, Phase 5, then Phase 1 atlas). Each time the failure record's `raw_response_head` was entirely `<think>` preamble; the JSON that actually failed to deserialise was past the cap. My first instinct was to bump the cap 8×; the user called out "8x bump is a hammer — please take the time to do this right." Correct — the right fix is to keep the *post-strip* bytes, not more bytes.

How to apply — any time you're designing or touching a parser that captures model output:
1. Strip `<think>…</think>` BEFORE truncating for diagnostics (use `strip_reasoning_tags`).
2. Persist the STRIPPED content in failure records — it's what the parser actually saw.
3. Fall back to the reasoning preamble only when stripping leaves nothing (truncated mid-trace), and flag the mode explicitly (e.g. `"<think block truncated — answer never emitted>"`).
4. Keep the cap modest (~2 KB fits a typical structured JSON). WHICH bytes you keep matters, not HOW MANY.

Reference impl: `corpus-engine/src/enrichment/pipeline/runner.rs :: truncate_response_head`. Helpers: `strip_reasoning_tags`, `is_truncated_thinking_response`, `extract_json_block` in `pipeline/types.rs`. Also stored as sovereign note (kind=invariant) with id c55ff900-25f9-4ece-ac97-7ae2ea2fd433.
