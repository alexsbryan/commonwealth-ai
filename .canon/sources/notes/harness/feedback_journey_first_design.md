# Alex wants designs and pitches built operator-journey-first — trace the user's path hop by hop and pin each hop to technical facts;…

When proposing a system, feature, or plan, lead with the operator's (or end user's) journey traced scene by scene — what happens today at each hop (cited/measured), and the single change the proposal makes there — then let artifacts, mechanisms, and phases derive from the scenes.

Why: 2026-08-06, comaintainer moonshot design. Two successive redirects in one session: first "what is the actual deliverable? the mechanism seems unclear" (answered artifact-first), then "actually start with the operator, trace the user journey from operator to end goal — that's the path we have to connect with technical facts." This mirrors the repo's own reporting rule ("end-user impact is the lens") — Alex applies it to design docs, not just feature reports.

How to apply: Structure both the chat briefing and the doc as: journey scenes (today-fact → change-at-this-hop, each grounded in a measured number or cited surface) → the crux scene named explicitly → metrics the journey moves → only then the artifact/mechanism inventory.
