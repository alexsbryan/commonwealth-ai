# AN AGE CANNOT BOUND A STORE WHOSE WRITE RATE OUTRUNS IT, and a reclaimer must never share a gate with the producer it cleans up after.…

AN AGE CANNOT BOUND A STORE WHOSE WRITE RATE OUTRUNS IT, and a reclaimer must never share a gate with the producer it cleans up after. Measured 2026-08-31 on wikipedia; both halves were wrong at once and each hid the other.

HALF ONE — the shared gate. corpus_maintenance::sweep_once gated BOTH phases on unindexed_rows_estimate() >= 5000. But newsworthy_watcher.rs:942 folds every tick's writes into the index immediately (idx.optimize(None)), on purpose, so search never degrades — which pins unindexed PERMANENTLY below that floor. Daemon logs, cycle after cycle: 'sweep: cycle complete checked=41 acted=0 failed=0 max_unindexed=3153 floor=5000'. The producer of versions was suppressing the exact signal the reclaimer waited on. Neither subsystem is wrong alone; together they leak forever. The watcher's own call-site comment says 'Pruning is destructive and stays the maintenance sweep's decision: None is passed deliberately' — correct delegation to a sweep that could never fire.

HALF TWO — the age. Even on the rare cycle it DID fire, prune_days=7 had ZERO eligible versions: wikipedia writes ~850 manifest versions a day, so all 5,972 it retained were younger than the window meant to bound it ('find _versions -mtime +7' returned 0). The one historical firing in the logs reclaimed 6.8GB/126 versions — a thin tail that happened to age past the line. THE MEASUREMENT THAT SETTLES IT: chunks.lance/data held 166GB across 2,736 fragments; the CURRENT manifest referenced THREE, 12.3GB. 153.9GB was retained solely to support time-travel to 5,882 superseded versions.

THE TRAP THAT COST 12GB: 'svrn corpus optimize wikipedia --prune-days 7' exits 0, prints 'pruned 0 version file(s), 0.00 GB', and GROWS the corpus 201.80 -> 213.91 GB, because compaction is non-destructive and writes a fresh ~6GB fragment each run. A green exit on a run that made the problem worse. Every optimize that prunes nothing adds ~12GB, so do NOT iterate experimentally. The CLI now reports this case out loud.

THE FIX. Retention is two bounds in one decider (corpus_engine::index::maintain::Retention::cutoff_days): min_age_days is READER SAFETY, keep_versions is SPACE, composed with max(). max() not min(): the count bound may reach FURTHER BACK than the age floor, never NEARER — swapping it deletes a version an in-flight reader holds. State the consequence plainly: the smallest reachable directory is whatever the corpus writes during min_age_days, so a corpus still over budget needs a SHORTER FLOOR, not a smaller count. The sweep now gates the phases independently — expensive fold on unindexed_rows_estimate(), cheap prune on version_count(), one metadata listing each.

RESULT: 221.85GB / 2,813 fragments / 6,035 versions -> 96.31GB / 451 / 871. 5,167 version files and 132.89GB reclaimed in 117.8s. Versions settled at 871 = ~one day of writes, exactly what the design predicts, and now bounded instead of growing. Defaults PRUNE_DAYS 7->1, KEEP_VERSIONS=1000 added. Gate: lint --full exit 0, 11,424 tests pass 0 fail.
