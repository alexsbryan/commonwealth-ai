# A SPLIT THAT LOSES CONTENT AND A CORRECT SPLIT LOOK IDENTICAL IN A LINE COUNT — SO A SPLITTER MUST PROVE CONSERVATION BEFORE IT WRITES.…

A SPLIT THAT LOSES CONTENT AND A CORRECT SPLIT LOOK IDENTICAL IN A LINE COUNT — SO A SPLITTER MUST PROVE CONSERVATION BEFORE IT WRITES. Found 2026-09-01 splitting `enrich_cmd/build.rs` (1747 lines) during the ontology-v1 P0 crate split.

WHAT HAPPENED: the splitter's first run produced 1303 lines from a 1747-line input. 444 lines silently vanished, and the output was PLAUSIBLE because two independent bugs cancelled into a believable shape:
  - `^impl Step` also matched `impl StepOutcome`, mis-attributing an item;
  - the `{`-vs-`;` item-terminator test read only an item's FIRST line, so every multi-line `fn` signature took the `;` branch and truncated the body.

WHY "IT COMPILES" WOULD NOT HAVE CAUGHT IT: the losses were WHOLE items. A file missing entire functions still compiles if nothing left behind calls them — it just compiles to something smaller and wrong. A test run only catches it if a test happened to cover the lost item. And a human reviewing four new files against one old file has no cheap way to notice 444 absent lines.

THE GUARD (cheap, and it is the whole lesson): before writing ANY output, assert that every non-blank character of the input is claimed by exactly one output. Not a line count — a partition. After the guard was added it REFUSED three more times until each stray comment block was explicitly assigned, and two further latent bugs surfaced from the same investigation: `brace_end` counted braces inside `format!("{}")` string literals, and `lead` did not attach plain `//` comment blocks to the item they precede.

THIS IS THE SECOND TOOL-VALIDATION FAILURE IN ONE NIGHT FROM THE SAME WORKER, and they fail in opposite directions — worth holding both:
  - the import scanner FABRICATED findings (invented two missing names and hid a definition) — note 344d10d1;
  - the splitter SILENTLY DROPPED input.
Both were caught by instrumenting the tool against a known input, not by reasoning about its output. A refactoring tool is a measuring instrument: validate it on an input whose answer you already know before trusting it on one you do not (ARCH §18.4).
