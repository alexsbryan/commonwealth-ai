`hf download` DOES NOT RESUME LARGE FILES ACROSS PROCESS RESTARTS on this host (hf 1.23 xet backend — verified twice, 2026-08-01, during the DeepSeek-V4-Flash 155 GB pull). Kill + relaunch abandons every in-flight `.incomplete` (fresh random-suffixed partials appear beside the old ones) and the xet chunk cache (~/.cache/huggingface/xet) held only 38 MB — so a restart re-downloads abandoned shards from byte 0. Cost when trusted blindly: a relaunch at 84% complete was about to re-pull ~98 GB over ~40 Mbps Wi-Fi (~5.5 h).

SALVAGE RECIPE (verified — both shards sha256-clean): the abandoned `.incomplete` is a clean byte PREFIX of the target file. (1) pick the LARGEST `.cache/huggingface/download/<variant>/<prefix>*.incomplete` — the target's sha256 is embedded in the partial's filename; (2) `curl -sfL -r <partial-size>- <resolve URL> >> partial` to append the tail; (3) verify against the LFS pointer (`https://huggingface.co/<repo>/raw/main/<path>` returns oid sha256 + exact size); (4) mv into the final location. 281 + 696 MB of tail fetched instead of 98 GB.

RELATED FAILURE MODE: the first attempt STALLED SILENTLY overnight — process alive, zero writes, zero errors logged (Wi-Fi blip → dead TCP that never times out). Pair any multi-hour `hf download` with a stall watchdog (no file writes in 15 min → alert) and expect ~40 Mbps effective on RuggedFox Wi-Fi (~9 h per 155 GB) until the box is wired — it has an unused 2.5 GbE port; wiring also cuts BeefyMac's ~47 GB shard-warm from ~2.6 h to minutes.
