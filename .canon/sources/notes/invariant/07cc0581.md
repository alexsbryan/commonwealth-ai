# Daemon force_tool_calls=true (and SOVEREIGN_FORCE_TOOL_CALLS=1) grammar-locks output to JSON tool envelope on every emit. Codex + opencode…

**Daemon `force_tool_calls=true` (and `SOVEREIGN_FORCE_TOOL_CALLS=1`) grammar-locks output to JSON tool envelope on every emit. Codex + opencode both default `tool_choice="auto"` → infinite tool-call loops. Confirmed by H1 isolation 2026-05-12.**

`[daemon] force_tool_calls = true` in `~/.sovereign/config.toml` (and the equivalent `SOVEREIGN_FORCE_TOOL_CALLS=1` env var) installs the JSON-Schema tool-envelope grammar on every tools-using request that came in with `tool_choice="auto"` or unset — promoting it internally to `"required"`. The model can then emit only `{"name":..., "arguments":{...}}` envelopes; a regular assistant message is grammar-impossible.

Why: Codex 0.130 and opencode both default to `tool_choice="auto"`. With this flag on, every turn — including turns the model wants to terminate with a final answer — produces another tool call. The harness runs it, sends the result back, model emits another forced tool call, loop.

Empirical isolation (2026-05-12, FINAL-Bench_Darwin-35B-A3B-Opus model):

| Test | force_tool_calls | tool_choice | finish_reason | Output |
|---|---|---|---|---|
| A — no tools | n/a | n/a | stop | "Hi!" |
| B — tool present, prompt says "no tool needed" | true | auto | tool_calls | `{"name":"shell","arguments":{"cmd":"echo $((2+2))"}}` |
| C — same as B | false | auto | stop | `"2+2 is 4."` |
| D — multi-turn [user, assistant(tool_call), tool(result)] | false | auto | stop | proper final message |

C vs B is the unambiguous proof: same request body, only daemon config differs. Codex retested with `force_tool_calls=false` produced "MARKER_OK" + exit cleanly (9,845 tokens).

How to apply:

- Default `force_tool_calls=false` for any daemon serving codex/opencode/Claude Code / any harness that uses `tool_choice="auto"`. The grammar still engages when clients send `tool_choice="required"`, which is the original "no parse failures on tool envelopes" guarantee.
- Set `force_tool_calls=true` only for tool-only workflows (Aider single-tool sessions, autonomous loops that never need narration) where every output should be a tool call.
- When investigating "model loops on tool calls" with ANY harness: check `~/.sovereign/config.toml` `[daemon] force_tool_calls` first. It's the single biggest root cause of loop-on-tool behavior.
- The `<tool_call>{...}` markup parse failures on Qwopus / FINAL-Bench that originally motivated the flag are handled by the marker-based parser's fallback path (`parse_tool_calls_with_errors`). Loss-of-loop bug is worse than rare parse-failure bug; the trade is wrong.

Config chain: `~/.sovereign/config.toml [daemon].force_tool_calls` → `daemon_cmd.rs` sets env → `inference_adapter::force_tool_calls_env()` → `tool_envelope_schema_for_with_env()` → grammar install.
