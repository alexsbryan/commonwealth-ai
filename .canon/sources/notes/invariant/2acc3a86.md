corpus_complete_unit triggers coordinate_merge on phase=Merging; coordinate_merge synthesizes partitions from work queue; pull uses GET /internal/index/serve

The work-queue (pull-based) collaborative ingest path has three load-bearing wires that were originally missing — without any one of them, peers complete their units and the merge silently never runs, leaving every node with a `<corpus>-partition-<self>/` dir but no canonical `<corpus>/`.

1. Merge trigger — `routes_internal::corpus_complete_unit` checks `matches!(phase, HandoffPhase::Merging)` after `complete_unit` returns and calls `spawn_queue_merge`. The original author left `// that wiring lives in the caller` at `work_queue.rs:354-355` and never wrote the caller side. Don't remove the if-block or the merge will never fire on the queue path.

2. Queue-aware coordinate_merge — `ShardManager::coordinate_merge` checks `handoff.is_queue_mode()` (= `partitions.is_empty() && phase != legacy_open`). In queue mode it synthesizes `IngestionPartition` entries from `WorkQueueManager::snapshot().participating_peers` and skips the partition-status polling loop (every entry is already Complete by definition since `complete_unit` only flipped phase to Merging when all units terminated). Requires `ShardManager::with_work_queue(...)` at construction; without it, queue-mode merges log a warning and become a no-op.

3. Pull endpoint — `GET /internal/index/serve` (NOT `POST /internal/index/transfer`). The transfer endpoint reads the request body (upload semantics); serve writes the response body (download). The original `fetch_remote_shard` did POST-no-body and silently failed against the upload endpoint. Both ends use a flat-content tar (`tar cf - -C partition_dir .`) so the puller's `tar xf -C dest_dir` lands `_corpus_meta.json` directly in `dest_dir` — a wrapper-layer tar produces `dest_dir/<corpus>-partition-<peer>/_corpus_meta.json` which `merge_partitions` won't recognize.

When debugging a stalled queue-mode ingest:
- `grep complete_unit ~/.sovereign/logs/daemon.log` on the coordinator — should show `phase = Merging` after the last unit lands
- `grep coordinate_merge ~/.sovereign/logs/daemon.log` — `synthesized partitions from work queue` confirms the queue-mode path engaged
- `grep index_serve ~/.sovereign/logs/daemon.log` on each peer — `tarred and returning partition-of-self` confirms the puller actually pulled

If the coordinator's `participating_peers` is empty (e.g. queue lost across daemon restart), the synthesized list contains only the coordinator's own partition and the merge produces a "merge with available shards" warning. Cure: re-run collaborative ingest.
