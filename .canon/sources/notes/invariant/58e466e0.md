THREE sovereign-cli CONTRACT TESTS JUDGE A BINARY THEIR OWN BUILD DOES NOT REBUILD, SO THEIR VERDICT DEPENDS ON TARGET-DIR STATE RATHER THAN ON SOURCE. Found 2026-09-01 in the ontology-v1 wave.

    cli_contract_flags::flags_missing_from_their_own_help_do_not_grow
    cli_journey_dispatch::every_journey_step_dispatches
    cli_contract_code::direction1_dev_build_every_canonical_command_dispatches

`sovereign-cli` is a thin dispatcher that `exec`s sibling binaries. These tests run the dispatcher, so what they actually judge is the SIBLING (`sovereign-cli-llm` for `recipe`, `mesh`, `enrich`, …). `cargo test -p sovereign-cli` builds sovereign-cli and the libs it depends on; it does NOT build another package's BINARY target. So the sibling on disk can be arbitrarily old.

MEASURED, same source tree, two target dirs:

  main tree      sovereign-cli 22:58, sovereign-cli-llm 17:20 (AFTER `recipe new`/`migrate` landed)  → 3 tests PASS
  p2 worktree    sovereign-cli 23:07, sovereign-cli-llm 15:59 (BEFORE those verbs landed)            → 3 tests FAIL

The failure reads "15 declared flags are missing from their command's own --help, above the baseline of 11", naming `svrn recipe new --ontology`, `--id`, `svrn recipe migrate --ontology-version`, `--dry-run` — i.e. exactly the flags whose help text lives in the stale sibling. It looks like a docs/contract defect and is not one.

TWO CONSEQUENCES:
1. In a fresh worktree with a private CARGO_TARGET_DIR (the multi-worktree topology), these three fail on a tree that is entirely correct. Fix: `cargo build --bins --features sovereign-cli/dev-tools,corpus-engine/treesitter` before the test run. A prediction that "merging and re-running clears it" is WRONG — nothing in the test run refreshes the sibling; only an explicit bins build does.
2. In the main tree they pass only because something else happened to rebuild the sibling that day. That is luck, not coverage: the same three could go green over a genuinely broken help text if the stale binary happened to be a good one. A gate whose verdict is a function of build-directory state is not measuring what it claims (ARCH §18.1).

REAL FIX (not done): make the dependency explicit — have those tests build or require a current sibling (a build-script/`escargot`-style step, or an assertion that the sibling's mtime is newer than its sources), so the test cannot silently judge yesterday's binary. Related: `AGENTS.md` already warns "rebuild the sibling that owns the verb you changed, or your change won't run"; this is that trap reaching the test suite rather than a human.
