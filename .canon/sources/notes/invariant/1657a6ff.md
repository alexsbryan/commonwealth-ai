build_self_manifest must derive provider.name via resolve_primary_model_name(provider), not by size_gb. A larger code slot must not shadow the chat primary in peer attribution.

`sovereign-mesh::inference_adapter::build_self_manifest` derives the OICP
`provider.name` (what peers see attributing replies, what "model_name @
peer" UIs render) by calling `resolve_primary_model_name(provider)` —
i.e. `provider.model_id_for(Speed::Slow)`, falling back to Fast, then a
`"sovereign-local"` sentinel.

Why: before 2026-05-10 the function picked the largest model in the
emitted manifest by `size_gb`. That heuristic broke when the code slot
GGUF was larger than the chat primary's — observed when the user swapped
the primary to `FINAL-Bench_Darwin-36B-Opus-Q6_K` (~28 GB) while keeping
`Qwopus3.6-35B-A3B-v1-Q8_0` (~34 GB) in the code slot. Peer-side OICP
manifests advertised the code model as the provider identity; mesh
attribution and capability scoring both went wrong.

How to apply:
- Any change to the OICP manifest building path should preserve the
  `resolve_primary_model_name(provider)` call.
- Don't reintroduce a "pick by size_gb" heuristic for primary
  identification. Size_gb is appropriate for capacity / VRAM-budget
  comparisons; it is NOT a primary-identity signal.
- Regression test: `manifest_provider_name_is_chat_primary_not_largest_slot`
  in the `self_manifest_tests` module of `inference_adapter.rs`.
- Cross-ref: `invariant_daemon_no_slot_aliases.md` covers a separate
  primary-identity issue on the `/v1/chat/completions` side.
