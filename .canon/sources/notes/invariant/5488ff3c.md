# THE "Raw cargo output" PATH IN A GATE REPORT IS WRONG WHENEVER CARGO_TARGET_DIR IS REDIRECTED — IT POINTS AT A STALE LOG, AND THE STALE LOG…

THE "Raw cargo output" PATH IN A GATE REPORT IS WRONG WHENEVER CARGO_TARGET_DIR IS REDIRECTED — IT POINTS AT A STALE LOG, AND THE STALE LOG READS AS "NO ERRORS". Found 2026-09-01 by the P0 worker after the supervisor sent it to the wrong file.

CAUSE: `scripts/sovereign-lint.sh` (~line 399) sets `RUN_DIR="${REPO_ROOT}/target/sovereign-lint/latest"` — the REPO ROOT's `target/`, not `$CARGO_TARGET_DIR`. Under the ontology-v1 broker every worktree builds into a private target dir (`~/dev/cw-ont-target-pN`), so the two diverge: the live log lands under the WORKTREE's `target/`, while the redirected dir holds whatever run last wrote there — in this case one ~14 hours old.

  live:   ~/dev/cw-ont-p0/target/sovereign-lint/latest/cargo.raw.log
  stale:  ~/dev/cw-ont-target-p0/sovereign-lint/latest/cargo.raw.log

WHY IT IS WORSE THAN A WRONG PATH: the file is cargo JSON, one object per line. `grep '^error'` over it returns NOTHING — which reads as "the build is clean" rather than "you are looking at the wrong file, in the wrong format". Two silent failures stacked. Reading errors out of it needs a JSON pass selecting `message.level == "error"` and its primary spans, not a text grep.

PRACTICAL RULE: when a gate is run through a wrapper that redirects `CARGO_TARGET_DIR`, do not trust the triage path the banner prints. Resolve it against the worktree's own `target/`, and parse the JSON. Same family as note `58e466e0` (a test judging a binary its build never refreshed) and the stale-binary-as-measurement trap: a redirected target dir makes several "obvious" paths point at yesterday.

RELATED FINDING FROM THE SAME ROUND — the error was not what the call sites suggested. Three failing lines all CALLED `read_latest_run`, so the natural inference was that the function was still too narrow; it was already `pub(crate)`. What was private was its RETURN TYPE (`LatestRun`). Widening a function does not carry the types in its signature with it. A sweep for "private type in a public signature" that matches `^pub fn` will never examine a `pub(crate) fn` or `pub(super) fn` — exactly the visibilities a crate split manufactures. The rule is level-relative: for an item of visibility V, no type in its signature may be less visible than V.
