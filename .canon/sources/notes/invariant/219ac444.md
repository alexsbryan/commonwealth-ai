THE GUARD THAT WAS SUPPOSED TO STOP ROTATE FROM PARTITIONING THE MESH SHIPPED INERT, AND IT WAS THE SECOND HALF OF THE SAME BUG (found + fixed 2026-08-27, branch mesh-multi-membership). Extends 07c2e829, which fixed the steady-state partition; this is the same failure re-entering through the UPGRADE WINDOW.

WHAT WAS WRONG. `EmbeddedDaemon::rotate_invite` (daemon.rs ~1663) refused with `PreSplitPeersOnline` while any online peer was still pre-split. The filter read:

    .filter(|_| mesh.mesh_secret == [0u8; 32])

`|_|` ignores the member. `mesh.mesh_secret` is OUR OWN credential, and it is non-zero on every migrated node — so the predicate was ALWAYS FALSE, `stale` was ALWAYS EMPTY, and the refusal NEVER FIRED. Rotation proceeded and silently partitioned exactly the peers the guard named. The doc comment directly above it cites ARCH §18.3 against that substitution.

The inverse also broke: on a node whose own secret was not yet migrated, EVERY online peer got named, including fully upgraded ones.

WHY NOTHING CAUGHT IT. `PreSplitPeersOnline` appeared in ZERO tests across the workspace. 1460 passing tests in the mesh crates said nothing about it. ARCH §18.1 exactly: a check with no failing input you can name is not a check. It also passed a full lint and a human read, because the line is short, plausible, and mentions the right field.

THE CATEGORY ERROR, WHICH IS THE GENERALISABLE PART. The guard asked a PER-PEER question ("is this peer pre-split?") of a MESH-WIDE field. `mesh_secret` is one value for the whole mesh; no member record carries a per-peer copy, so the question as written was not expressible. When a filter's closure ignores its argument, that is the tell — the predicate is not about the thing being filtered.

THE FIX. A peer's build generation is visible ONLY in the gossip payload it just sent (a pre-split peer omits `mesh_secret`, serde defaults it to zero), and it is discarded the moment the merge ends. So capture it there:
  - `MergeReport::peer_pre_split` — set in `Mesh::merge_from`, meaningful only when `!rejected` (a refused merge tells you nothing about the sender).
  - `AppState::observe_peer_split_generation` / `peer_confirmed_post_split` — the gossip round records it per node_id in `AppState::peer_post_split`.
  - The guard now requires EVERY online member to be CONFIRMED post-split. UNKNOWN COUNTS AS UNSAFE, so a freshly booted daemon refuses until it has gossiped once with each peer. One round clears it.

DELIBERATELY NOT A `MemberRecord` FIELD. This is our own observation of a peer's payload, not a claim the peer makes about itself and not something a third node may assert on its behalf (§18.1 — never let the subject supply the field a guard reads). It also keeps the four MeshWire mirrors untouched, which is the trap 07c2e829 already documented.

EVIDENCE, RED-FIRST. `tests/rotate_pre_split_guard.rs`, 5 cases. Against the inert filter 3 of 5 fail; the headline one reports:
    expected PreSplitPeersOnline, got Ok(RotatedInvite { join_key: "cwth-e3a8-0aae-033b", ... })
i.e. rotation SUCCEEDED with an unconfirmed peer online. The 2 that pass either way assert rotation SUCCEEDS (--force, and a fully-upgraded fleet) — they guard against an over-strict guard, not an inert one, so passing on both sides is correct and expected.

STANDING LESSON. A mixed-version fleet is not an edge case to test last, it is the only configuration in which upgrade-window guards have any input at all. Both machines on new code makes this class of bug permanently invisible. Keep one peer on the old build while verifying anything gated on "has the fleet upgraded yet".
