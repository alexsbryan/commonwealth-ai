macOS builds use lld (.cargo/config.toml [target.{aarch64,x86_64}-apple-darwin] rustflags '-fuse-ld=lld'). Unlike ld64, lld does NOT inject an implicit @loader_path/@executable_path rpath, so binaries linked against co-located dylibs (llama-cpp-sys-2 ships libggml-*.dylib into target/<profile>/) crash at startup with dyld 'no LC_RPATH's found' for libggml-base.0.dylib. Mitigation already in tree: both apple-darwin rustflags blocks add explicit '-Wl,-rpath,@loader_path' and '-Wl,-rpath,@executable_path'. Do NOT remove either rpath flag when touching this file; do NOT switch back to system ld64 without dropping the explicit rpath args (harmless duplicates with ld64, but worth knowing). If a pre-existing release binary still has zero LC_RPATH after a rebuild, run: install_name_tool -add_rpath @loader_path target/release/sovereign-cli && install_name_tool -add_rpath @executable_path target/release/sovereign-cli — but the real fix is rebuild so the rustflags take effect. Reproduced 2026-05-17 after commit 76d4c4a introduced lld; daemon failed to start until rpaths added.
