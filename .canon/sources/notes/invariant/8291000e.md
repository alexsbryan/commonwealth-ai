THE ACTUAL MECHANISM (instrumented and proven, not inferred). The real llama.cpp error is NOT "n_tokens == 0" and NOT "DeltaNet state can't be rewound". It is:

```
init: the tokens of sequence 0 in the input batch have inconsistent sequence positions:
 - the last position stored in the memory module ... for sequence 0 is X = 209
 - the tokens for sequence 0 in the input batch have a starting position of Y = 189
 for M-RoPE, it is required that the position satisfies: X < Y
```

Temporarily instrumenting the `Ok` arm at `model_slot.rs` (in `prefill_reusing_prefix`) — behaviour unchanged, then reverted — printed the decisive bool:
- hybrid `qwen35`: `partial clear returned removed=FALSE lcp=189`
- control `gemma4`: `partial clear returned removed=TRUE lcp=191`

So `llama_memory_seq_rm` REFUSES partial-range removal on a recurrent/hybrid memory module, the KV positions are therefore never rewound (X stays 209), and the next batch starting at Y=189 trips M-RoPE's strict-monotonicity check. It is a REFUSED TRUNCATION surfacing as a position desync — not state corruption.

LATENT DEFECT (real, unfixed, worth a PR). `vendor/llama-cpp-4/src/context/kv_cache.rs:80` — `clear_kv_cache_seq` returns `Result<bool, KvCacheConversionError>`. The `Err` arm is ONLY a u32→i32 overflow; llama.cpp's own verdict rides in the `Ok(bool)`. Handling `Ok(false)` would make recurrent models degrade to a full prefill instead of erroring, turning the gate into defence-in-depth rather than the only thing preventing a hard failure.
