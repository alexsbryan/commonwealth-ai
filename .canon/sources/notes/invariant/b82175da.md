# THE ENTIRE POST-CONFIG HALF OF svrn setup IS UNREACHABLE — verified 2026-08-06, both entry points, not just the direct one.

THE ENTIRE POST-CONFIG HALF OF `svrn setup` IS UNREACHABLE — verified 2026-08-06, both entry points, not just the direct one.

THE CHAIN (every hop cited, nothing recalled):
- `daemon_cmd/mod.rs:122` — `let mut forwarded = vec!["--wizard-only".to_string()]` — the `svrn daemon --setup-only` path PREPENDS the flag.
- `setup_cmd/mod.rs:92` — `invoked_via_daemon_path = args.iter().any(|a| a == "--wizard-only")` — true for that path.
- `setup_cmd/mod.rs:94-105` — if NOT that path (i.e. a direct `svrn setup`), FORCE-APPEND `--wizard-only`.
- `setup_cmd/args.rs:28` — either way `opts.wizard_only = true`.
- `finish.rs:68` — `if opts.wizard_only { ...; return 0; }`.

So there is NO invocation of setup that reaches `finish.rs:78` onward. Dead in production: service install, the 30 s `wait_for_daemon`, `diagnose_daemon_failure`, the inline doctor health check, the mesh/endpoint banner, the "Next steps: svrn chat session / svrn model list" banner, and the opencode config write.

THE PRIOR SURVEY UNDERSTATED THIS. Note 9ae0b9a5 said the tail was dead "for that path" (direct `svrn setup`). It is dead for BOTH paths, because the daemon path prepends the same flag that the direct path force-appends. Do not re-derive this as a one-path problem.

MOST OF THE TAIL IS *CORRECTLY* DEAD, and the code says so at `finish.rs:62-67`: service registration would compete with the daemon for `:9741`, and service install deliberately moved to `svrn install-service` in Phase 4. So the tail is vestigial, not broken — deleting it is net-simplification work, NOT a bug fix. Left in place deliberately this commit (ARCH §10.2: a refactor must not "just clean up some nearby stuff").

THE ONE PIECE THAT WAS GENUINELY ORPHANED: the opencode config write. Writing `~/.config/opencode/opencode.json` does not compete for `:9741`, so it had no reason to sit below the service-install gate. FIXED: extracted to `write_opencode_config(client_port)` and called ABOVE the early return, right after the config save. This is what made `svrn doctor`'s hint at `doctor_cmd.rs:1186` ("Run `svrn setup` to write it") impossible to satisfy by any invocation.

THE TEST COVERAGE WAS POINTING AT THE WRONG FUNCTION (ARCH §18.1 — a gate nobody has watched fire). `install_opencode_config` (the no-arg wrapper, `opencode.rs:67`) had exactly ONE non-test caller: the dead line at `finish.rs:144`. All eight tests in `setup_cmd/mod.rs` (:907, :950, :979, :981, :989, :990, :1023, :1057, :1075) call `install_opencode_config_at` directly. So the wrapper production would have used was uncovered, and the covered function was one production never called.

ALSO FIXED THIS COMMIT: `doctor_cmd.rs:398` emitted `Repair::Executable("svrn index project")` — `index` has never been a verb in any build. The real verb is `refresh` ("Rebuild the project code index", `sovereign-cli/src/main.rs:423` → sibling `project-refresh`, `sovereign-cli-dev/src/main.rs:101`).

STILL WRONG, deliberately deferred: `doctor_cmd.rs:292` emits `Repair::Executable("svrn code index .")`, which exits 2 on a shipped build because `code` is a DEV_VERB. That hint becomes TRUE when `sovereign-cli-dev` ships in the release tarball; fixing the string instead of shipping the binary would be treating the symptom.
