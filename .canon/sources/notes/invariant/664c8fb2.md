HARNESS WORKTREE ISOLATION DOES NOT GUARANTEE A main-BASED BRANCH — VERIFY THE BASE AS STEP ZERO OF EVERY WORKTREE ORDER.

MEASURED 2026-08-16 (financial-corpora, three concurrent worktree workers spawned in one message). `isolation: "worktree"` branched from a STALE LOCAL TIP (40e5c98a), not from main, and it did so INCONSISTENTLY across three agents spawned minutes apart:

- M3 (`wt-sec-coverage-card`): HEAD == main (4eccc77c). Correct, by luck of timing.
- M2: HEAD 1a1737cb = a MERGE of main into the stale tip. 0 behind main, 19 AHEAD. Usable — every artifact present — but its branch carries 18 commits of A PEER SEAT'S UNLANDED WORK (deep-research T1, serve50 fleet scaling, code-intel-reindexer-fix).
- G3: HEAD 40e5c98a, the stale tip WITHOUT the merge. DIVERGED, not behind: 22 commits in main absent from HEAD, 18 in HEAD absent from main, `merge-base --is-ancestor HEAD main` false. The entire SEC line was missing — scripts/sec_facts.py, corpus-engine/.../analysis/sec_facts.rs, the recipe, the concept map, and the frozen prereg that is F2's instrument.

THE TWO FAILURE MODES, and the second is the dangerous one:
1. MISSING FILES — loud. G3 could not find a single artifact its order named, diagnosed it in one turn, and stopped without touching anything. Cheap.
2. FOREIGN COMMITS ON THE BRANCH — SILENT. M2 has everything it needs and nothing looks wrong, but merging its branch at landing would drag a peer seat's 18 unlanded commits onto main. One seat landing another seat's work is a recorded miss here (926bb331). Nothing in the worker's day-to-day would surface this; only the seat checking topology catches it.

STEP ZERO FOR ANY WORKTREE ORDER (put it in the spawn prompt, do not rely on the worker thinking of it):

    git rev-list --count HEAD..main        # MUST be 0
    git rev-list --count main..HEAD        # anything > 0 that is not yours = foreign commits
    ls <two or three files the order actually names>

PRE-AUTHORIZE THE REPAIR IN THE PROMPT so a base error costs zero round trips: `git checkout -b <fresh-name> main`. That is safe — a NEW branch from main leaves the existing branch and any live peer's history untouched. What is NOT safe, and must never be pre-authorized: rebasing, resetting or deleting the provisioned branch, because `git branch --contains` showed the stale tip on THREE branches, one of them checked out in a LIVE peer worktree. Rewriting it would rewrite base state under a running worker and orphan another initiative's commits.

LANDING RULE THAT FOLLOWS: when a worker's branch carries commits that are not its own, CHERRY-PICK ITS COMMITS ONTO main — do not merge the branch. That requires each commit to be ATOMIC AND SELF-CONTAINED, so tell the worker up front; a commit that only builds when a sibling is present makes the cherry-pick fail at exactly the wrong moment.

WHAT THE WORKER DID RIGHT, worth copying: it did not self-repair. It found three branches containing the stale tip and a live peer checked out on that history, recognised the fix as a topology call above its authority, and escalated-and-waited rather than quietly branching off main — which would have meant running the order against a base the seat had not chosen (principle 6). Nothing written, no scope declared, nothing rebased. That is the escalation clause working as designed.</content>
