A JOURNEY STEP MUST NEVER BE ABLE TO CONSUME THE MANIFEST THAT DRIVES IT (2026-07-29, sovereign/scripts/cli-journey-verify.sh attempt_step). Companion to note f5acdf59.

THE RULE. The runner pipes the plan into its read loop (`done < <(plan_source)`, ~line 523). Any step command invoked WITHOUT `</dev/null` inherits that pipe as its stdin, so a command that reads stdin eats PLAN ROWS. The loop then resumes mid-manifest with cur_id still set to the current journey and BINDS A LATER JOURNEY'S STEP TO IT. attempt_step now runs every command with `</dev/null`; the redirect is load-bearing, not hygiene.

HOW IT PRESENTED. `corpus remove` prompts for confirmation. It ate the rows after corpus-lifecycle[4], and corpus-lifecycle[5] was RECORDED IN THE JSONL as `atos teardown {feature_id}` — atos-feature's step 5, same index. The journey reported a plausible "partial 5/6" with "no fixture for a placeholder", so a MISSING ASSERTION was dressed as an ordinary missing fixture. Exactly 1 of 57 recorded steps was affected, so it was invisible in aggregate. Cross-check method that found it: compare each JSONL-recorded `run` verb against the plan row for the same (journey, index).

WHY IT HAD BEEN UNREACHABLE. corpus-lifecycle[3] (chat inspect) failed on the stdout/stderr inversion, and a failed step kills the remainder of the sequence — so step [5] was never reached and the binding bug could not surface. THREE LAYERS: the stdout bug masked the stdin bug, which masked the product defect below. Fixing the outermost is what made the next visible. Expect this pattern; do not assume the first green means done.

THE PRODUCT DEFECT IT REVEALED, NOT FIXED. `svrn corpus remove <id>` prompts, and on EOF `std::io::stdin().read_line()` returns Ok(0) — NOT an error. The empty answer parses as "not yes", the removal ABORTS, and the command still EXITS 0. So `corpus remove x </dev/null` (any script, any CI, any harness) is a SILENT NO-OP THAT REPORTS SUCCESS. The is_err() branch that prints "aborted (could not read stdin)" is unreachable on EOF. The journey now passes `--yes` (the correct fix for a non-interactive lane), but the underlying behaviour stands and deserves an explicit call: arguably a non-TTY stdin with no --yes should exit non-zero rather than pretend the operator declined.

GENERAL LESSON for this manifest: any mutating step whose command can prompt MUST carry its non-interactive flag explicitly. A harness cannot answer a question, and the failure mode is a vacuous pass, not a hang. Worth auditing the other mutating steps for the same shape.
