# pi-coding-agent declares agent_end when the model emits zero tool calls in a turn — there is no max-iteration counter

pi-coding-agent declares agent_end when the model emits zero tool calls in a turn — there is no max-iteration counter

`@earendil-works/pi-agent-core/dist/agent-loop.js` line 84-165 — pi's
agent loop exits as soon as the assistant message contains no
`toolCall`-typed content. There is no `maxIter`/`maxTurn`/`maxStep`
counter; the loop is purely tool-call-driven.

Code-side relevant snippet:

```js
hasMoreToolCalls = false;
if (toolCalls.length > 0) {
    const executedToolBatch = await executeToolCalls(...);
    hasMoreToolCalls = !executedToolBatch.terminate;
}
```

If the model emits a text-only response (chat about the plan,
"thinking out loud," explanation prose), pi declares the agent done
and the bench reports `ExitReason::Completed` with insufficient
tool calls.

Why: standard tool-use API semantics — `finish_reason=stop` with
no `tool_calls[]` means "the model is done." Cursor / Claude /
codex all treat it the same way. Pi did not invent a stop heuristic;
it inherited it.

How to apply:
- The fix for "agent stopped after 2 reads with 0 writes" is NOT
  "raise pi's max-iter" (doesn't exist) — it's either (a) sharper
  prompt that forces the model to emit a write tool call before
  text, (b) grammar alternation in sovereign-inference so plain
  text is *also* a legal continuation but tool calls remain
  available, or (c) a `shouldStopAfterTurn` hook that re-injects
  a continuation instruction when work is incomplete.
- See `sovereign-agent-bench/HANDOFF.md` "Three system bugs
  deferred" — this is Bug B.
- Related: [[invariant-force-tool-calls-locks-model-into-loop]]
  (the opposite failure mode — force_tool_calls=1 traps the model
  in tool calls with no plain-text escape hatch).
