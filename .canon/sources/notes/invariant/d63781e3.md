PREFIX-STATE RESTORE IS NOT BIT-FAITHFUL ON qwen4exp, AND THE REASON IS HOST-SIDE STATE THAT NO SESSION FILE CAN SEE (read from source 2026-08-27; NOT yet measured — the instrument that would settle it is named below).

THE MECHANISM. Flash-Next's PLE n-gram engram hashes each token together with its 2 predecessors (ngram_size=3). Predecessors that fall before the current ubatch come from `ple_hist`, declared at llama.cpp/src/models/models.h:2288 as:

    mutable std::unordered_map<llama_seq_id, ple_history> ple_hist;

It is a member of the MODEL, not the context — and it appears in exactly three places in the whole tree (the declaration, the `ple_history` struct, and the mutation at qwen4exp.cpp:931). There is NO state_read/state_write hook. So `llama_save_session_file` / `llama_state_seq_save_file` do not serialize it, and a restore does not restore it.

WHY IT BITES EVERY RESTORE, NOT JUST CROSS-PROCESS ONES. qwen4exp.cpp:948 guards the history on contiguity:

    if (h.next_pos != ubatch->pos[i]) { h.toks.assign(n_gram - 1, eos); }

After a Learn, generation continues past the pin, leaving `next_pos` well beyond `pin_len`. The next Restore re-enters at `pin_len`, `next_pos` does not match, and the history is reset to EOS padding. So the guard fires on essentially EVERY restore even inside one process.

THE BLAST RADIUS IS EXACTLY 2 TOKENS, traced through `prev()`: ubatch index 0 gets ctx [tok, EOS, EOS] (cut=true); index 1 gets [tok1, tok0, EOS]; index 2 onward is fully correct because both predecessors are in-ubatch. So the 16 engram rows (8 bigram + 8 trigram heads) are wrong for the first two tokens after every restore, feeding a wrong contribution into layer 1 of 48 and propagating.

WHY THIS MATTERS NOW. Note 4993e07d cites "restore is bit-faithful (32/32 greedy-identical…, state_cartridge_spike.rs 2026-07-12)" as the reason the pinned-prefix cache is the answer to Flash-Next's cold-start tax. THOSE RUNS WERE ON qwen35 AND qwen35moe — NEITHER HAS PLE. The faithfulness claim has never been established for qwen4exp, and the pin-thrash fix committed today (6102a3578) deliberately INCREASES how often restores happen.

THE INSTRUMENT ALREADY EXISTS AND WOULD CATCH IT.
    SPIKE_GGUF=<flash-next part 1> cargo test -p sovereign-inference \
      --test state_cartridge_spike -- --ignored --nocapture
Its protocol is exactly the discriminator: ctx A prefills, SAVES, then decodes a suffix and generates M tokens — which pollutes `ple_hist` past the save point — and only then does ctx B load into a fresh context and decode the same suffix. B therefore hits the reset branch and diverges from A. A PASS would falsify this note; a token-for-token divergence starting at token 1 or 2 confirms it. Cost is one model load, not a bench — but Flash-Next needs ~95 GiB GTT, so the daemon must be stopped first.

IF CONFIRMED, the fix is upstream-shaped but small: `ple_hist` is 2 tokens + a position per sequence, so it belongs in the context state alongside the recurrent buffers. Until then, treat prefix-state restore on qwen4exp as a measured-latency win with an UNMEASURED quality cost, and do not repeat the bit-faithful claim for this arch.

SEPARATE, SAME READ: `build_ple` is called inside the layer loop (qwen4exp.cpp:301) and rebuilds its index tensor and re-gathers on every call, though nothing in `set_input` depends on `il` — the gather is byte-identical across PLE layers. Flash-Next declares `ple.layers = [1]`, so it pays this exactly once and there is nothing to fix here today. A later model shipping PLE on many layers would pay it N times, in CPU index work AND in graph splits against a CPU-resident 26.8 GiB tensor.
