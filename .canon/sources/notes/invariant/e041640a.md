THE CONV ENTITY GRAPH IS PER-SOURCE-DOCUMENT. IT CANNOT BRIDGE TWO DOCUMENTS — there is no cross-document edge anywhere in the retrieval path. Verified 2026-08-03 from code + git, not recalled.

THE STRUCTURE:
- `rerank_conv_chunks_via_ppr` (runtime/retrieval/conv_tiered.rs) groups chunks by `(corpus_id, source_doc_id)` and builds ONE `ConvEntityGraph` per source document. `conv_tiered.rs:111` is the ONLY production construction site of that graph in the workspace (grep `ConvEntityGraph::from_` — everything else is tests).
- PPR diffuses INSIDE that single-document graph. A shared entity does NOT create a path from document A to document B. Each document gets an independent entity-relevance prior; those priors then compete in the global re-sort of the conv-chunk pool. Cross-document RANKING effect: yes. Bridge: no.
- `conv_briefing::tiered_group_key` returns `source_doc_id` for EVERY category. Its `_category` and `_corpus_id` params are unused (leading underscores).

WHY THIS FOOLED SOMEONE (it will fool you too): until commit `0a12aa3f` "wiki + folder raptoring", `tiered_group_key` returned `corpus_id` for `watched_folder`, which genuinely DID give folder corpora one cross-document graph. That commit changed it to `source_doc_id` unconditionally and left the comment at `conv_tiered.rs:44` describing the OLD behaviour. The whole `sovereign/bench/conversation-bridge/` design (40 questions, ~1 day of non-delegable authoring) was written against that stale comment. Comment corrected 2026-08-03 in the same commit as the README block.

SECOND, INDEPENDENT CONSTRAINT — PPR IS A RE-RANKER, NOT A RETRIEVER. Signature is `chunks: &mut [ScoredChunk]`: it mutates in place and re-sorts, and NEVER adds a chunk. It runs at `runtime/retrieval/mod.rs:285`, AFTER the deep pipeline truncates to `KQ_MERGED_LIMIT + raptor_n` = 20 leaf chunks + RAPTOR summaries (`retrieval_pipeline.rs:1919`; `KQ_MERGED_LIMIT = 20` at `prompts.rs:362`). A document cosine ranked below that cutoff is not in the array and NO weight can recover it. The entity layer's entire operating room is reordering within ~20 chunks.

CONSEQUENCE FOR ANY FUTURE ENTITY-LAYER BENCH:
- Do NOT write a "positive control" of the form "second document reachable ONLY by entity bridge". That reachability does not exist; the control would fail every run and (by the usual rule) void it.
- Do NOT gate question selection on "cosine cannot find document B" (low inter-doc cosine τ). That selects exactly the pairs where B falls outside the top-20 pool and PPR provably cannot touch it — the falsifier fires for a reason unrelated to the hypothesis, which reads as evidence and is not.
- `bridge_recall@k` is mis-specified: it can only measure what cosine already retrieved, attributing cosine's recall to the entity layer.
- The measurable question is RANK PROMOTION of the hardest required source CONDITIONED ON it being in the pool. The authoring filter inverts: pick pairs where B IS retrieved but ranks low (~11-20).

THE MECHANISM IS NOT TRIVIAL, so the corrected bench is worth doing: conversations in `conversations-anthropic` carry a mean 54.5 distinct entities each (min 1, max 492, n=574 convs) — real graph structure to diffuse over. Seeding requires the entity to appear in the QUERY TEXT (`seed_indices_from_query`: word-boundary match, or >=4-char prefix-stem token match).

CORPUS CENSUS REPRODUCES (so the bench README's feasibility half is sound): 68,464 chunk_entities rows for conversations-anthropic; entities spanning 2-3 convs = 2,211 (README said 2,192 — small drift, archive grew).

STILL UNMEASURED and the gate before any bank authoring: how often does a candidate pair actually put B in the 11-20 rank window? Cheap, needs no authored questions.
