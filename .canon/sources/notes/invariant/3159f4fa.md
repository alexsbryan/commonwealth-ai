# A RELATIVE VISIBILITY IS A CLAIM ABOUT A LOCATION, SO MOVING CODE SILENTLY RE-EVALUATES EVERY ONE OF THEM — WITHOUT CHANGING A CHARACTER OF…

A RELATIVE VISIBILITY IS A CLAIM ABOUT A LOCATION, SO MOVING CODE SILENTLY RE-EVALUATES EVERY ONE OF THEM — WITHOUT CHANGING A CHARACTER OF THE DECLARATION. Found 2026-09-01, ontology-v1 P0 crate split, as a prior correct analysis reversing on its author.

THE CASE: `extract::read_latest_run` was `pub(super)` and called from `build.rs`. Both sat at the crate root, so `pub(super)` meant "visible in `crate`" — it resolved, and the worker checked this explicitly and recorded "no widening needed". That was TRUE WHEN WRITTEN. It stopped being true when `build.rs` became `build/steps.rs`: `pub(super)` then meant "visible in `build`", and the call site was outside `extract` entirely. The declaration never changed; its meaning did. Surfaced as E0364 (`private, and cannot be re-exported`) plus E0603, because a `pub(crate) use` re-export was WIDER than the `pub(super)` item behind it — a re-export can never exceed its target's visibility.

THE GENERAL RULE: `pub(super)`, `pub(in path)` and `pub(crate)` are all statements about where an item SITS. Any move — a file into a directory module, a function between siblings, a test to the other side of a boundary — re-evaluates every such claim in the moved code AND in the code that calls it. Re-check after the move, never before; an analysis of a file is valid only against that file's final POSITION, not merely its final contents. Same shape as the import trim that went stale when a test was relocated afterwards (note 344d10d1): any edit after an analysis invalidates it, and the analysis will not announce that it has gone stale.

TWO COROLLARIES WORTH HOLDING:
- Privacy is DIRECTIONAL — an item private to module `m` is visible in `m` and its DESCENDANTS, never in its parent. A check written as "flag any cross-FILE access" flags the legal direction (child reading parent) and misses the illegal one (parent reading child), which is worse than no check. Model parent/child, not "different file".
- Not every unresolved-name error is a visibility error. Of twelve in this round, only ONE was: `probe_embedder` was already `pub(super)` and simply never imported; `run_extract_step`'s import belonged in the sibling that dispatches to it, not in the parent a trim had correctly cleaned. Reading E0425 as "add `pub`" would have widened two internals that were already correct.

ALSO: a checker that cries wolf on correct code teaches people to ignore it. The same worker's bare-call check threw two false positives (`parse_args`, `write_token_snapshot`) because its `^use` regex did not match `pub use`; it verified both were in scope rather than "fixing" working code, and reported the tool's fault. Do that.
