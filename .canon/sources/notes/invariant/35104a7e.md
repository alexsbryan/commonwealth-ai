Jellyfin 12.0.0 authenticates ONLY via `Authorization: MediaBrowser Token="<key>"`. Probed 2026-09-12 against a live 12.0.0, same API key, GET /Items: X-Emby-Token 401, X-MediaBrowser-Token 401, ?api_key= 401, no auth 401, Authorization 200. Its OpenAPI document declares one security scheme (apiKey, in header, named Authorization) and contains zero occurrences of `emby-token` or `api_key`. Distinct from the already-banked finding that `X-Emby-Authorization`, the CLIENT-identification header, is also dead (note f838b2fc).

House-mesh declaration is therefore:
  printf 'MediaBrowser Token="%s"' "$KEY" | svrn mesh media declare authorization
NOT `declare x-emby-token`, which is what every example shipped before 7f3ca83f8. Jellyfin 10 still wants the old spelling with the bare key, so a mixed house needs both.

The value has an inner space and two quotes and both are load-bearing. wire_value (commonwealth-transport/src/iroh_identity_forward.rs) keeps ' '..='~' and trims only the ends; narrowing it to is_ascii_graphic silently yields MediaBrowserToken="..." and the origin refuses a credential that looks correct in every log. Pinned by a_multi_word_declared_credential_reaches_the_origin_verbatim, which needs --features iroh; sovereign-test.sh's --filter scoping does NOT resolve that feature and reports exit 4 / no tests matched.

origin_fanout NEVER asks this node: a `peers` entry naming self gets a never_asked row (origin_fanout.rs:22-25). A merged catalogue is unprovable on a one-machine mesh by construction, not by bug.

Jellyfin 12 wizard over the API: GET /Startup/FirstUser seeds the user (POST /Startup/User 404s before it), then POST /Startup/User, POST /Startup/Complete, POST ~, POST /Auth/Keys?app=<name>. /Auth/Keys items put AccessToken BEFORE AppName, so selecting a key by app name needs a split on },{ first: grep -A2 '"AppName":"x"' reads the NEXT key's token.
