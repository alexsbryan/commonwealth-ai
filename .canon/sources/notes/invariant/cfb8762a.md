`TenantId` MUST LIVE IN `oicp-types` — THE LAYER MAP LEAVES EXACTLY ONE LEGAL HOME. Derived 2026-08-04 when org and tenant collapsed into one identity spine (mesh compute plan). Verified against quality/ARCH_LAYERS.toml and the Cargo.tomls; do not re-derive, and do not "just put it in sovereign-contracts".

THE CONSTRAINT CHAIN:
1. `TenantId(pub String)` is at sovereign-server/src/auth.rs:92 today. As the mesh's identity spine it must be visible to BOTH families — commonwealth-core (Mesh / MemberRecord / NodeCapabilities.clearance) and sovereign-contracts (CorpusVisibility::Private{owner}, types/mod.rs:904).
2. `[[forbid]] from = "commonwealth-core", to = "sovereign-*"` with NO `except` — ARCH_LAYERS.toml:125-128, reason "mesh foundation must stay consumable without the agent runtime". SO sovereign-contracts IS UNAVAILABLE to commonwealth-core, even though the owner field already lives there. NOTE THE CONTRAST that makes this easy to get wrong: commonwealth-api (:169-173) and commonwealth-daemon (:160-164) BOTH carry `except = ["sovereign-contracts"]`. commonwealth-core deliberately does not.
3. THE FORBID IS A NAME GLOB, NOT A LAYER RULE. So it also rules out `sovereign-time` — the zero-dep contract-layer leaf that is otherwise the exact precedent for "a shared primitive both families need". Any NEW crate created for this must NOT be named sovereign-*.
4. Layer order is contract < mesh-foundation, so sovereign-contracts cannot reach UP into commonwealth-core either. The two crates that need the type cannot see each other in EITHER direction.
5. `oicp-types` is the unique existing crate that satisfies everything: contract layer (bottom), serde-only leaf (oicp-types/Cargo.toml:9-11), and ALREADY a dependency of sovereign-contracts (:14) AND commonwealth-core (:9). ZERO new dependency edges, no ARCH_LAYERS.toml change, no [[exception]] entry.
6. sovereign-server depends on both sovereign-contracts (:66) and commonwealth-core (:78), so it bridges whatever the lower layers cannot.

WHY IT MATTERS BEYOND TIDINESS: once node clearance and corpus owner carry the SAME type, residency policy becomes one predicate over two existing fields — "a corpus owned by tenant T may only be hosted on a node whose clearance set contains T" — checkable continuously and enforceable at registration. That predicate is inexpressible while the two sides are a newtype on one side and a bare String on the other.

NAMING TENSION, ACCEPTED CONSCIOUSLY: oicp-types is named for the inference capability protocol; a tenancy type is a stretch there. SPLIT TRIGGER — if a THIRD shared identity type appears, lift them into a neutral contract-layer leaf (e.g. `identity-types`) rather than growing oicp-types into a junk drawer. Do not add the third type without doing the split.

RELATED DEFECT TO FIX IN THE SAME MOVE: TenantId is an unvalidated free-text String and is now the security root. "Firm", "firm " and "firm" are three distinct tenants, so a clearance check passes or fails on whitespace. Canonical form + validator land WITH the move, not after.
