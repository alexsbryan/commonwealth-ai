THE `svrn setup --fim` FALLBACK BANNER IS THE ONLY INSTALL INSTRUCTION A TARBALL USER EVER SEES — AND IT POINTED AT A TAG STREAM THAT NEVER EXISTED (fixed 2026-07-29, sovereign-cli-daemon/src/setup_cmd/fim.rs `VSIX_RELEASES_URL`).

THE BUG. `install_extension()` finds the vsix by locating `packages/vscode-sovereign` in a source checkout and running `npm run package`. Anyone who installed via `curl https://svrnme.sh/install.sh | sh` has only three binaries and NO source tree, so they always land in `EditorOutcome::Unavailable("extension sources not found (this build isn't running from a repo checkout)")`. The banner then told them to fetch the vsix from "GitHub releases (tag `svrn-fim-*`)" — a prefix no release has ever used — with no URL at all. Nothing failed loudly; it just sent every non-developer user hunting. Found while publishing the extension so non-developers could install it, which is exactly the journey it broke.

THE FIX. A `VSIX_RELEASES_URL` const pointing at the real shelf, plus banner text naming the real prefix (`vscode-v*`) and the real asset (`sovereign-fim-*.vsix`). Guarded by test `vsix_releases_url_points_at_the_public_shelf`.

WHY THE UNFILTERED RELEASE LIST, WHICH LOOKS LAZY. I tried `?q=tag%3Avscode-v` first. GitHub returns HTTP 200 with the release absent from the body (measured 2026-07-29: 9 occurrences of `vscode-v0.1.0` on the plain `/releases` page, 0 on both `?q=tag:vscode-v` and `?q=vscode`). A filtered link would be a 200-OK empty page — strictly worse than a list the reader can scan, and status-code-checking a link is not enough to catch it. There is also NO per-prefix latest pointer: `/releases/latest` is repo-global and belongs to the desktop stream.

THE GENERAL RULE. Any user-facing pointer to a release artifact must name a tag prefix that a release actually carries, and must be fetched-and-grepped, not just status-checked.
