CORRECTION, same day, to my own note 550049b6: THE >4 GiB ALLOCATION SCALES WITH PROMPT SIZE, NOT CONTEXT SIZE. `fast_context_size` IS NOT THE LEVER — I recommended it before measuring, and the measurement refuted it.

THE DISCRIMINATING MEASUREMENT. Two compose-replay arms, IDENTICAL n_ctx=65536, different prompt sizes, each on a freshly restarted daemon (20s RssAnon sampling, research/deep-research/arms/mem-forensics/):

  arm   prompt_chars   anon step at first prefill
  44:6      65,904        +14.28 GiB   (7.08 -> 21.36)
  60:8      89,553        +18.83 GiB   (7.29 -> 26.12)

  step ratio   18.83/14.28 = 1.32
  prompt ratio 89553/65904 = 1.36

They track. KV is CONSTANT between these two arms (same n_ctx), so the allocation cannot be the KV cache. Capping fast_context_size would not have touched it.

CONFIRMED SEPARATELY: the 4B's own KV pins FINE in GPU. Its context is built at slot load (kv budget: slot="fast" n_ctx=65536 kv_ceiling_mib=8448) and anon does NOT step there — GTT absorbs it. So KV above 4 GiB is being suballocated successfully; only the prefill staging path falls back.

WHAT IS STILL TRUE FROM 550049b6: the device ceiling (RADV GFX1151, maxBufferSize = maxMemoryAllocationSize = 0xfffffffc ~ 4 GiB); the fallback path (ggml-vulkan.cpp:16191 -> CPU host buffer); that the fallback is NOT leaked but RETAINED at high-water (3 fallbacks, 1 step); and that GGML_VK_FORCE_MAX_BUFFER_SIZE is not a fix.

A THIRD, LOAD-TIME COMPONENT EXISTS AND IS SEPARATE. The 27B's load stepped anon +6.45 GiB with NO prompt in flight (14:29:44: anon 23.37->29.82, GTT 20.82->50.70 for the 24.7 GB of weights, kv_ceiling_mib=16640). So there are at least two distinct >4 GiB allocations: one at model load, one per-prefill scaled by prompt.

WHERE THE FIX ACTUALLY LIVES:
1. ENGINE (likely the real bug): ggml_backend_vk_host_buffer_type_get_max_size() returns suballocation_block_size — 1 GiB by default (ggml-vulkan.cpp:16212, :6385). Something requests a SINGLE host buffer >4x that and hits the driver cap. A caller ignoring get_max_size defeats the suballocation that exists to prevent exactly this.
2. PRODUCT (available now, no engine change): per-request prompt size is ours to bound — the deep-research round budget is a hardcoded ~96,000 chars (synthesize.rs:1448, ROUND_EVIDENCE_TOKENS * CHARS_PER_TOKEN) and the section evidence budget is section_evidence_budget(). Bounding the prompt bounds the staging buffer.

METHOD NOTE FOR THE NEXT READER: two points fit a line, and two points are not a law. The ratio agreement (1.32 vs 1.36) is strong evidence for prompt-scaling and is NOT a measured slope. A third arm at a different prompt size would settle the functional form; nothing here should be extrapolated to a formula.
