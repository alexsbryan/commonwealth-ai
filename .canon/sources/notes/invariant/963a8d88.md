# Five invariants that keep the §4.1 predicted-time objective admissible (sovereign-mesh/predicted_time.rs + scheduler_core.rs, landed…

Five invariants that keep the §4.1 predicted-time objective admissible (sovereign-mesh/predicted_time.rs + scheduler_core.rs, landed 2026-07-26).

1. NO TUNABLE CONSTANT IN predicted_time.rs. No floor, no weight, no tie-margin. This is the whole point of §4.1 versus the product: `rtt` sits INSIDE the predicted number, so a hop that buys less than it costs loses arithmetically and there is nothing left for a fudge factor to protect against. The moment a constant appears here, the objective has regressed to being a product with extra steps. (Contrast `cold_start_weight`'s 0.7 floor, which F7 showed had become the product's only brake by accident.)

2. RankObjective IS A PARAMETER ON RankInputs, NEVER A BRANCH AT THE CALL SITE. One scoring body, one record shape, one `finish_at`. If a caller branched instead, the decision record under the new objective would carry the product's verdict — i.e. describe a choice the decider did not make — and every record-derived scoreboard metric would silently be measuring the wrong thing. Production passes `Product`; the sim passes `arm.objective()`.

3. **`Unpredictable` IS NEVER DEFAULTED TO A RATE.** A candidate advertising no benchmark has NO prediction; it is dropped from ranking, not scored with a substituted rate. A guessed rate is a fabricated fact with a unit attached, and it would read as knowledge in the glassbox trace. Same discipline as the grounding work: absence is reported, not filled in.

4. LocalOption HAS THREE STATES AND THEY MUST NOT COLLAPSE. `Predicted(p)` → hop only if strictly faster. `Unpredictable(_)` → NO hop (no comparison exists, and missing information must read as a decline, not a discount). `Infeasible` → ANY feasible peer wins (the time-objective twin of `local_sentinel`'s negative infinity). Unpredictable and Infeasible point in OPPOSITE directions: conflating them either strands work on a node that cannot serve it or ships every request over the wire on a missing benchmark. Do not "simplify" this to an Option or an infinity.

5. **`faster_than_local` IS ORDER-SENSITIVE ON EXACT TIES** — same rule, same reason as `winners_over_local`: the sort is stable, so equal predictions rank in the caller's order, which is scoring order, which is the order candidate records were pushed. Reordering the `push_candidate` calls reorders these winners.

METHOD RULE the arm added, and the generalisable one: an arm must price the harness assumption that most flatters it. The mesh-sim builds each node's advertised BenchmarkResult from the same `Hardware` its service-time model consumes, so the rate card was EXACT TRUTH by construction and the predictor was being graded against its own inputs — zero model error, only queue error, efficiency 0.95-1.00. `SimConfig::advertised_rate_error` (two-sided, per node, THIRD RNG stream so `0.0` still reproduces every pre-existing number) discloses it: the win drops ~10 points to 0.85-0.90 and then goes flat, so it survives a ±2x mis-rated fleet. Generalisation: when an arm consumes a signal the harness generates, the arm cannot measure that signal's error, and the report must say so before anyone quotes the number. This is the same family as the F7 lesson (don't ship a causal claim the table cannot carry).

Side finding worth keeping: arm 0's efficiency RISES with rate-card error (0.29 → 0.91 at ±100%) because mis-rated peers fall under `throughput_factor`'s 20 tok/s reference, the F3 clamp finally discriminates, and fewer bad offloads happen. A broken rate card becomes an accidental brake — the third sighting of the over-eager-offload pathology, not arm 0 improving.
