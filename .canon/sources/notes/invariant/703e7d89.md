# A per-document tiered provider must NEVER stamp the corpus-level _enrichment_state.json terminal (Complete/Failed) — the shared per-corpus…

A per-document tiered provider must NEVER stamp the corpus-level _enrichment_state.json terminal (Complete/Failed) — the shared per-corpus file is owned by the RUNNER; per-note terminal stamps caused the "vault went silent at 65/314" flicker bug

`_enrichment_state.json` is one file per corpus (`<index_dir>/_enrichment_state.json`, keyed by corpus, read by GET `/internal/enrichment/status` and the desktop NotebookDetail poll). But `FolderTieredProvider::enrich_conversation` (and the conv variant) is called once per document/note by the runner. So any TERMINAL stamp (`EnrichmentPhase::Complete` or `EnrichmentStateFile::fail`) written from inside the per-note provider makes the shared file flicker to terminal after every note.

The bug this caused (2026-07-16): the desktop poll (`NotebookDetail.svelte` `pollEnrichOnce`, stops on `phase === "complete"`) caught one transient per-note `Complete` and stopped, marking a 314-note Obsidian vault "explorable" with only 65 notes enriched (the 65 smallest — the runner sorts ascending by chunk count, `tiered.rs:520`, and the run was interrupted at note #66). The user saw a frozen `{phase:"raptor_leaves", completed_at:<set>, last_progress_at:<completed+16s>}` — non-terminal phase yet `completed_at` set, because per-note `Complete` set it and a later per-note phase never cleared it.

INVARIANT: the RUNNER owns the single run-level terminal stamp. `run_folder_tiered_enrichment` and `run_tiered_enrichment` (both in `corpus-engine/src/enrichment/tiered.rs`) call `stamp_folder_terminal(index_path, corpus_id, completed, failed)` AFTER the whole per-doc loop + `finalize_corpus`: `Complete` normally, `Failed` only on total wipeout (`completed==0 && failed>0`); a partial run is `Complete` (successful notes are real retrieval surface; per-note failures live in `conv_skeletons.state`). The per-note provider stamps ONLY non-terminal progress (`Scanning`/`RaptorLeaves`/`Persisting`). The incremental `reenrich_changed_sources` and the driver's pre-loop-error arm (`watched/enrich.rs`) each stamp their own run-level terminal too.

Defensive backstop: `EnrichmentStateFile::stamp` now clears `completed_at` on any non-`Complete` phase (and `fail()` clears it), so a stale completion can never coexist with a non-terminal phase again (`state.rs`).

Gotcha for future work: the CorpusEngine wires `FolderTieredProvider` for BOTH runners (`build_folder_tiered_provider` in desktop `state.rs` + daemon `bootstrap.rs`) — so the conv-variant runner also uses it. If you add a THIRD runner or a new per-item provider that writes the shared corpus state, it must follow this same runner-owns-terminal rule. `ConvTieredProvider` is a separate impl that does NOT write `_enrichment_state.json` at all. Part of [[project_folder_tiered_enrichment_durable_fix_2026_07_16]].
