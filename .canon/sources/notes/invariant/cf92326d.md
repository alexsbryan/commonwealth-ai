THREE AGENT TOOLS REACHED THE OPEN INTERNET ON ORDINARY CHAT TURNS WITH NO RUNTIME SWITCH. Found 2026-08-03 while auditing egress for the on-prem legal pilot; the plan's claim that "three config keys" give a zero-egress box was FALSE.

THE GAP (sovereign-server/src/main.rs, tool registration block):
  SearchTool::with_web(..., SearchBackend::DuckDuckGo)
      POST html.duckduckgo.com -> www.google.com (when bot-blocked) -> lite.duckduckgo.com.
      Fires on ANY chat turn where the top LOCAL retrieval score is below SCORE_SUFFICIENT,
      i.e. exactly when the corpus is thin — which on a fresh deployment is often.
  WebFetchTool::new()
      Retrieves ANY url the model emits. Scheme-only validation, no host allowlist, 5 redirects.
  WikipediaFetchTool::new(corpus_engine)
      en.wikipedia.org. ALSO registered on the daemon's MCP registry (tool_registry.rs).

WHY IT WAS EASY TO MISS: these sit THREE LINES BELOW `#[cfg(feature = "dev-routes")] tools.register(Box::new(ShellTool))`. The adjacent gated line makes the ungated ones read as already-considered.

TWO THINGS THAT ARE NOT CONTROLS FOR THIS:
  1. `Permission::Network`. WebFetchTool declares it and sovereign-core/src/executor.rs WILL skip a
     tool whose stored permission is false — but that check exists at EXACTLY ONE call site, in the
     plan executor. The chat/agent path calls `tool.execute()` directly and never consults
     get_permission. Do not cite Permission::Network as a mitigation.
  2. `--no-default-features`. It removed ShellTool and the dev routes; it did NOT remove these.

THE FIX: `net-tools` cargo feature on sovereign-server, default ON so no other build in the fleet
changes. Under --no-default-features: web_fetch and wikipedia_fetch are NOT REGISTERED AT ALL, and
search is built with SearchTool::new (local corpora only) instead of with_web. Corpus search is the
product; reaching the open web was a separate capability sharing a tool id.

DELIBERATELY A SEPARATE FLAG FROM `dev-routes`. dev-routes gates surfaces whose risk is PRIVILEGE
(a shell, an arbitrary file read). net-tools gates product features whose risk is EGRESS. One flag
for two unrelated decisions would make neither name true (ARCH_PRINCIPLES §10.6, one decider one name).

VERIFIED THREE WAYS, because a compile-time flag you cannot observe at runtime is not a gate:
  - acceptance.sh check 0c enumerates GET /v1/tools on the running box and FAILS if either tool id
    is present OR if `search` went missing with them (asserting only absence would pass a build
    where retrieval had been crippled too).
  - package.sh greps the built binary for the tool-id literals and refuses to package.
  - Both on-prem systemd units carry IPAddressDeny=any + IPAddressAllow=localhost, so the kernel is
    the backstop rather than this analysis.

STILL OPEN: the DAEMON's MCP registry keeps wikipedia_fetch — there is no equivalent feature there.
Loopback-only reachable and sovereign-server does not drive the daemon's MCP surface, so
IPAddressDeny is its control. Named explicitly in EGRESS.md rather than omitted. If a daemon-side
`net-tools` is ever wanted, tool_registry.rs is the one site.

DO NOT re-register these on sovereign-server without the cfg gate. There is no tool allowlist/denylist
config anywhere in a production surface (searched disabled_tools, tool_allowlist, deny_tools,
SOVEREIGN_DISABLE_TOOLS) — the cargo feature is the only in-process switch these have.
