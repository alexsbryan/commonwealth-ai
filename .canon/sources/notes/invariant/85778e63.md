# MetalingualQuery must resolve 'this codebase' via IndexInfo::is_code_corpus (SCIP graph OR CorpusKind::Code tag) — NEVER the tag alone.

MetalingualQuery must resolve 'this codebase' via IndexInfo::is_code_corpus (SCIP graph OR CorpusKind::Code tag) — NEVER the tag alone.

Root cause found 2026-07-25: handle_metalingual_query filtered retrieval with kind_filter = Some(CorpusKind::Code). Repo corpora deliberately ship as knowledge-kind (chat retrieval admits only Knowledge|Catalog, so a Code tag would DELETE them from chat). So the filter matched ZERO corpora on every real install and every 'in this codebase' question returned the no_source empty state — while commonwealth-ai (41,691 chunks, scip_graph.db present, kind=knowledge) sat right there.

This was misdiagnosed for a month. CODE_INTEL_CHAT.md logged the symptom on 2026-06-25 as a ROUTER problem ('in this codebase mis-routes to Metalingual', follow-up ii). It was not. Even a correctly-routed metalingual code question could never have worked.

Why it hid: handlers/code_query.rs already used the robust signal, so the code route worked and masked the broken one; and the failure looked exactly like a misroute. The predicate existed in THREE places that disagreed — code_query (graph-only), sovereign_tools::code::has_code_graph (graph OR tag), metalingual (tag-only) — because sovereign-core carries sovereign-tools only as a DEV-dependency and cannot call the corrected version at runtime.

Fix: one predicate on corpus_engine::IndexInfo::is_code_corpus, beside IndexInfo where every consumer reaches it. All three sites delegate. If you add a fourth code-aware consumer, call is_code_corpus — do not re-derive it.
