VAST SSH: INJECT YOUR OWN KEY VIA --onstart-cmd. DO NOT RELY ON VAST'S ACCOUNT-KEY INJECTION — it silently fails. SOLVED 2026-08-04, cost $0.22 + ~$0.10 of cheap boxes.

THE FIX, in `cloud/pod.sh::cmd_up`:
  onstart="mkdir -p /root/.ssh; chmod 700 /root/.ssh; \
           echo '<pubkey>' >> /root/.ssh/authorized_keys; \
           chmod 600 /root/.ssh/authorized_keys"
  vastai create instance <id> --onstart-cmd "$onstart" --ssh --direct ...
The pubkey has no single quotes, so single-quoting the echo is safe. sshd runs INDEPENDENTLY of onstart, so this composes rather than conflicts.

PROOF IT IS THE FIX, NOT LUCK: instance 46848691 came up `ssh up after 50s` on machine 41522 — THE SAME TAIWAN HOST that rejected the key on three prior instances with no injection. Same host, same key, same account, injection added -> works. Also succeeded first try on machine 21744 (RTX A2000, Poland, t=140s) with the `/root/.verifier-onstart` marker confirming onstart executed.

WHAT WAS ACTUALLY WRONG: Vast registers the key on the ACCOUNT and claims to associate it with each instance (`vastai attach ssh` returns success, or "already associated"), but the key never reaches the container's authorized_keys. `ssh -v` shows the correct key Offered and rejected BEFORE the signature step, i.e. the server does not have it. Not fixable from the CLI; the console shows the same (correct) key.

NEGATIVE RESULTS — none of these was the cause, do NOT re-investigate:
  - The local keypair. `~/.ssh/id_ed25519{,.pub}` were written by ONE ssh-keygen run (mtimes 0.27ms apart, 2026-04-23) and never touched; ssh-agent holds the matching private half. Passphrase-protected, but irrelevant — rejection precedes the signature.
  - The API key (fine — search/create/destroy/invoices all worked throughout).
  - Console-vs-CLI key mismatch (identical).
  - Stale registration (deleted 1147518, created 1178540 before a fresh instance — still denied).
  - `--onstart-cmd 'sleep infinity'` suppressing Vast's startup (an instance with NO onstart failed identically).
  - Proxy vs direct port (both).
  - Host-specific permission forwarding — RULED OUT by the same-host before/after above.
  - Impatience. The clean no-injection test waited for status==running AND ports mapped (120s) plus 45s margin.

TWO OPERATIONAL RULES THIS ESTABLISHED:
1. **Wait on `actual_status == "running"` AND `len(ports) > 0`.** `status_msg` reports "success, running" while `actual_status` is still `loading`; they genuinely disagree. Before ports are mapped you get "Connection refused"; after, you get real auth results. Conflating refused-vs-denied cost a full debugging round.
2. DEBUG PLUMBING ON A 2-CENT BOX. 64 offers exist under $0.15/hr (GTX 1060 $0.022, RTX A2000 $0.052). Debugging SSH on a $0.93/hr A100 is most of the $0.22 spent. Vast runs a per-instance DERIVED IMAGE BUILD + apt provisioning after the pull, so first boot is 2-5 min regardless of GPU class.

`vastai execute <id> "<cmd>"` is NOT a shell escape hatch (restricted whitelist, 400).
