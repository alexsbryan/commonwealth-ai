`claim_affinity` does NOT need to be added to CandidateRecord, and the reason is structural rather than lucky. This was the open S1 gap (the scorer takes it, the record omits it) and it resolved to "no schema change".

  observation_mult = effective_affinity(a, obs) / a
                   = (clamp(a) · (1 − w·f)) / a      [samples > 0]
                   = (1 − w·f)                        for a ∈ (0, 1]

and a ∈ [0,1] BY CONSTRUCTION — ScoredClaim::claim_affinity is always CapabilityClaim::effective_affinity(), which clamps and maps NaN→0 (oicp-types/src/capability.rs:361). So the multiplier is independent of `a` across the whole legal domain except a==0 — and a==0 is exactly the claim_score==0 case, because both are that same clamped number upstream (score_claim_for_request returns hint × latency × effective_affinity).

decision_replay probes with 1.0 when claim_score > 0 and 0.0 otherwise, and reproduces the breakdown EXACTLY in both branches. If CapabilityClaim::effective_affinity ever stops clamping, this identity breaks and `claim_affinity` becomes a required record field — the lemma is covered by `observation_mult_is_independent_of_claim_affinity_over_its_whole_domain`.

Related invariant: `decision_replay::observations_from` is written as an EXHAUSTIVE struct literal with no `..Default::default()`. A new NodeObservations field is a new scorer input, and the correct response is a compile error there forcing the question "does the record carry this?"
