# Parse LLM output from the post-</think> tail, NEVER the preamble.

Parse LLM output from the post-</think> tail, NEVER the preamble.

When a thinking-capable model (Qwen3, DeepSeek R1, o1-family) fails to parse, the diagnostic signal is the substring AFTER </think> — that is the JSON the parser actually tried to deserialise. The <think> preamble is reasoning noise.

This session hit the same pattern 4 times in the same enrichment pipeline:
  - Phase 1 extraction failures (Qwen3-Coder-Next, Brothers Karamazov)
  - Phase 3 name-concerns "key must be a string"
  - Phase 5 extract-positions null-in-extensions and truncated-thinking conflation
  - Phase 1 atlas extraction with missing epistemic_status at line 44 — the failing JSON was hidden past the 1 KiB response_head cap

Correct design for any inference-output parser that captures responses for post-mortem:

1. Strip <think>...</think> BEFORE capturing for diagnostics (use strip_reasoning_tags).
2. Persist the STRIPPED content in failure records — that is what the parser saw.
3. Fall back to the preamble only when stripping leaves nothing (truncated mid-trace), and flag the mode explicitly ("<think block truncated — answer never emitted>").
4. Keep the cap modest (~2 KiB is enough for a typical atlas JSON response). The real lever is WHICH bytes you keep, not HOW MANY.

Bumping the head cap without addressing what you keep is treating the symptom; the useful bytes still live past whatever cap you set because the <think> block dominates the head.

Reference implementation: corpus-engine/src/enrichment/pipeline/runner.rs :: truncate_response_head (post-fix). Helpers live in corpus-engine/src/enrichment/pipeline/types.rs: strip_reasoning_tags, is_truncated_thinking_response, extract_json_block.

Applies to: any new Phase parser, any new Pipeline impl, prepare_phase_json in pipelines/literary.rs, and any future adapter that surfaces model output for debugging.
