# Destructive operations on target/ go through scripts/with-cargo-lock.sh, exactly like builds and tests — and the wrapper is now REENTRANT…

Destructive operations on target/ go through scripts/with-cargo-lock.sh, exactly like builds and tests — and the wrapper is now REENTRANT so wrapping a script that wraps its own cargo step no longer deadlocks (5a356e11a, 2026-09-11).

TWO traps, both cost real time on 2026-09-11:

1. DEADLOCK. AGENTS.md tells every cargo-adjacent invocation to go through with-cargo-lock.sh, which makes nesting inevitable: scripts/stage-daemon-sidecar.sh:89 wraps its own cargo build, so `with-cargo-lock.sh scripts/build-desktop-macos.sh` waited forever on a lock its own parent held. It did NOT look like a bug — it printed "with-cargo-lock: waiting for pid N" every 5s, the normal queue message, where N was the waiter's own ancestor. Fixed: the holder exports SVRN_CARGO_LOCK_HELD=$$ and a nested call execs through, announcing "nested under pid N — passing through" on stderr. The env var reaches descendants only, so it cannot make one session skip another session's lock.

2. A DELETE OUTSIDE THE LOCK IS INDISTINGUISHABLE FROM A CORRUPT CHECKOUT. Removing target/llama-cmake-cache/<hash> (or any target subtree) while another agent's cargo is compiling llama kills it with `ninja: error: mkdir(src): No such file or directory` — which reads like a broken vendor tree, not a race. Three desktop builds died on 2026-09-11 with that plus `No space left on device`; the actual cause was the OPERATOR clearing target/ by hand at ~13:06 because the volume was full (target/ was 58G). Diagnosing it took cross-session messages to two peers. On a shared checkout, put the wipe and the build in ONE locked command.

Corollary for long builds: message the other live sessions (ListAgents -> SendMessage) before holding the lock for 30+ minutes. commonwealth-ai-c2 and commonwealth-ai-80 were both live on this host that day.
