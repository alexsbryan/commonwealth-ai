`[daemon] client_bind` IS NOT WHAT THE DAEMON BOUND — AN ENCRYPTED MESH OVERRIDES IT, SILENTLY AS FAR AS THE CONFIG IS CONCERNED (measured 2026-08-27 on this host).

`start_daemon` (`sovereign-mesh/src/daemon.rs:2688`) forces the client listener back to `127.0.0.1` when `Mesh::require_encryption` is true, whatever `client_bind` says, and then `install_client_token(None)` because the bind is loopback. `internal_bind_addr` (same file, ~line 35) does the same for `:9742`. Remote access on such a node is the key-authenticated iroh acceptor forwarding to loopback — see the log line "iroh(mesh): dial-by-key access enabled ... client_forward=127.0.0.1:9741".

MEASURED, not inferred: this host has `client_bind = "0.0.0.0"` set and mesh `Meshsonics` (`~/.svrnmesh/meshes/27ba8166.../mesh.json`, `require_encryption: true`, 6 members). The daemon logged `Commonwealth daemon started (client: 127.0.0.1:9741, internal: 127.0.0.1:9742)` and a curl to `<lan-ip>:9741` returned 000.

CONSEQUENCE FOR ANY FEATURE THAT PUBLISHES AN ADDRESS: never derive reachability from config. `svrn mesh grant` did exactly that in its first form (commit 035c64cc) and would have minted a `sovereign://guest/…` link naming an address nothing listens on — the failure its check existed to prevent. Fixed by probing `<base>/status` (an `AUTH_EXEMPT_PATHS` entry, so no credential) before minting: one probe covers encrypted-mesh forcing, a stale daemon, a firewall and a wrong interface, where a config read covers none of them.

SECOND CONSEQUENCE: a guest link cannot work at all on an encrypted mesh as things stand. The client API is loopback-only and the sole ingress wants a mesh key a guest by definition does not hold. Lending a model off an encrypted mesh needs either a guest-facing iroh ALPN or an operator-run proxy; neither exists. The mint now refuses instead of pretending.
