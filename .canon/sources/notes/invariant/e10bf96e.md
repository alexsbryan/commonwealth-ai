`conv_motifs` IS A WRITE-ONLY TABLE. NOTHING IN THE WORKSPACE READS IT, AND BUILDING IT COSTS 42.8% OF TIME-TO-ENRICHED ON THE FOLDER/VAULT PATH. Verified 2026-08-02 by exhaustive census, not by sampling.

THE CENSUS. `ConvMotifRow` has exactly four uses in the whole workspace: the struct definition (`sovereign-core/src/conv_tiered.rs:97`), the two construction sites in `conv_tiered_provider.rs:1305`, and the `save_conv_motifs` parameter. The table itself has one INSERT and two DELETEs (`sovereign-store/src/sqlite/conv_tiered.rs:330`, `:339`, `:888`) and NO SELECT in any file type — not Rust, not TypeScript, not raw SQL. There is no `list_conv_motifs`, no `get_conv_motifs`, and no motif method on the `ConvTieredReader` trait (which does carry readers for skeletons, RAPTOR nodes, chunk entities, and vault themes).

THE COST. 22.3m of a 52m03s cold build of a 330-note vault — measured in the first clean cold baseline, `~/.sovereign/bench-runs/vault-report/1785678945/`. Inside `raptor_per_note`, motifs 22.3m vs tree 9.3m = 2.41x. The candidate pool is saturated: median 200, max 200, none under the cap, so the cost is the LLM classification of 200 candidates per note.

WHY THE CODE LOOKS LIKE IT HAS A READER AND DOESN'T. `conv_tiered_provider.rs:232` comments that "the briefing layer surfaces motifs alongside RAPTOR signposts". That traces to `CONV_TIERED_PORT.md:385` — "Briefing layer WILL pick top distinctive motifs per conv to surface in Deep mode" — which is future tense and was never built for the conv/vault side. The attached-document briefing DOES render motifs (`runtime/handlers/attached_doc.rs:1172-1180`) but reads `AssetMotif` from the `asset_motifs` table: different table, different surface, unaffected.

CONSEQUENCE. Deleting the `save_conv_motifs` write on the folder path is a ~1.75x speedup on time-to-enriched with no reachable behaviour change. This does NOT extend to `asset_motifs`, which has a live reader.
