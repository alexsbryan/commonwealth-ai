THE CRASH-LOOP CEILING RESETS ON PROOF (A GENERATION THAT SERVED), NEVER ON ELAPSED WALL-CLOCK. A sliding-window ceiling is structurally unreachable for any child whose spawn→crash cycle is longer than the window is wide.

FOUND 2026-08-03 by post-mortem of the DeepSeek-V4-Flash distributed run that froze RuggedFox for ~10 minutes and forced a restart.

THE INCIDENT. The 148 GB distributed primary loaded and reached `serving` twice (5m18s and 4m36s). Both generations died on the FIRST request — a 10-token prefill — with `ggml-rpc.cpp:498: Remote RPC server crashed or returned malformed response`, i.e. the BeefyMac worker aborted, 18.3s and 12.6s after prefill began. Zero tokens were ever produced. Between 11:33 and 11:40 the supervisor re-mapped 148 GB of unified memory twice more; by 11:40:11 amdgpu was returning -ENOMEM on every VA update (`Not enough memory for command submission!`, then a flood of `Couldn't update BO_VA (-12)`), Xwayland and gnome-shell lost their VMs, and the kernel OOM killer hit user.slice. A WORKER-SIDE CRASH ESCALATED INTO A HOST-WIDE FREEZE.

WHY THE EXISTING CEILING DID NOT FIRE. `SupervisorConfig` had `crash_loop_window: 600s` / `crash_loop_max: 5`, and `handle_crash` kept a `VecDeque<Instant>` retained to the window. Each cycle of this child cost ~290s (load 4m36s + serve 13s), so at most TWO crashes could ever coexist in a 600s window against a ceiling of five. The breaker could not trip — not "did not trip", COULD NOT. The arithmetic makes it unreachable for every slow-loading child, which is precisely the class where a runaway restart is most expensive.

THE FIX (sovereign/crates/sovereign-compute/src/supervisor.rs).
  * `crash_loop_window: Duration` → `healthy_reset_after: Duration`. `crash_times: VecDeque<Instant>` → a plain `consecutive_crashes: u32`. The counter clears ONLY when a generation stayed healthy at least `healthy_reset_after` (60s in manager.rs and both desktop configs). One decider, one name.
  * New `GenerationCost { load: Option<Duration>, healthy_for: Duration }`, returned by `supervise_until_exit` alongside `ExitOutcome`. `load` = spawn → first successful probe; `healthy_for` = first probe → exit.
  * Backoff is floored at the previous generation's `load`: `delay = scheduled.max(cost.load)`. The 1s/2s/10s/60s schedule assumes restarts are cheap; for a 4.5-minute load it meant the host was inside a load nearly 100% of the time. The floor bounds that duty cycle to ~50% and gives the spawn gate / discovery loop / operator room to change the answer.

THE THREE TESTS, EACH WATCHED TO FAIL BEFORE BEING BELIEVED (mutation-checked 2026-08-03):
  * `brief_healthy_stretches_do_not_reset_the_breaker` — child serves 200ms then exits, `healthy_reset_after=1s`; must reach Failed. Mutating the reset to unconditional makes it fail with the exact pathology in the assert output: endless Starting→Healthy→Restarting, no Failed.
  * `a_proven_healthy_generation_resets_the_breaker` — child serves ~400ms, `healthy_reset_after=150ms`, `crash_loop_max=1`; must NEVER reach Failed. Fails if the reset is removed.
  * `backoff_is_floored_by_the_last_generation_s_load_cost` — `spawn_slow_health_server(400ms)` gives a measurable load; the gap from Restarting to the next Starting must be ≥300ms, not the 20ms schedule. Fails if the floor is dropped (observed: 21.9ms).

WHAT THIS DOES NOT FIX. The Mac-side worker crash itself is untouched and still unexplained — see the separate todo. This change bounds the blast radius; it does not make the distributed run work.

Gates: lint --full 0 errors, 8988/8988 tests, both exit 0.
