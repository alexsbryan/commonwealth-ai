MEASURED 2026-08-19 — llguidance forces JSON object keys to be emitted in the order it ITERATES `properties`, and that order depends on a Cargo FEATURE, not on the schema text. Read this with 0479b961 (which schemas compile); this one is which key order they then demand.

THE MECHANISM, probed rather than reasoned:
- The emitted order follows `properties` iteration order. It is NOT the `required` array order — three permutations of `required` over one identical `properties` map produced the same first key every time.
- `serde_json::Map` iterates in INSERTION order only when `serde_json/preserve_order` is on. Off, it is a BTreeMap and iterates ALPHABETICALLY.
- `cargo tree -e features` on this repo: sovereign-desktop, sovereign-server, sovereign-cli-daemon all resolve `preserve_order` transitively; `sovereign-core` built ALONE does not. So the same `plan_schema()` call serialises `{"type","additionalProperties","required","properties"}` insertion-ordered in every binary that runs the planner, and alphabetically in a bare `cargo run -p sovereign-core --example`. Verified both ways by dumping the schema from each graph.

WHY IT MATTERS: a schema whose key order disagrees with the worked example in its own prompt does not error and does not refuse. The model is simply masked at every step and forced to reorder — plans still come out, just fought for token by token. Nothing in a test run, a lint, or a 200 response says so. This is the failure class F1 does NOT catch, because the schema compiles fine.

I GOT THIS WRONG ONCE BEFORE TESTING: my first comment said "properties DECLARATION order", implying schema text was the decider. It is map iteration, and the map's type is a feature-resolution outcome. Do not re-derive from the comment; re-probe.

CONCRETE: `planner.rs` `step_branch` inserts id, description, kind, <kind-specific>, inputs — matching PLAN_SYSTEM_PROMPT's example. Correct today ONLY because preserve_order is on everywhere the planner runs.

Pinned by `plan_schema_key_order_matches_the_prompt_example` (alignment) and `plan_schema_key_order_depends_on_preserve_order` (the feature it rests on, with a failure message naming the consequence) in `sovereign-inference/tests/llguidance_parity.rs`. A dependency bump that drops the feature reddens the second one.
