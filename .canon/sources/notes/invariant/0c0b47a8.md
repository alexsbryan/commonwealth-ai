THE DAEMON WAS LOADING EVERY LOCAL MODEL INTO ANONYMOUS MEMORY, BECAUSE IT REGISTERS RPC DEVICES (root-caused + fixed 2026-08-26, RuggedFox). This is not a Flash-Next bug; it applies to every local load on any host with mesh/RPC inference wired.

MECHANISM, cited: llama-model.cpp:1388

    if (ml.use_mmap && params.load_mode == LLAMA_LOAD_MODE_AUTO) {
        for (const auto & dev : devices) {
            if (!props.caps.mmap_support) { ml.use_mmap = false; break; }
        }
    }

ONE device without mmap_support disables mmap for the WHOLE model. The daemon installs the rpc-warm orchestrator and routes rpc_tensor, so RPC devices are registered — and a remote device cannot mmap. A purely LOCAL load therefore silently lost its mapping and every weight was COPIED into anonymous memory. Anonymous pages are unreclaimable; file-backed ones are not. That is the difference between "the kernel evicts under pressure" and "the kernel OOM-kills".

MEASURED, same model, same binary, same host:
  standalone (no RPC devices):  loads, 79.3 GiB GTT, 12.2 tok/s
  daemon, before fix:  RssAnon 8.85 -> 21.47 GiB, RssFile 0.29 -> 0.06, OOM (status=137) x3
  daemon, after fix:   RssFile 0.92 -> 55.44 GiB, RssAnon FLAT ~9, MemAvailable barely moves
                       -> PRIMARY SLOT READY, HTTP 200 in 2.4s, GTT 94.97, avail 11.5 GiB

FIX: LocalOnly loads request `.with_load_mode(LlamaLoadMode::Mmap)` explicitly instead of leaving AUTO. The device-caps loop only runs under AUTO, so an explicit request skips it. The distributed arms keep AUTO, where the check is CORRECT — those loads really do span a device that cannot map. model_slot.rs, LoadPlacement::LocalOnly arm.

WHY THIS MATTERS BEYOND THE OOM: the local-fit gate's whole premise is that mmap-resident weights are evictable and should not be charged as demand (see the `cpu_only` arm in gate_local). With mmap silently off, that premise was false for every daemon load, and the gate was reasoning about a world it was not in.

DIAGNOSTIC THAT FOUND IT: split RSS into RssAnon vs RssFile from /proc/<pid>/status during the load. Total RSS looks identical either way; the split is what says whether memory is reclaimable. Neither GTT nor total RSS nor majflt distinguishes the two cases — I chased MAP_POPULATE and `no_host` for hours on total-RSS evidence before splitting it.
