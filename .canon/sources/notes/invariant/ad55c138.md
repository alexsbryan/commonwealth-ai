# A SANDBOXED svrn daemon start|stop|restart MUST NEVER DRIVE THE HOST'S SERVICE MANAGER (fixed 2026-07-30,…

A SANDBOXED `svrn daemon start|stop|restart` MUST NEVER DRIVE THE HOST'S SERVICE MANAGER (fixed 2026-07-30, sovereign-cli-daemon/src/service_install.rs `service_manager_is_addressed`, gating `managing_service()`).

THE INCIDENT, with timestamps. The CLI journey sandbox lane boots its own daemon under a throwaway HOME on :19741 precisely so it cannot touch the operator's. During a lane run at 16:45, `daemon-triage[2] daemon restart` restarted the OPERATOR's `sovereign.service` (journal: started 16:45:38) and `first-run[6] daemon stop` then stopped it (journal: "Stopping sovereign.service" 16:45:43). Both steps reported exit 0 — systemctl succeeded — and the sandbox's own daemon on :19741 was never touched. Note 1e6b57cc's closing observation that "the daemon died three more times under the heavy lanes" was THIS, misread as flakiness and hand-restarted three times.

HOW IT SURFACED — and it is the argument for the whole unfalsifiable-step burn-down. `first-run[6] daemon stop` had NO `expect` block, and `first-run` ended there. The moment it gained one (`exit = 0`) plus a closing step [7] `daemon status` asserting `exit = 1` + "not reachable", the lane went red on the first run with the message `[7] daemon status — exit 0, want 1`, output `✓ daemon running at http://127.0.0.1:19741`. A stop that stopped the wrong daemon is invisible to any gate that does not ask what happened afterwards.

THE GUARD THAT EXISTED WAS BYPASSED BY PLACEMENT. `SOVEREIGN_STOP_SANDBOXED=1` was added 2026-06-10 after the phase3 serve test killed a developer's daemon twice, and it confines the stop chain to its pidfile legs. But it is checked partway down `stop_daemon`, and the service-manager leg added 2026-07-29 was placed ABOVE it under an "OWNERSHIP FIRST" comment — right about ownership, silent about whose. Per-call-site guards are the wrong shape here: the failure mode is a NEW call site that does not know to ask. There were three (`stop_daemon`, `start_daemon`, `restart_daemon`).

THE FIX. `managing_service()` — the single point every delegation path already passes through — returns None when this invocation is not addressing the installed unit. Two signals, either sufficient: (1) `SOVEREIGN_STOP_SANDBOXED=1`, the explicit assertion, which operators must never set; (2) a resolved `[daemon] client_port` other than the default, which is the AUTOMATIC half and the half that catches this — the journey lane sets no env var, it just runs on :19741. The asymmetry justifies the bias: wrongly delegating kills a production daemon from a sandbox, wrongly declining sends SIGTERM to a pid we own and lets the manager's restart policy notice, which is what every version before 2026-07-29 did.

VERIFIED BOTH DIRECTIONS, not reasoned about. Sandbox `first-run` went ✗ 7/8 → ✓ 7/8: `daemon stop` now SIGTERMs the sandbox daemon via the port-lookup leg (:19741) and step [7] correctly finds it unreachable. On the host, `svrn daemon start` still prints "sovereign.service is registered — starting via the service manager" and brings the unit up, so the normal path is unchanged.

DO NOT set `SOVEREIGN_STOP_SANDBOXED=1` in the journey lane. It would confine the chain to pidfile legs only, and the sandbox daemon is started by `daemon run` rather than `daemon start` — the port-lookup leg is what actually finds it.
