# corpus chunk ids must be allocated from a monotonic high-water mark (IndexMeta.next_chunk_id), never chunk_count() — the row-count scheme…

corpus chunk ids must be allocated from a monotonic high-water mark (IndexMeta.next_chunk_id), never chunk_count() — the row-count scheme reused ids and broke citation read-back

`CorpusIndex::insert_batch` (corpus-engine/src/index/write.rs) allocates chunk
`id`s. It used to derive them from `self.chunk_count()` (the ROW COUNT). That
is wrong: after any delete / dedupe / delta append, the row count falls below
`max(id)`, so the next insert REUSES ids that already exist. `id` is the key
`neighbors(id)` (the citation read-back, `read_chunk`) filters on — once it's
non-unique, a citation resolves to the wrong chunk.

Symptom (2026-06): mobile citation "2026 Lebanon war" opened text "Gold can
be used in food and has the E number 175". The wikipedia index had 31,432
duplicate rows (1.7%) in the delta block 1850303..1899111 — every fresh
newsworthy article. id 1896541 carried 5 different chunks; `neighbors` returned
whichever Lance hit first (Gold). Retrieval itself was CORRECT (vector search
matched the right text + synthesized a good answer); only the id-only read-back
was ambiguous. Only `wikipedia` was corrupted — it alone had heavy delta ingest.

Fix (L1, root): new `IndexMeta.next_chunk_id` high-water (persisted in
`_corpus_meta.json`, `#[serde(default)]`, seeded lazily from `max(id)+1` for
legacy indexes). `allocate_chunk_ids(n)` reads it, bumps by n, never decreases →
ids globally unique + monotonic across deletes/deltas. Test:
`insert_ids_never_reused_after_delete`.

Fix (L3, data repair): `sovereign/bench/repair_wikipedia_chunk_ids.py` —
re-id duplicate-id groups IN PLACE (keep group-leader, reassign extras above
max). Mechanism (validated on fixtures): read full group rows (id IN dup_ids) →
`ds.delete` → `lance.write_dataset(mode="append")` with corrected id column →
`ds.optimize.optimize_indices()`. Lance searches unindexed/appended rows
transparently (FTS + vector), so coverage is never lost; optimize just folds
them in. Reversible via `lance.dataset(path).restore(<version>)`. E2E: the
Lebanon query went 26/26 mismatched → 0/26.

Gotchas learned: `_rowid` is virtual — not writable, not usable in a filter or
merge key. A merge-key column can't be the column you mutate (so
`merge_insert(["id",..])` can't change `id`). `content_hash` is ~99.96% unique
(705 collisions / 1.9M, zero nulls) and distinct WITHIN every dup-id group, but
delete+reinsert keyed on `id IN (dup_ids)` sidesteps the key problem entirely.
Old Lance versions retain the pre-repair data until `cleanup_old_versions()` —
don't compact until the repair is confirmed. See [[project_distributed_rpc_embedded_host_2026_06_04]].
