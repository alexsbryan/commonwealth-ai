HF chat templates routinely call Python-shape methods on dicts/strs/lists; stock minijinja lacks these — register an unknown_method_callback

Hugging Face-grown Jinja2 chat templates (Gemma 4, Llama 3.x with
tools, Phi-4 multi-turn) call Python-stdlib methods on values:
`dict.get(key)`, `dict.get(key, default)`, `str.split(sep)`,
`str.startswith(prefix)`, `str.endswith(suffix)`, `str.upper()`,
`str.lower()`, `str.strip()`, `list.append(...)` (less common).

`minijinja 2.x` doesn't ship these out of the box — stock dict/str
value kinds have NO methods. The `minijinja-contrib` crate's
`pycompat` feature does, but pulling it in for half a dozen methods
is excessive.

Why: the `apply_chat_template_minijinja` path is the fallback when
llama.cpp's built-in template parser fails (which it does for any
template using `{%- macro -%}`, `{%- set -%}`, complex `{%- if -%}`
patterns — all common in modern HF templates). When the minijinja
path *also* fails because `.get()` is missing, the only remaining
path is plain-text concat (`{system}\n\n{user}`) which has no role
markers and silently degrades the model to multi-turn role-play
until max_tokens.

Observed 2026-05-19 with Gemma 4 E4B-it: minijinja errored at
template line 236 with `unknown method: map has no method named get`.

How to apply: in `apply_chat_template_minijinja` (or any other
minijinja env spinning up a chat template render), call
`env.set_unknown_method_callback(...)` and dispatch by `(value.kind(),
method)`. Implementation in
`sovereign-inference/src/embedded.rs::apply_chat_template_minijinja`
covers the methods listed above; add new ones as they're discovered.
Return `Err(Error::from(ErrorKind::UnknownMethod))` for anything not
recognised so the renderer can fail cleanly rather than silently.

Related: [[chat-template-lookup-must-retry]] is the sibling correctness
bug — without it the template never reaches the renderer in the first
place. Both bugs co-occurred on the 2026-05-19 Gemma 4 gym pass.
