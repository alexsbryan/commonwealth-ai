Governance rule-baseline seeding (migrate-ids + AssertRule seed) is NOT automatic on the in-process enrich path — the desktop must call governance_post_build_seed after enrichment completes

Enriching a governance corpus (`recipe [enrichment] domain = "governance"`) does NOT auto-seed its rule baseline. The in-process enrich path (`lcEnrichNow` → enrich-once → tiered/structural atlas) writes atoms.json but does NOT write the governance oplog. The living-governance rule set is defined by `<atlas>/governance_oplog.jsonl` (`AssertRule` ops), which is seeded ONLY by explicit calls — there is no server-side hook (the FolderDropFlow "seeded server-side on build completion" comment was aspirational; the CLI `enrich build` never seeded either — it relied on the desktop wrapper or manual `svrn govern seed`).

The desktop seeds it client-side after enrichment completes via the self-gating `governance_post_build_seed` tauri command (governance_commands.rs — runs `migrate_atlas_ids` THEN `seed_at`, no-op for non-governance). Wired at: `ConflictsPanel.onUpdateComplete` (always) and `FolderDropFlow.handleAtlasComplete` (governance template). Migrate-then-seed order is load-bearing (content-hash ids must be stable before rules reference them).

If you add a NEW desktop surface that enriches/re-enriches a governance corpus (e.g. WatchedFolderDetail rebuild, NotebookDetail make-explorable on a governance notebook, recipe-author governance recipe), you MUST call `governancePostBuildSeed(corpusId)` in its enrichment-completion handler or that corpus's baseline silently stays empty (`governance_view` derives zero governed rules).

TRUE central fix (follow-up): lift `seed_at` from the desktop crate into a shared crate (next to `corpus-engine/.../atlas/migrate_ids.rs`) and hook it into the daemon's tiered-build completion gated on governance domain — covers every path incl. the standalone daemon.
