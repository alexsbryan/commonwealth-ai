NEVER RUN THE CARGO GATES WHILE A FLIGHT IS IN PROGRESS ON THIS HOST — the parallel cargo fan OOM-kills the daemon (re-confirmed 2026-08-24, three times in one evening).

EVIDENCE: `journalctl --user -u sovereign.service` shows three `Main process exited, code=exited, status=137/n/a` (137 = SIGKILL) at 20:52:24, 21:46:06 and 22:55:04. Each coincides with a cargo gate I was running:
  20:52 — full sovereign-test.sh  => killed all 3 pinned scoring calls (`Connection refused`, unit exited looking like a clean finish)
  21:46 — full lint + test        => killed web-composite task 56 attempt 1 (`error sending request`)
  22:55 — cargo check --all-targets + rustfmt => killed outline-ab control-1
systemd's own "86.2M memory peak" is the supervisor only and is NOT the model's RSS — do not read it as evidence the daemon was small.

THIS IS ALREADY DOCUMENTED AND I RE-TRIGGERED IT. `.sovereign/sovereign.toml` `[watchers] enabled = false` carries the comment "disabled 2026-05-31: the parallel cargo fan OOM'd the daemon under a resident big model". The watchers were turned off for exactly this. Running the gates BY HAND during a flight is the same fan.

RULES:
 - Sequence, never overlap: gates OR flights, not both. Long flights run on the durable tier; do the gates before launching or after landing.
 - `memory-watch: hard limit disabled (default; unsupervised daemon)` — there is no RSS guard catching this. `SOVEREIGN_RSS_HARD_LIMIT_MB` exists but is off.
 - Every long-running script MUST gate on daemon readiness and RETRY transport failures rather than recording them as results — a bounce that eats a measurement silently is the §18.3 failure. The composite's retry is what saved task 56.
 - A daemon restart also evicts the loaded judge; re-warm before timing anything.
