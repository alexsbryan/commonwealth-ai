# FORCE_COLOR SILENTLY DISABLES TWO SAFETY GATES — root-caused 2026-08-25, fixed at both seams. This is a PRODUCTION defect class, not a test…

FORCE_COLOR SILENTLY DISABLES TWO SAFETY GATES — root-caused 2026-08-25, fixed at both seams. This is a PRODUCTION defect class, not a test artifact, and it is worth grepping for elsewhere.

=== THE MECHANISM ===
`FORCE_COLOR` (set by several agent harnesses and CI runners — including Claude Code's own shell, which is how this was found: `FORCE_COLOR=3`) makes CPython 3.13 and pytest emit ANSI escapes EVEN INTO A PIPE. Two first-party subsystems PARSE that output as plain text.

**1. `PythonSyntaxValidator` (commonwealth-agent-tools/src/syntax.rs) FAILS OPEN.**
`parse_cpython_syntax_error` matches `kind.ends_with("Error")`. Colourised, the line is `"\x1b[1;35mSyntaxError\x1b[0m"` — ends with the reset escape, not `Error`. So the probe runs correctly, DETECTS every syntax error, discards it, logs "non-zero exit but no SyntaxError parsed; fail-open", and returns no errors. Net effect: the pre-write gate that exists to stop a model writing broken Python is INERT on exactly the machines most likely to be running an agent.

**2. `run_tests` (commonwealth-tdd/src/shared/test_runner.rs) REPORTS `0p/0f`.**
Colourised, pytest's `1 error in 0.06s` arrives as `\x1b[31m\x1b[1m1 error\x1b[0m...` and matches nothing. `0p/0f` reads as "no tests" rather than "could not read the result", so the TDD solver stalls against a repo that is working fine. §18.3 exactly — an absence dressed as a result.

=== THE FIX, AND WHY IT IS AT THE SEAM ===
Both now DEMAND machine-readable output instead of hoping the ambient environment is plain: `NO_COLOR=1`, `PYTHON_COLORS=0`, `CARGO_TERM_COLOR=never`, and `FORCE_COLOR`/`CLICOLOR_FORCE` removed from the CHILD env. No parser changes — stripping ANSI in each parser would be one more thing to forget. `run_tests` is the ONE seam every verify command goes through whatever the language, so normalising there covers pytest, cargo test and anything else a verify_cmd runs.

=== WHY IT WENT UNNOTICED ===
Neither failure is loud. One fails open, one reports a number. The syntax validator's own doc comment even says a silent fail-open is a glassbox violation and it WAS warning — nobody was reading the warn. If you own a subsystem that parses subprocess output, check it against a coloured environment before trusting it.

=== A DIAGNOSIS I GOT WRONG ON THE WAY (recorded because the shape recurs) ===
First read of the tdd failure was "pytest is not on PATH" — it is importable via `python3 -m pytest` (9.0.3) but not on PATH, and that looked sufficient. It was WRONG: the guard uses `python3 -m pytest`, so it passed. Two plausible environmental explanations for one symptom, and the first one that fit was not the true one. Reproducing the exact subprocess by hand — printing `repr()` of its stderr — is what settled it, and would have settled it 20 minutes earlier.
