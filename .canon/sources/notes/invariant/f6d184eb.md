# EPISTEMIC LEDGER: a holding's verification: "failed_once" means NOT SUPPORTED — it is the ledger's rendering of !GateClaim.supported, not…

EPISTEMIC LEDGER: a holding's `verification: "failed_once"` means NOT SUPPORTED — it is the ledger's rendering of `!GateClaim.supported`, not of `GateClaim.failed_once`.

epistemic.rs:102-108 builds every holding as:
  let verification = if fail_open { FailOpen }
                     else if c.supported { Verified }
                     else { FailedOnce };

`GateClaim.failed_once` (grounding/mod.rs:589 — "the first check failed and the claim went through retry/rewrite/annotation before release") is NEVER consulted here and never reaches a transcript. The obvious reading of the serialized string is therefore backwards.

Why it matters: anything replaying frozen chaos transcripts for per-claim incumbent verdicts (epistemic_state.holdings[].verification) that reads failed_once as "supported" erases the ENTIRE negative class. Measured across the three committed transcripts on skunkworks/native-grounding: 87 holdings = 75 verified + 12 failed_once, and there is no other negative value — so the mis-read collapses the label set to one value and any agreement metric computed on it is meaningless (trivially 1.0 for a mechanism that always says "supported").

Two further survivor biases in the same record, both structural:
 * abstained turns contribute ZERO holdings ("An abstained turn asserts nothing: its failed claims stay in the gate meta (glassbox), not in holdings", epistemic.rs:97-100), so abstentions are invisible to a per-claim replay;
 * `Verification` is a closed 4-set (contracts/types/epistemic.rs:210): Verified | FailedOnce | FailOpen | Unverified. FailOpen and Unverified are could-not-judge (verifier errored / never ran), NOT failures — collapsing them into either class is the §18.3 smell.

Caught 2026-08-08 during H4 deliverable 3; the first draft of sovereign-cli-llm/src/bench_cmd/h4/transcript.rs had it inverted and cited grounding/mod.rs:589 to justify it.
