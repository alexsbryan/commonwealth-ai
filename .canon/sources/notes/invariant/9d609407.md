THE SESSION ID `declare_scope` RETURNS IS NOT THE SESSION ID FRAMES USE — BANKING A FRAME UNDER IT CREATES AN ORPHAN THE BOOT HOOK CAN NEVER FIND (hit live 2026-07-29, and repaired by hand).

WHAT HAPPENED. `declare_scope` returned `session_id: c63329fe-7c4b-4249-a2ea-4329e34a2163`. I used that for `session_state`, so the frame landed at `~/.sovereign/sessions/c63329fe.../frame.md`. The harness session id for the same session was `d75f39c0-f97d-4785-97ac-81dbbeaddc06` — visible in the scratchpad path (`/tmp/claude-*/<repo>/<id>/scratchpad`) and in the boot banner.

HOW IT SURFACED. `sovereign session frames --claim-window` reported: "Predecessor in this window: `d75f39c0` — but it banked NO frame; falling back to the index." The window lineage is keyed on the HARNESS id, so it looked for a frame under `d75f39c0`, found none, and fell back to ranking 66 candidates — the exact 5,872-token guessing failure `session_lineage` was built to eliminate.

WHY IT IS INVISIBLE. Every surface reports success. `session_state` returns `created: true` with a real path. `sovereign session frames` lists the orphan among the live frames, because the index globs the sessions directory and does not care which namespace an id came from. Nothing correlates the two. The cost lands on the NEXT session, as a silent fallback to guessing.

THE RULE. Take the session id from the scratchpad path or the boot banner. Never from `declare_scope` (that is the daemon's own session identity, a different namespace) and never from a note or claim response.

REPAIR IF YOU ALREADY DID IT: move `frame.md` into the harness-id directory, fix the `session_id:` frontmatter line, delete the orphan directory, and re-run `sovereign session frames --claim-window <harness-id>` so the window pointer names the right occupant.

RELATED: as of 2026-07-29 frames also carry `predecessor:` frontmatter, stamped from a `predecessor` sidecar written at the claim-window hand-off (SESSION_CONTINUITY §2.2). The sidecar is written to `<sessions_root>/<claimed-id>/`, so an id mismatch ALSO breaks the carried-item lineage walk, not just predecessor selection.
