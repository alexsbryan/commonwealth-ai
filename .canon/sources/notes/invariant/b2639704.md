# THE SCIP INDEX DOES NOT EVICT SYMBOLS OF kind = 'unknown', AND last_indexed_head == HEAD DOES NOT PROVE FRESHNESS FOR THEM.

THE SCIP INDEX DOES NOT EVICT SYMBOLS OF `kind = 'unknown'`, AND `last_indexed_head == HEAD` DOES NOT PROVE FRESHNESS FOR THEM.

Found 2026-09-04 while measuring the cw-lift wire-fork convergence. After a full `sovereign code index .` whose `scip_meta.last_indexed_head` equalled HEAD exactly (47aac21f9), `svrn code converge shape` still reported two forks I had just deleted:

  commonwealth-knowledge::LeasedUnit == sovereign-mesh::LeasedPayload
  commonwealth-api::RingSyncResponse == sovereign-mesh::SyncReply

Both phantom. `git grep` proves neither `LeasedPayload` nor `SyncReply` exists in the tree; the index still holds rows for them at their old lines (auto_ingest.rs:935, ring_sync.rs:226).

SCOPE — NARROW, AND MEASURED, SO DO NOT OVER-READ THIS. Of 13,632 real indexed symbols in sovereign-mesh (line_start > 0, excluding doc-link names), exactly 17 have a name absent from their own file. 15 are lifetime params (`'a`, `'de`) that a word-boundary regex cannot match — false positives of the probe, not staleness. The 2 real ones are the two above, and BOTH carry `kind = 'unknown'`.

Zero rows point past EOF. Zero rows reference a deleted file. FILE-level eviction works; whole-file deletion is evicted correctly (verified separately against Phase 0's 5,013 deleted lines, which returned clean). The gap is symbol-level eviction for the `unknown` kind.

WHAT THE TWO HAD IN COMMON: unusual declaration sites. `LeasedPayload` was declared INSIDE A FUNCTION BODY; `SyncReply` was a private module-level struct. The exporter classified both `unknown`, and the eviction path appears to key on kind or on a re-declaration match that `unknown` rows never satisfy.

CONSEQUENCE FOR ANY MEASUREMENT. `converge shape`, `converge census`, `converge verb`, `dry-report`, `callers` and `blast` all read this graph. A convergence that DELETES a type of this kind will still be reported as a live fork afterwards. My own after-number was wrong because of it: reported 8 groups -> 7, true answer 8 -> 5 (cross-family forks 6 -> 3), and I only caught it because I checked the tree against the tool instead of believing the tool.

THE CHECK THAT CATCHES IT (cheap, and the freshness check alone does NOT):
  git grep -n 'TheTypeName' -- '*.rs'
on every symbol a report claims still exists, before reporting a number. `last_indexed_head == HEAD` is necessary and NOT sufficient.

This is the nc-redundant failure class (an instrument blind to the deletion it exists to reward) in a new place — but far narrower than nc-redundant's, and worth fixing rather than distrusting the graph wholesale.
