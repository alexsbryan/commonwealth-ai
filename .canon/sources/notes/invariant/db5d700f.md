RE-FILING EXEMPLARS BETWEEN CLASSES INFLATES MARGIN ACROSS THE WHOLE SHARED NEIGHBOURHOOD — RE-CHECK THE ABSTAIN CASES, NOT JUST THE POSITIVES. Measured by A/B on 2026-07-29, and it refuted a plausible-sounding argument I had made from first principles.

MECHANISM. The intent axis is k=1 nearest-neighbour and `margin` = winner_sim - runner_up_sim, i.e. a RELATIVE measure. When you move exemplars from class A to class B and A was the class supplying the runner-up in that region, the runner-up disappears into the winner's own class. Every query in the neighbourhood then looks far more confident WITHOUT ANY SIMILARITY CHANGING. Same embeddings, same nearest exemplar, same sim_positive — only which class claims the win, and therefore the margin.

MEASUREMENT. Moved "Where is the chunking strategy defined here?" and "How is rerank implemented here?" from metalingual_query -> code_query. A/B by flipping the tags back, `router-cache rebuild`, re-fit. sim_positive identical in both worlds for every case; margins moved:
  int_abstain_chunker_overlap_hunch  +0.043 -> +0.128   <-- SHOULD ABSTAIN
  int_code_retry_owner               +0.058 -> +0.127
  int_code_chunker_type              +0.214 -> +0.223
  int_code_tokenizer_handoff         +0.110 -> +0.116

THE REFUTED ARGUMENT (mine, do not repeat it). I reasoned: "the same exemplar wins in both worlds at the same sim, so the FP predates the re-filing; only its committed LABEL changed." WRONG. sim_positive was indeed identical (0.561) — but at the margin of 0.100 shipped at the time, the case did NOT fire before the move (margin 0.043) and DID after (margin 0.128). The re-filing CREATED that false positive. The invariant "same winner => same verdict" is false whenever the gate has a margin term. Sim-identity does not imply verdict-identity.

NET EFFECT IS STILL POSITIVE at the gate that ships (0.55, 0.206), which is why the re-filing stands: 40-case bank, WITHOUT re-filing 2 correct/1 mislabel/0 FP; WITH 3 correct/0 mislabel/0 FP. The created FP sits at margin 0.128, far below the 0.206 gate, so it never fires. At the OLD (0.55, 0.100) gate the move was a wash on error count (4c/3ml/2fp -> 5c/2ml/3fp) — it traded a mislabel for a false positive and bought a correct fire.

HOW TO A/B THIS CHEAPLY: back up router/exemplars.toml + router/router-embed-cache.json to a scratch dir, flip the tags in place (text unchanged, tag only, so embeddings are identical by construction), `router-cache rebuild`, `router fit --axis <axis> --format json`, diff the per-case attribution, then restore from backup and verify by shasum.
