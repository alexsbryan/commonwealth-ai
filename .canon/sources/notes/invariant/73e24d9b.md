# Default-chat provenance vanished because the dispatch-time auto-tag stamped the globally-active workspace skill (recipe-author) onto NULL…

Default-chat provenance vanished because the dispatch-time auto-tag stamped the globally-active workspace skill (recipe-author) onto NULL conversations; fixed 2026-07-15 with a background-only resolver

FIXED 2026-07-15. Symptom: desktop chat answers showed NO provenance/citations for general-knowledge questions (e.g. "What were Einstein's four 1905 Annus Mirabilis papers about?") that should have grounded in the Wikipedia corpus.

Root cause (verified by reproducing via the desktop command bridge :9745 → send_message_stream + inspecting the message-complete metadata):
- Router CORRECTLY classified the query as DeepQuery. But `active_mode=Some("recipe-author")` overrode it → intent became ComplexTask → dispatched into the recipe-author agent loop, which runs NO retrieval and attaches NO `provenance`/`retrieved_chunks`. Model answered from parametric weights only.
- `active_mode` = `resolve_active_mode(conv)` = the conversation's `skill_id`. New default chats are created with skill_id NULL (correct), but a dispatch-time auto-tag at `streaming.rs:2600` (and `turn.rs:40`) stamped `set_conversation_skill_if_unset(conv, primary_skill_id_for_conversation())` on first message — clobbering the NULL. This is the exact legacy coupling the 2026-05-24 "surface declares skill at create-time" redesign was meant to remove; it was left behind in both dispatch paths.
- `primary_skill_id_for_conversation()` gives WORKSPACE-kind skills precedence, so it returned `recipe-author` because that workspace skill was globally active.
- It was globally active because `~/Library/Application Support/svrnmesh/desktop.toml` had `active_skills = ["recipe-author"]` persisted. Boot's non-empty branch (`state.rs:450`) re-activates every listed skill INCLUDING workspace ones — unlike `activate_all()`, which deliberately skips workspace skills. So every new default chat got hijacked.

Fix (durable, coupling-free): added `SkillRegistry::background_skill_id_for_conversation()` (background-only, never a Workspace skill) in `sovereign-contracts/src/skills.rs`, and switched both auto-tag sites to it. Now a globally-active workspace skill can NEVER capture a default chat → skill_id stays NULL → routes by intent → retrieval + provenance. Recipe Author conversations are unaffected (their skill_id comes from the create-time surface declaration, not this auto-tag). 3 unit tests pin it. Also: config unblocked (`active_skills = []`) and nulled the two mis-tagged conversations (46c4d3a0, 71e774fb) in sovereign.db.

Verified live on the 35B: Einstein query now → intent=DeepQuery, active_mode=None, provenance present, sources=[{wikipedia, count:29}], 29 retrieved_chunks. A recipe-author-tagged conversation still routes to `recipe_author_loop`.

INVARIANT: workspace ownership of a conversation is a CREATE-TIME surface declaration (persisted skill_id), never inferred from global registry state at dispatch. The dispatch-time auto-tag exists only for background privacy-tagging (LocalOnly exclusion from the shared KnowledgeView).

Secondary leak ALSO FIXED (same session): a globally-active workspace skill leaked into default chats via four sites that fall back to `primary_skill_id_for_conversation()` — `narrow_tools_pre_classification_for_mode` (system_message.rs:341), `narrow_tools_for_intent` (361), `maybe_compute_tool_dossier` (turn_prepass.rs:57), and the register. Self-rearming: opening Recipe Author re-persists `active_skills=["recipe-author"]` via `toggle_skill`, so the next launch re-activated it.

Root fix: `SkillRegistry::activate_configured(ids)` (skips Workspace skills, mirroring `activate_all`) replaces the raw `for id { activate(id) }` loop in `state.rs` boot. Workspace skills are now NEVER globally activated from persisted config — only navigation activates them. Safe because routing/tools/agent-loop all key off the conversation's create-time `skill_id` (via `resolve_active_mode` + `skill_by_id`), NOT global registry activation — PROVEN live: with `active_skills=["recipe-author"]` still in config, a default chat showed `active_mode=None`, `tools=24` (full catalog, not recipe-author's 12), provenance + 29 wikipedia chunks; a recipe-author-tagged conv still routed to `recipe_author_loop` (tools=12). The only thing that read global workspace-active state was the cosmetic `list_skills` `active` flag. Boot logs the skip ("workspace skill in active_skills is navigation-scoped; not globally activating"). Tests: `activate_configured_skips_workspace_skills`, `background_skill_id_*`.
