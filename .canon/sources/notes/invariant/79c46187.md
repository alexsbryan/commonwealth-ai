# A GUEST GRANT WAS UNUSABLE ON ANY DAEMON WITH NO CLIENT TOKEN — INCLUDING THE DAEMON THAT MINTED IT. Proven on the wire 2026-08-28, MAC…

A GUEST GRANT WAS UNUSABLE ON ANY DAEMON WITH NO CLIENT TOKEN — INCLUDING THE DAEMON THAT MINTED IT. Proven on the wire 2026-08-28, MAC guest / FOX lender, encrypted mesh Meshsonics.

Three probes, same tunnel, same ALPN `cwth/guest/0`, same listener:

- FOX plain `http://<tailnet-ip>:9741/status` -> `000`. Correct: an encrypted mesh binds the client API loopback-only.
- `dial_probe --alpn guest --path /status`, fresh RANDOM key, NO bearer -> 200, body names `node-44ae76142b0c3c72`, Meshsonics, `Qwen3.5-4B-UD-MTP-Q6_K_XL` resident.
- `dial_probe --alpn guest --path /v1/models --bearer <the valid grant>` -> **403 `{"error":"remote access not configured"}`**.

The exempt path answers a caller holding NOTHING; the credentialed path refuses a caller holding a VALID grant. Transport, relay, guest ALPN and guest listener are therefore all live, and the failure is the auth layer alone. That pair is the measurement — one probe could not have distinguished "tunnel broken" from "credential refused", and the first read of this (bar 3.2, `svrn mesh use` printing "The issuing node did not accept this link") could not either.

CAUSE. `commonwealth-api/src/client_auth.rs::client_auth_layer` ran `let Some(expected) = state.client_token() else { 403 "remote access not configured" }` BEFORE the guest-grant arm, which lived inside the `match` that followed. `"remote access not configured"` has exactly ONE production emitter, so that branch fired and the grant was never looked at. The two credentials were not independent: absence of the daemon-wide one refused the narrow one.

WHY IT SURVIVED REVIEW. The arm ordering carried a correct and well-argued comment — "ordered strictly after the full-token arm so a guest token can never widen into full access by matching first". That constraint is real and is preserved. What no one checked is that the guard ABOVE both arms dominated them, and the guest path had only ever been tested on a state built by `state_with_guest`, which installs the daemon token first. Every guest test was blind to the case by construction.

FIXED. Daemon token checked first (ordering constraint intact), then the grant, independently; no-credential-at-all still 403s `remote access not configured`. Tests watched failing: `a_guest_grant_is_honoured_on_a_daemon_with_no_client_token`, `no_token_and_no_grant_still_refuses_a_credential_less_remote_caller`.

HOW TO APPLY. When a feature ships a NEW credential class, the fixture that installs it must also cover the case where every OTHER credential is absent. A fixture that always installs the incumbent hides exactly this defect, and it is the same shape as note `68bfc154` (the mint believing config rather than asking the address): the code holds a belief about its environment that the environment does not owe it.
