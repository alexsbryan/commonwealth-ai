THE `chat` ANSWER PATH RUNS IN `sovereign-cli-llm`, NOT THE DAEMON — REBUILD THAT SIBLING OR YOU MEASURE OLD CODE AND NEVER KNOW.

MEASURED 2026-08-16 (financial-corpora F2, commits d8154c36 + 4eccc77c). A frozen 9-item adversarial set was run through the product surface (`sovereign-cli chat ask`) to judge whether a landed fix reached users. It returned 8/9 — the SAME score as the previous measurement — and the failing item was the exact one the fix targeted. Everything read as "the fix did not work".

The fix had never executed. `sovereign-cli` is a thin DISPATCHER that execs into sibling binaries; `chat` is owned by `sovereign-cli-llm`, and that binary was 22 HOURS OLD (Aug 15 20:55 vs the commits at Aug 16 18:04/18:56). Proven against the run's own saved answers, not inferred: `answers/period-beyond-asof.raw.txt` ends the refusal at "can exist here yet." with ZERO matches for the clause commit (ii) appends, and `answers/period-calendar-trap.raw.txt` shows the new `PeriodNotAsAsked` refusal never fired at all. The correct verdict for that run is COULD-NOT-JUDGE (ARCH §18.2/§18.4), not `failed` — the instrument did not measure the subject.

WHAT MADE IT EXPENSIVE: roughly an hour went into the DAEMON — two restarts, a genuine exec-vs-write race, an inode proof — because "the deployed code is stale" feels like a daemon question. The daemon was never on this path. Both the seat and the worker verified the daemon rigorously and neither checked which binary actually serves `chat`.

THE WARNING WAS PRINTED AND READ PAST, on every single invocation: `warning: sovereign-cli-llm binary is 21h older than the sovereign dispatcher — if you changed its code, rebuild: cargo build -p sovereign-cli-llm`. It appeared in the first command of the investigation and was treated as banner noise. IF THAT WARNING IS ON SCREEN, STOP AND REBUILD BEFORE MEASURING ANYTHING.

THE RULE. Before any run that judges whether a change reaches a user, REBUILD EVERY SIBLING THE PATH CROSSES, not just the one you edited and not just the daemon:

    cargo build --bins --features sovereign-cli/dev-tools     # debug; exit 0; ~4m30s warm here

then confirm the binary that OWNS THE VERB carries your change (`strings <binary> | grep -c '<a string your change added>'`), and for the daemon additionally confirm the running process mapped it (inode check — see the companion invariant). Verb ownership: chat/corpus/mcp/recipe/bench/eval/enrich/atlas/claim/mesh/pipeline -> `sovereign-cli-llm`; tools/code/project/atos -> `sovereign-cli-dev`; daemon/doctor/setup -> `sovereign-cli-daemon`; the rest in-process in `sovereign-cli`.

SECOND-ORDER: `sovereign-cli-dev` was MISSING entirely on this host, which is why `sovereign tools call` failed and why the session-boot working-set brief had been failing with exit 127 all session. The same one-line rebuild fixed both. A missing sibling degrades as "feature not available" rather than "your install is incomplete", so it hides.

GENERAL FORM, third instance in one evening of the same mistake: A CHECK ON AN ARTIFACT IS NOT A CHECK ON THE THING THAT CONSUMES IT. Link success is not the test binary; file mtime is not the process image; the daemon is not the answer path. Ask what actually executed the bytes, and check THAT.</content>
