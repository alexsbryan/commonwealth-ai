THE DESKTOP DOES NOT BRIDGE SOVEREIGN_* → SVRNMESH_* ENV VARS — SOVEREIGN_* IS THE CORRECT PREFIX FOR A DESKTOP-ONLY VAR (verified 2026-07-28).

promote_legacy_env() lives at sovereign-contracts/src/rebrand.rs:65 and is called ONLY by the CLI binaries: sovereign-cli/src/main.rs:646, sovereign-cli-llm/src/main.rs:62, sovereign-cli-dev/src/main.rs:56, sovereign-cli-daemon/src/lib.rs:143. sovereign-desktop's fn main() (src-tauri/src/main.rs:63) does NOT call it. Grep confirms ZERO SVRNMESH_* reads anywhere in src-tauri/src/ — every desktop env read is SOVEREIGN_*-only (the sole rebrand usage is path resolution via sovereign_core::rebrand::mesh_data_dir() at state.rs:714).

WHY THIS MATTERS: session frame d7c3d4c1 carried an open 'wart' to rename SOVEREIGN_INVOKE_COVERAGE → SVRNMESH_INVOKE_COVERAGE because the app prints 'bridged 1 legacy SOVEREIGN_* env var(s) to SVRNMESH_* (deprecated)' on every instrumented run. That premise is wrong about WHERE the line comes from. The desktop never prints it — the deprecation line is emitted by the daemon CHILD the desktop re-execs (main.rs:85 → sovereign_cli_daemon::daemon_child_main() → lib.rs:143), which inherits the env and dutifully bridges it. Only the SOVEREIGN_→SVRNMESH_ direction increments the counter that triggers the message.

CONSEQUENCE: renaming to SVRNMESH_INVOKE_COVERAGE would silence the warning (the reverse direction does not increment), and would still work because invoke_coverage.rs reads its own name directly. But it would make sovereign-desktop the ONLY crate in the workspace reading a SVRNMESH_* var, in a process that has no bridging at all — so a future SOVEREIGN_-named caller would silently get nothing. Either name works; neither is a bug. Decide it as a rebrand-direction question, not as a fix for the log line.
