# THE GIT INDEX IS SHARED MUTABLE STATE ACROSS CONCURRENT WORKER SESSIONS. Staging and committing must not straddle two shell invocations…

THE GIT INDEX IS SHARED MUTABLE STATE ACROSS CONCURRENT WORKER SESSIONS. Staging and committing must not straddle two shell invocations while peer workers are live, or your commit sweeps up whatever they staged in the window.

HASH NOTE: the incident commit was rewritten away by the seat-ordered disentangle of 2026-08-14; the clean landed pair is c3ae4428 (tombstone slice) and 688f8eba (drafter-attribution D2). Corrected commit record: note 1ea7c147.

WHAT HAPPENED, 2026-08-14, three live sessions in ONE checkout:
  call 1: git reset; git add <my 5 files>; git apply --cached <filtered hunk>;
          git diff --cached --stat  -> verified EXACTLY 5 files / 310 insertions
  call 2: git commit -F msg          -> committed 16 files / 854 insertions
A peer ran `git add` into the same .git/index between the calls. `git commit` with no pathspec commits THE INDEX. My commit carried the peer's whole slice under my message; its follow-up carried only leftovers under a message describing work I had already committed. Net content was correct; both messages misdescribed their trees. Untangling cost a seat ruling, a freeze on three workers, and a verified rewrite.

NOT THE CAUSE, so nobody re-diagnoses it: not a hook (.githooks/pre-commit is a warn-only rustfmt advisory that stages nothing), not the hunk-filtering (`git apply --cached` was correct and verified), not a bad pathspec. THE VERIFICATION WAS TRUE WHEN RUN AND FALSE 30 SECONDS LATER. In a shared checkout a staged index is a RACE WINDOW, not a state.

THE FIX — PRIVATE INDEX, and it is two steps not one. Step 2 is the part I got wrong the first time and is why this note was revised:

  # 1. build and commit from an index only you can see
  export GIT_INDEX_FILE=/tmp/myindex
  git read-tree HEAD
  git add <paths>              # and/or git apply --cached <filtered.patch>
  git diff --cached --stat     # verify
  git commit -F msg
  unset GIT_INDEX_FILE

  # 2. MANDATORY — refresh the shared index for the paths you just committed
  git reset -q -- <the same paths>

WHY STEP 2 IS MANDATORY AND NOT HYGIENE. The shared .git/index still reflects the pre-commit world, so for a NEWLY ADDED file it now reads as a STAGED DELETION relative to the new HEAD (`git status` shows `D`). The next peer to run `git commit` from the shared index would DELETE YOUR FILE — you would have traded sweeping their work for them silently removing yours. `git reset -- <paths>` resets only those index entries to HEAD and leaves every other peer-staged entry untouched. Verified: after step 2 the path reports clean, the blob is present at HEAD, and peers' staging survives.

SIMPLER ALTERNATIVE when you do NOT need partial-hunk staging: `git commit --only -- <paths>` commits only the named paths and is race-proof against extra staged entries, with no step 2. The private index is needed only when part of a file must be staged (the case that forced it here).

RELATED: the pathspec-commit trap (note 37f84703) covers a file whose WORKTREE holds more than your slice. This is the other axis — a file that is not yours at all entering via the INDEX. Both are live in a shared checkout; the private index closes both.

DETECTION, cheap, do it every time BEFORE reporting a hash: `git show --stat --format="" HEAD` and compare the file count to what you staged. A mismatch means you swept a peer. That check is the only reason the disentangle here was clean rather than archaeological.
