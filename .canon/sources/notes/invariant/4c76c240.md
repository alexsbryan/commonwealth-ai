# A merge does NOT produce a usable corpus. ShardManager::merge_participants -> CorpusEngine::merge_partitions -> sharding::merge_shards…

A merge does NOT produce a usable corpus. `ShardManager::merge_participants` -> `CorpusEngine::merge_partitions` -> `sharding::merge_shards` writes the merged chunks and stops; the output carries `ingestion_in_progress: true, indexes_built: false`, so `installed_indexes()` skips it (is_ingestion_complete gate), `usable_indexes()` cannot search it (indexes_built gate), and `hosted_corpora` gossip advertises nothing (capabilities.rs:103 -> :122 reads installed_indexes()). Finishing it is `corpus_engine::finalize_canonical` (corpus-engine/src/sharding.rs): build_indexes -> mark_indexes_built -> mark_ingestion_complete -> fingerprint LAST. Order is load-bearing twice: the fingerprint after ingestion-complete (a peer pulling against a fingerprint trusts the chunk set is stable), and indexes_built before ingestion_in_progress clears (otherwise a window where a corpus is advertised to peers and not yet searchable).

Fixed on the FOLD path at 2dc1bf160 (`auto_recover::merge_from_fold_coverage`). STILL OPEN on the LEGACY queue path: `coordinate_merge` shares `merge_participants` and neither of its call sites (commonwealth-api/src/routes_internal/corpus_queue.rs:210 and :550) finalizes afterwards, so a queue-mode merge still produces an invisible canonical. Left alone deliberately per ARCH 10.2.

Consequence to know: any test that probes a merged canonical with `CorpusIndex::open` on a path is asking whether the bytes landed, NOT whether the corpus works. That is how cw-lift 5g part 2's bar B2 went green over a corpus `installed_indexes()` returned zero rows for.
