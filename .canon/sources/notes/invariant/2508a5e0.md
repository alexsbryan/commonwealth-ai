RENAMING A CORPUS ID REQUIRES A RE-INGEST, NOT A METADATA PATCH (learned 2026-08-07 renaming brothers_karamazov -> brothers-karamazov-book-1).

Chunk rows in chunks.lance carry `title` and `source_doc_id` DERIVED FROM THE DOWNLOAD FILENAME at ingest time (BulkDownloader writes `<corpus_id>.txt`). Rewriting corpus_id in _corpus_meta.json / chapters.json / config.json / schema_validation.json / cache/seed.json / _tokens.json leaves every retrieval citation still printing the OLD id — verified live: `corpus search` returned "1. [0.033] brothers_karamazov" after a complete metadata rename. That is the one place an end user sees the name, so a metadata-only rename fixes nothing that matters.

THE ATLAS SURVIVES A RENAME UNTOUCHED. atoms.json, edges.json, trajectories.json, configurations.json, gaps.json and _summary.json contain ZERO occurrences of the corpus id (checked by grep -c). So the correct migration is: preserve atlas/ + chapters.json, re-ingest under the new id, copy the atlas back, `enrich backfill-sections`, re-publish. Every scoring axis was identical before and after — the adjudicated artifact is not lost.

SEQUENCE THAT WORKS (bounded, ~5 min, no re-enrichment):
  1. cp -a atlas/ chapters.json + enrichment/ to a keep dir
  2. strip [prebuilt] from the LIVE recipe (~/.sovereign/recipes/<id>/) or install just restores the old snapshot
  3. corpus install <new-id>  -> lands in <id>-partition-node-<hash>/, NOT promoted
  4. corpus merge-partitions <new-id> --yes   (see the partition note below)
  5. copy atlas/ + chapters.json back, enrich backfill-sections
  6. snapshot publish --upload, paste new sha into recipe AND registry
  7. restore [prebuilt], re-verify with a cold install

ALSO: A FRESH `corpus install` ON THIS BOX LANDS IN A PARTITION AND IS NEVER PROMOTED. Reproduced twice (both ingests 2026-08-07). `_corpus_meta.json` shows indexes_built:true, vector+both FTS built, ingestion_in_progress:true, but no canonical dir ever appears and the daemon log records nothing. `svrn corpus merge-partitions <id> --yes` is the documented rescue and completes in 0.1s. scripts/setup-literary-corpus.sh now detects and auto-recovers this. Root cause NOT diagnosed — if this shows up elsewhere, that is the lead.
