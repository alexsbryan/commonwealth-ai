THE PHASE-1 SCHEMA'S PROPERTY ORDER IS THE MODEL'S GENERATION ORDER, AND A BUILD WITHOUT serde_json `preserve_order` SILENTLY CHANGES IT. ontology-v1, measured 2026-09-02 against the live daemon (Qwen3.6-35B-A3B, llguidance strict json_schema).

THE MEASUREMENT. One section (wessex-hoard sec_00014, Halstead 2014 die-link), one body, identical except the JSON-schema property order:
- authored order (section_id, entities_introduced, …, events, claims, questions_raised): 2/2 replays emit `claims`, each with `grade` + `proposed_date` filled.
- alphabetical order (claims first): 0/2 replays emit `claims` at all — 12/12 across four sections and four prompt/schema variants in a matrix that turned out to be invalid for exactly this reason.
The mechanism: llguidance walks `properties` in schema order; an OPTIONAL array asked for first, before the model has "written" the entities, is skipped. The runner sends authored order because sovereign-cli-llm happens to resolve serde_json with `preserve_order` via a neighbour; a `cargo build -p corpus-engine --example …` did not, and its schema was alphabetical.

WHAT CHANGED. `corpus-engine/Cargo.toml` now declares `serde_json = { workspace = true, features = ["preserve_order"] }` itself, and `phase1_schema_keeps_its_authored_order` fails without it (watched fail: the example binary produced the alphabetical schema).

HOW TO PROBE FAITHFULLY (the two errors that cost an hour): (1) the runner's ChapterInput text begins with the section TITLE line and the user body carries `**Position:** chapter N` — a probe without them got different behaviour on the same section; (2) build the probe from the RUNNER'S body (`RUST_LOG=sovereign_enrichment_build=debug` now logs the full request body at `inference_client: request body`), never from a schema you serialised in a different binary. `corpus-engine/examples/phase1_dump.rs` + a 15-second POST is the tight loop; a rebuild is 6 minutes and one build is not a measurement.
