Claude Code background tasks (Bash run_in_background) SURVIVE a worker being parked — process-tree parentage is NOT evidence they will be killed.

2026-08-20, nc-5-corpus rung. I launched ./scripts/sovereign-test.sh as a background task, was told to park, and inspected `ps -o pid,ppid` to answer "will it survive?". The tree was 68714 cargo-nextest <- 68713 bash <- 68695 sovereign-test.sh <- 68692 /bin/zsh (my session's shell). I reasoned: every process descends from my shell, therefore the harness reaper kills it at session end, therefore the gate is never-ran. I broadcast that to the seat in capitals ("TREAT IT AS DEAD, NOT AT-RISK").

It completed 28m31s later: 10288 passed, 0 failed, 47 skipped, cargo exit 0, empty:false.

Two distinct errors, and the second is the transferable one:

1. PARK != SESSION END. Being told to stop acting does not tear down the harness's background-task supervisor. The task keeps running and delivers a completion notification on a later turn. Only actual session termination reaps it.

2. I converted an INFERENCE into a reported FACT. The parentage was real and correctly read; the conclusion drawn from it was a guess about harness lifecycle semantics I had never observed. ARCH_PRINCIPLES §18.1 names four verdicts — passed, failed, could-not-judge, never-ran. The honest verdict for a still-running suite is COULD-NOT-JUDGE (or simply "still running"); "never-ran" is a claim about an event that has not happened yet and cannot be observed in advance. Reporting a predicted failure with more confidence than a measured one is the same defect as reporting a predicted pass — §11 (cite, don't recall) applies to claims about the future too.

Cost of the error, had it not been caught: the seat re-runs a 28-minute suite that had already gone green, or blocks a landing on a phantom gap.

RULE: for a background job, report only what you have OBSERVED (still running as of T; exit code E; log truncated at line N). If you want to know whether it survives, wait for the completion notification or check the task output file — do not predict from ps output. The launchd-one-shot habit for >25min runs is still right for jobs that must outlive a whole session; it was not needed here.
