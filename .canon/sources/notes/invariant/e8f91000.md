# "IS THE DAEMON RUNNING MY CODE?" — CHECK THE PROCESS'S INODE, NOT THE FILE. strings ON THE PATH PROVES NOTHING ABOUT THE RUNNING IMAGE.

"IS THE DAEMON RUNNING MY CODE?" — CHECK THE PROCESS'S INODE, NOT THE FILE. `strings` ON THE PATH PROVES NOTHING ABOUT THE RUNNING IMAGE.

THE CHECK (seconds, no model, no chat turn):

    stat -f '%i' target/debug/sovereign-cli-daemon        # on-disk inode
    lsof -p <daemon-pid> | awk '$4=="txt"'                # image the PROCESS mapped

Equal inodes => the running process IS that file, and `strings` on it is then meaningful. Different inodes => the process is holding an older image and the path is lying to you.

WHY THE PATH LIES. Cargo replaces a binary by RENAME, which mints a NEW inode. A daemon that exec'd before the link finished keeps the OLD inode mapped, while `ls`/`stat`/`strings` on the path all describe the NEW file. Every file-level check then reports your change as present while the daemon serves code without it. `sovereign daemon start` printing "daemon ready" says nothing either — it reports the socket, not the image.

MEASURED, 2026-08-16 (financial-corpora, commit 4eccc77c): a `sovereign daemon stop && start` at 18:37:17 raced a concurrent gate build that finished writing the same binary at 18:37:46 — 29 seconds later. The daemon (pid 94628) loaded the previous image. Both the seat and the worker verified "the binary has my new strings", both were right about the FILE, and the live answer path served two-day-old behaviour for another 35 minutes. It was caught only by a BEHAVIOURAL probe: a refusal whose text commit (ii) had changed came back in the old wording. The restart at 19:14 (37 minutes after the last write) showed inode 108935882 on disk and inode 108935882 mapped by pid 39195 — equal, and only then was the daemon provably on the new code.

THE GENERAL FORM, which is the part worth carrying: A CHECK ON AN ARTIFACT IS NOT A CHECK ON THE THING THAT CONSUMES IT. The same error appeared three times in one evening, each in a different costume: (1) a successful LINK against a new symbol was read as proof the crate's TEST BINARY contained new tests — it did not, and the tests never ran; (2) a file MTIME was read as "all this file's content arrived at that instant" — an mtime is the LAST write of many; (3) `strings` on a binary PATH was read as proof about a running PROCESS. In each case the artifact was genuinely fine and the consumer was stale. Ask what actually consumed the bytes, and check THAT.

RELATED SPECIFIC CHECKS THAT FOLLOW THE SAME RULE:
- New tests actually ran? Grep the run artifact (`target/sovereign-test/latest/cargo.jsonl`, or `target/nextest/default/junit.xml`) BY TEST NAME, with a pre-existing test from the same file as a CONTROL. nextest prints only failures, so silence is not evidence, and a summary count that rose by roughly the right amount is the most convincing form of the trap.
- A filtered test run is self-validating: `sovereign-test.sh --filter <name>` exits 4 if it matched nothing, so it cannot pass vacuously.
- Daemon liveness: /v1/models or /status; there is NO /healthz (404).</content>
