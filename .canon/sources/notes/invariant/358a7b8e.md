# Build sovereign-cli with --features dev-tools or you silently downgrade the deployed dev binary.

Build `sovereign-cli` with `--features dev-tools` or you silently downgrade the deployed dev binary.

`cargo build -p sovereign-cli` WITHOUT the feature succeeds, writes target/debug/sovereign-cli, and that binary has NO `notes`, `code`, `project`, `atos`, or `tools` verbs — the developer toolchain is gated out of the default (end-user) build. Nothing fails at build time. The loss surfaces minutes later on an unrelated command as "<verb>: … not in the default build", which reads as a missing feature rather than "your last build downgraded your install".

Correct: `cargo build -p sovereign-cli --features dev-tools` (plus `-p sovereign-cli-dev` for the sibling that actually runs the verb). Workspace form: `cargo build --bins --features sovereign-cli/dev-tools`.

GUARDED IN CODE since 2026-07-26 (sibling.rs::warn_if_dev_tools_missing, called from main.rs before dispatch): when a `sovereign-cli-dev` sibling sits next to a dispatcher built without the feature, EVERY invocation prints a warning naming the exact repair. Dev-tree-only by construction — an end-user install has no dev sibling co-located, so it stays silent. Muted by the same SOVEREIGN_NO_STALE_WARN=1 knob as the stale-sibling warning. The gated-verb error now also names `-p sovereign-cli` (without `-p` you rebuild the workspace default, not the dispatcher).

The CLAUDE.md line that recommended `cargo build -p sovereign-cli -p sovereign-cli-dev …` was itself reproducing the trap — corrected in the same change.

Same failure family as the stale-sibling warning that already lived in sibling.rs: what you are running is not what you think you built.
