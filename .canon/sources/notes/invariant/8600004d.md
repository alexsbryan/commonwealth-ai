# oicp_version is written on the wire in 49 places and compared in ZERO. Verified 2026-09-11 by grepping every .rs outside target/: the only…

`oicp_version` is written on the wire in 49 places and compared in ZERO. Verified 2026-09-11 by grepping every `.rs` outside target/: the only read anywhere is `oicp-conformance/src/checks.rs:57`, `if m.oicp_version.is_empty()`.

`OICP_VERSION = "0.4.0"` (`oicp-types/src/version.rs:5`) is stamped into `ProviderManifest.oicp_version` (`manifest.rs:102`) and `InferenceRequirements.oicp_version` (`requirements.rs:17`) on every manifest and every request. Nothing compares it — no min-version gate, no refusal, not even a warn. The stated policy is additive-only (`oicp-types/src/lib.rs:21-25`: every v0.4 field is serde-defaulted) and the mixed-version note at `requirements.rs:56-59` confirms the intent: an old peer degrades silently rather than being rejected.

So it is a version LABEL, not a version CHECK, and the field advertises a compatibility guarantee the code does not make. Contrast the rail, which refuses: `oplog`'s `SkippedLine::NewerVersion` becomes `RailGap::NewerVersionLine` (`commonwealth-rail-core/src/admit.rs:87,316`) and the line is reported as a gap rather than downgraded. Two cores, opposite postures, same question.

The conformance check is also ARCH §5 shaped wrong — "is it non-empty" has no failing input anyone can name, because the field is populated by a const.

Two honest fixes, neither safe as a drive-by: check it and refuse on mismatch (starts rejecting peers — behaviour change, needs a compat story for the fleet already running), or delete the field (wire change). Do not "fix" it by adding a warn; that is a third non-answer.

Related, found the same day: `CapabilityHint` is deliberately an OPEN string space with an `x:` extension namespace and a promotion registry (`oicp-types/src/registry.rs`) — an IETF-style extension track. Do not close that while tightening the version field; they are different decisions.
