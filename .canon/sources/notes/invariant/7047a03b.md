=== THE STRUCTURAL HALF NOBODY DOCUMENTS ===
`retrieval:$c` and `retrieval-prod:$c` ARE DIFFERENT CODE PATHS and only one of them runs the product. `scripts/sovereign-ci-bench.sh` lane 2 shells `svrn eval run` with NEITHER `--synth` NOR `--prod-pipeline`, which lands in `runner::run_bank` — the eval runner's own chunk search (`eval_cmd/mod.rs:826`). It never reaches `retrieval_pipeline`, `merge_select`, the grounding gate, the formatter or the estate leg. Lane 2b adds `--prod-pipeline` => `run_bank_prod`, which is the production KnowledgeQuery pipeline in-process. The script's own comment says the raw lanes are "blind to" what 2b catches; the inverse is the part that bites — A CHANGE TO THE RUNTIME PIPELINE CANNOT MOVE THE RAW LANE, so a raw-lane red is never attributable to one.

Also: `--prod-pipeline` runs NO SYNTHESIS, so 2b does not exercise the grounding gate either. The gate's lanes are the SOFT synth ones and `chaos-gate`.

=== HOW TO ADJUDICATE, IN ORDER ===
1. Which lane? raw vs prod decides whether your change is even in the path.
2. `find <index> -newermt <baseline_captured> -type f | wc -l` for the failing corpus AND for a passing one in the same run. That contrast is the control.
3. Only then the per-question JSON at `target/ci-bench/retrieval-*.json` — `retrieval.current.results` vs `retrieval.baseline.results`, comparing `source_score.ratio` and `fact_score.ratio`. A source drop with fact held is a stale expectation.

RUNBOOK §6 says "Retrieval recall (HARD) — exact, any delta is real (embeddings + ANN are stable)". TRUE ONLY WHEN THE CORPUS IS ALSO STABLE, which the table does not say. The re-mint is the legitimate path (§6) and it is a CORPUS adjudication with a dated committed rationale — not something to do inside an unrelated rung to clear a red.
