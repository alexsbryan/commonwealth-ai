A STRANDED `<id>-partition-<node>/` MEANS THE INGEST FAILED — IT IS NOT A PROMOTION BUG (root-caused 2026-08-07, supersedes the "root cause NOT diagnosed" line in note 2508a5e0).

MECHANISM. Every new ingest writes to `<corpus>-partition-<self_node_id>/` by design (engine/ingest.rs "Choose output path": the canonical dir is materialised ONLY by `finalise_solo_ingest` or `ShardManager::coordinate_merge`). The finaliser is invoked from `match result { Ok(r) if !legacy_resume => ... }` — the Ok arm only. So ANY error after the index-build phase leaves a fully-built partition (chunks + vectors + both FTS) with no canonical, and `_corpus_meta.json` stuck at `ingestion_in_progress: true` next to `indexes_built: true`. That combination is the fingerprint.

WHY IT LOOKS LIKE A DAEMON BUG: `svrn corpus install` is fire-and-forget. It prints `{"spawned":true}` and exits 0 REGARDLESS of outcome; nothing polls for a terminal state. The failure exists only as a WARN in `~/.sovereign/logs/daemon.err`. Look in daemon.err, NOT daemon.log — daemon.log is accept/close connection noise and greping it for "ingest"/"partition"/"promote" returns nothing, which reads as "the daemon logged nothing."
  grep -i "ingest failed" ~/.sovereign/logs/daemon.err | tail -3

THE ACTUAL CAUSE HERE: the recipe declared `[enrichment] type = "field_model"` with `domain = "literary"`. Install skips the field-model engine only when `enrichment_type == "atlas"` (engine/ingest.rs ~1808, alongside the same guard for "investigation"); with "field_model" it fell through to `FieldModelEngine::from_recipe`, which returns `UnknownEnrichmentDomain("literary")`. ATLAS PIPELINES AND FIELD-MODEL DOMAINS ARE DIFFERENT REGISTRIES: field-model domains are exactly philosophy | personal | conversational | business_email | institutional (enrichment/domain_registry.rs); `literary`/`philosophy` as an *atlas* `domain` names a `*_atlas` pipeline. An atlas corpus MUST say `type = "atlas"`.

CONTROLLED A/B, same corpus same box same hour: type="field_model" -> `WARN spawn_corpus_install: ingest failed error=Unknown enrichment domain: literary`, partition stranded. type="atlas" -> `INFO finalise_solo_ingest: promoted partition-of-self to canonical`, ingest complete 41 chunks in 4s, zero partitions left.

HAZARD — `merge-partitions` LAUNDERS A FAILED INGEST. The documented rescue happily merges the partition into a "complete" canonical and prints success. That is how a broken recipe produced a working-looking corpus here for half a day. It recovers CHUNKS ONLY; whatever the ingest died on (enrichment, in this case) never ran and nothing says so. Read daemon.err before trusting a merged corpus.

OPEN (not fixed, not quantified beyond this case): `corpus install` surfaces no terminal state to the caller, so every recipe-authoring error in the enrichment block is silent at the CLI. A polling/report step on the install verb would close it.
