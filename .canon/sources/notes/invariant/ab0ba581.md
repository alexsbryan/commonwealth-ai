**`wikitext[start..end]` panics the daemon when byteoffset lands mid-codepoint (em-dashes etc.). Use `wikitext.get(start..end)` and skip on None.**

`corpus-engine/src/extractors/wikipedia_api_article.rs` slices the raw
wikitext using MediaWiki's `byteoffset` values to extract section
bodies. MediaWiki's byteoffset is a UTF-8 *byte* index, but it can
land inside a multi-byte codepoint when section boundaries abut
non-ASCII characters (em-dash `–` is the canonical repro).

**A raw `wikitext[start..end]` slice in that case panics the tokio
worker**, with the message `byte index N is not a char boundary; it
is inside '–'`. On the newsworthy watcher's follower step that runs
inside the daemon's tokio runtime, this kills not just the watcher
but the daemon's HTTP listener — the listener becomes unreachable
even though the process is still alive (visible via `pgrep` but
`curl http://localhost:9741/v1/models` returns HTTP 000 / connection
refused).

Use the fallible slice `wikitext.get(start..end)` and skip the
section (with a `tracing::warn!`) when it returns `None`. Skipping
costs at most one section per article; on the next refresh tick the
wikitext or byteoffsets typically differ and the slice succeeds.
Don't paper over with `String::from_utf8_lossy` (silently mangles
text) or panic-catching (still loses the section AND poisons the
runtime if it spreads).

Observed 2026-05-10: `2026_Israel–Lebanon_ceasefire` article had
a section starting at byte 177704, mid-em-dash at 177703..177706.
First panic took down the daemon listener; no HTTP requests served
for ~2 hours until the fix landed.

Cross-ref: any other place that slices MediaWiki-supplied byte
offsets needs the same treatment. Search for `wikitext[` /
`text[start..` patterns in `corpus-engine/src/extractors/` before
trusting a byteoffset.
