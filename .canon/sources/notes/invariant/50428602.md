# A PLATFORM-SPECIFIC PROBE INSIDE try { } catch { return null } IS A SILENT INSTRUMENT OUTAGE, and it can run for years unnoticed.

A PLATFORM-SPECIFIC PROBE INSIDE `try { } catch { return null }` IS A SILENT INSTRUMENT OUTAGE, and it can run for years unnoticed.

personas.mjs daemonRssMb() shelled pgrep then read /proc/<pid>/status VmRSS, wrapped in a bare catch returning null. On macOS there is no /proc, so it threw on EVERY call and returned null. persona-scoreboard.mjs then rendered the ΔRSS column as "—", which reads as "the daemon did not grow" rather than "nobody measured."

PROOF IT WAS REAL, not theoretical: soak-earlydecline-480-personas.jsonl — an actual EIGHT-HOUR soak — carries `daemonRssMb: null` at both run_start and run_end. Eight hours of memory-growth data that never existed, on a system whose daemon had previously ballooned 10.8GB->37.7GB and been OOM-picked twice (which is WHY the probe was added).

Fixed 2026-08-11 (commit ded482db): each platform branch names its own instrument (linux /proc, darwin `ps -o rss=`), returns {mb, why}, and an unsupported platform returns why="NOT-MEASURED: unsupported platform X". Scoreboard prints "n/m" — deliberately a different glyph from a measured zero — and still reads the old bare-number shape.

GENERAL RULE: a catch-all that returns the same value as "measured, and it was fine" is a §18.3 violation. Return the reason. And when adding a probe, run it once on every platform that will run it — this one was never executed on the host it was most needed on.

RELATED, same commit: when adding a THRESHOLD, measure the metric before choosing the number. A free-RAM sampler drafted against macOS "available" read 26.08GB while `top` showed ~5GB unused (21GB of it "inactive"); the order's 2GB abort line was written against the documented 3.5-5GB band, i.e. STRICT free (vm_stat free+speculative = 4.97GB same instant). Gating on the generous metric would have produced a threshold that could never trip — a safeguard in name only.
