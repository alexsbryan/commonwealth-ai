# Don't load Gemma 4 (E2B/E4B/E27B) into a Metal-backed chat slot on this stack — ggml-metal lacks the matmul pipeline kernels for Gemma 4's…

Don't load Gemma 4 (E2B/E4B/E27B) into a Metal-backed chat slot on this stack — ggml-metal lacks the matmul pipeline kernels for Gemma 4's architecture and decode SIGSEGVs. Qwen confirmed working.

Gemma 4 (E4B and presumably the rest of the E-series) cannot run on Apple
Metal with the ggml backend bundled in `llama-cpp-2 0.1.145`. Decode
SIGSEGVs in `ggml_metal_encoder_set_pipeline + 8` when ggml looks up a
Metal compute pipeline state for Gemma 4's matmul kernel shape and gets
nil back, then dereferences it.

Why: ggml's Metal kernel coverage lags behind CUDA for newer
architectures. Gemma 4 E4B uses embedding-tied weights and head/group
dimensions that don't match the matmul kernel pipelines compiled into
this version's bundled ggml-metal source. Confirmed reproducible across
Q6_K and Q5_K_M quantizations of `gemma-4-E4B-it` on M2 Max +
macOS 26.2 — quant-independent, architecture-level. Switching to
Qwen3.5 9B Q4_K_M runs cleanly on the same Metal stack, isolating
the fault to Gemma 4 specifically.

How to apply:
- Don't tag a Gemma 4 GGUF as the fast / primary slot when the desktop
  / daemon is running on macOS Metal. Pick a Qwen-family model
  (Qwen3 / Qwen3.5) for chat slots on Apple Silicon until llama-cpp-2
  bumps to a version with the missing Metal kernels.
- If Gemma 4 is needed despite this, set
  `SOVEREIGN_FORCE_CPU_CHAT=1` (now working correctly after the
  `n_gpu_layers=0` fix in `sovereign-inference/src/embedded.rs`).
  Decode runs on CPU via Accelerate / BLAS — slower but stable.
- Re-test before declaring this resolved: bump `llama-cpp-2` in
  `sovereign/crates/sovereign-inference/Cargo.toml`, restart the
  desktop, and confirm Gemma 4 decodes cleanly. The fix lands when
  upstream ggml-metal adds the kernel.
- Gemma 3 status: untested in the session that produced this note.
  Don't assume Gemma 3 has the same problem — its architecture is
  closer to Gemma 2 / earlier and may be fully covered. Test before
  ruling it out.

Code path:
- Crash site: ggml-metal's `ggml_metal_op_mul_mat` calling
  `ggml_metal_encoder_set_pipeline` with a nil pipeline state.
- Reachable via `ModelSlot::generate_sync` → `LlamaContext::decode`
  → `llama_decode` → ggml backend graph compute.
- Force-CPU lever: `embedded.rs::ModelSlot::load` reads
  `SOVEREIGN_FORCE_CPU_CHAT`; when set, sets `n_gpu_layers=0` AND
  context flags `offload_kqv(false).with_op_offload(false)`. Both
  are required — the kvcache flags alone leave model weights on
  the GPU and still hit Metal pipelines.

Diagnostic discipline:
A C-level SIGSEGV in ggml's Metal backend cannot be caught by Rust
`catch_unwind`. The process dies on the spot. Crash isolation
options if Gemma 4 ever HAS to run on Metal (rather than just being
avoided): route inference through the daemon's HTTP endpoint
(Attach mode partially achieves this but the desktop still loads
its own embedded slot today) or run inference in a subprocess
watchdog.

Confirmed on: M2 Max, macOS 26.2, AGXMetalG14X 342.3, llama-cpp-2
0.1.145.
