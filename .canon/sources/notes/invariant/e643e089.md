# QWEN3.5 ON gfx1151: INSTALL flash-linear-attention BUT NOT causal-conv1d. The COMPLETE transformers fast path is memory-infeasible…

QWEN3.5 ON gfx1151: INSTALL flash-linear-attention BUT NOT causal-conv1d. The COMPLETE transformers fast path is memory-infeasible (measured 2026-08-01/02, Strix Halo, sovereign-rocm-7.2.4).

Supersedes 470022d0, which had the right conclusion but an overstated evidence tally — see CORRECTION below.

Qwen3.5-0.8B is 18 `linear_attention` (gated deltanet) layers to 6 `full_attention`. transformers gates on `is_fast_path_available = all(...)` over four symbols: causal_conv1d_fn, causal_conv1d_update, chunk_gated_delta_rule, fused_recurrent_gated_delta_rule. With only fla, three of four resolve and the model takes the SEQUENTIAL path. Add causal-conv1d and all four resolve, switching to the CHUNKED gated-delta-rule path, whose intermediates at seq 4096 x 16 heads x 128 kv-dim do not fit.

MEASURED, ORPO probe, effective batch 32 / seq 4096 / micro 1 / grad-ckpt on:
- no fla at all .................. 231.8 s/it, ~24 GB GTT  (eager torch deltanet)
- fla only (ccc absent) ......... 177.1 s/it, ~25 GB GTT   <- USE THIS
- fla + causal-conv1d (all four) . dies,      ~100 GB GTT

The chunked path is genuinely FASTER per step — attempt 2 finished step 1 in 144.1 s vs 178.0 s for the shipped config. It simply cannot fit. That is the whole trade.

PER-RUN MARKER — which memory path did a run take? The trainer's env dump does NOT log causal_conv1d or fla, so the only record in train.log is the transformers warning:
  "The fast path is not available because one of the required library is not installed."
  PRESENT -> causal-conv1d absent -> sequential -> ~25 GB -> survives
  ABSENT  -> all four resolved    -> CHUNKED    -> ~100 GB -> dies
Ignore that warning when present. It fires if ANY of the four is missing, and the expensive part (the deltanet recurrence) is already on fla's Triton kernels. Chasing it to zero is what cost the two runs below. TODO: log both kernels in the env dump so this stops depending on a warning string.

CORRECTION 1 — evidence tally. 470022d0 said "SIGKILL, twice ... both died rc=137". Wrong. Verified from the logs 2026-08-02:
- m0-halo-trl-OOMKILLED-attempt2: rc=137 (SIGKILL). The ONE genuine host-OOM kill. Completed step 1, then died.
- m0-halo-trl-OOMKILLED-attempt3: rc=143 (SIGTERM) — a DELIBERATE kill, not the OOM killer. The directory name is a misnomer, kept only because notes cite the path; each run now carries a WHY_DISCARDED.txt.
Attempt 3 is actually the GTT ATTRIBUTION measurement: killing it dropped mem_info_gtt_used 102,892 -> 21,574 MiB, attributing ~80 GB to the trainer. Its steps.jsonl is 0 bytes and it lived ~104 s — LESS than one step — so GTT hit ~102.9 GB before a single step completed. The blowup is at the first forward/backward, not a slow leak. So: one OOM kill + one attribution kill, and the conclusion is unchanged.

CORRECTION 2 — causal-conv1d IS buildable. An earlier pass claimed "no ROCm compiler in this container" and concluded it was uninstallable. Wrong, and do not repeat that framing. The image is runtime-only ROCm but the ROCm 7.2.4 dnf repo is configured; hipcc/rocm-llvm/hip-devel/hipcub-devel install fine and causal-conv1d COMPILES clean for gfx1151. It is the RUNNING of it that is infeasible.

A SIGKILL leaves NO Python traceback, so an OOM death looks like the process silently vanishing. Do not hunt for a stack trace. And `torch.cuda.max_memory_allocated()` read only 20.31 GB while the process held ~100 GB — it does NOT see GTT the HIP runtime reserves outside PyTorch's allocator. On unified memory ALWAYS cross-check /sys/class/drm/card1/device/mem_info_gtt_used.
