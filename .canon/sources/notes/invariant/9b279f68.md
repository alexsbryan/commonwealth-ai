AXIS_CATALOG entries and resolve_type_extensions arms must land in the same PR — drift is silent

`AXIS_CATALOG` in `corpus-engine/src/enrichment/atlas/axis_catalog.rs` is descriptive of what `resolve_type_extensions` (in `corpus-engine/src/enrichment/atlas/resolution.rs`) actually projects into `atoms.json`. The two MUST land together.

Why: drift between projection and catalog is silent. The two failure modes:

1. Resolver projects, catalog missing. Atoms land in `atoms.json` (qualified Concept / Claim / Position / Opposition / etc.) but no `TypedAxis` entry exists for them. The bench has no axis to score against, so prompt-iteration improvements that lift those atoms are invisible to the F1 numbers. Repeats the pre-Gap-B failure mode (typed extractions were live but bench couldn't see them).

2. Catalog declares, resolver missing. Bench tries to score an axis whose `AtomKind` filter never matches anything in `atoms.json`. Every expectation comes back as a miss; F1 craters. False regression signal.

How to apply:
- When adding a `resolve_type_extensions` arm for a new typed extension shape (mechanism, position, evidence, motif, image, task, decision, etc.), add the matching `TypedAxis` const entry in `AXIS_CATALOG` in the same change.
- Also extend `axis_expectations` in `sovereign-cli/src/enrich_cmd/eval.rs` with the per-axis bridge from the GoldenSet's `expected_<axis>_atoms` named field into the uniform `AxisExpectation` view.
- See `~/dev/commonwealth-ai/sovereign/bench/BENCH_LOOP.md` §9 "Adding a new typed axis" for the four-step checklist.
- Move 2 (pipeline-as-config) and Move 3 (golden scaffolder) will lean on this invariant — the scaffolder samples atoms.json against the catalog to draft a golden TOML. A drifted catalog produces a draft that doesn't match reality.

Pairs with [[project-gap-b-resolver-projection-landed]] (the projection it describes) and [[project-obsidian-bench-loop-closed]] (the bench loop the catalog now drives).
