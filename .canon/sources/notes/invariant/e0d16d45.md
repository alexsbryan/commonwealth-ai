THE NEXT-EDIT WRONG-FIRE FLOOR IS ~12.8%, AND WHAT IS LEFT NEEDS SYMBOL RESOLUTION RATHER THAN ANOTHER THRESHOLD (measured 2026-08-06 at dbbf8cd4).

DECOMPOSITION OF THE 39 WRONG FIRES REMAINING AT MIN_RULE_CHARS=5: 12 on positives, 27 on negatives — and ALL 27 negatives are `neg_literal_trap`. Every other negative shape is at ZERO (neg_revert 0/130, neg_exhausted 0/106, neg_divergent 0/83, neg_dissimilar 0/18). So literal traps are not part of the wrong-fire problem, they ARE it.

THE BANK'S GATE LABEL ON THOSE CASES IS MISLEADING — do not design against it. All 27 carry `gate: "only comment/string sites remain"`, which reads like a lexing problem. It is not. Inspected directly, the surviving sites are mostly real CODE:
  neg_literal_trap-00007 (ruby)       `@launch_event_sent = false` — a genuine occurrence the dev chose not to rename
  neg_literal_trap-00008 (typescript) `const settings = ref ? ...`  — a DIFFERENT local variable sharing the name
  neg_literal_trap-00052 (json)       `"clientID"` as a schema key
  neg_literal_trap-00031 (php)        6 code sites
The real construction is "the identifier recurs in code but refers to something else."

MEASURED, SO IT NEED NOT BE RE-TRIED: a lexical site filter (skip sites inside comments and/or string literals, language-tabled state machine, `lexfilter.py`) removes only 6 of the 27 and makes wrong-fire WORSE — 12.8% -> 13.1% — because it drops more fires than wrongs (useful 141->139, partial 125->106). Comments-only: 27->25. Strings-only: 27->23. Not worth shipping.
Also refuted: a guard-dependent length bar (short rules allowed when word-guarded) leaves wrong at 52 / 15.5%, no better than baseline — because the traps ARE guarded identifier renames.

THE CEILING, STATED PLAINLY. The remaining 21 require deciding whether two textual occurrences of one identifier denote the same thing. That is scope/symbol resolution; a text matcher structurally cannot see it. Within the text-matching mechanism class the only remaining lever is `min_support>=3`, which reaches 0 negative wrong fires by firing almost never (56 useful vs 141, a 61% cut) — see note c97bf8cd. So: 12.8% is the floor for THIS mechanism, and going below it is a change of mechanism class, not a change of threshold.

WHAT WOULD ACTUALLY BREAK IT, unmeasured and NOT a recommendation yet: scope-aware site filtering. The daemon already owns a SCIP graph for indexed repos, but next_edit.rs is deliberately pure (no editor knowledge, no index) and the editor buffer is often unsaved/unindexed, so this is a real design question about where the lane lives — not a constant to tune. Cost it before building it.
