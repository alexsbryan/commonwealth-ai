M3 IS ARMED AND TRAINING — and the arming path itself was broken in two ways, each of which would have cost the run. Vast pod 46909861 (RTX PRO 5000 Blackwell, $0.6681/hr, Taiwan), armed 2026-08-05 ~12:40 PDT.

Payload preflight 9 passed / 0 failed -> FIT (93,693 rows, 921 MB; model 9.3 GB; sm_120; 47.27 GB >= 46 floor). Bucketing 93,693 rows in 257.7s, 23 rows (0.025%) dropped over 4080 tokens. Memory tripwire armed at 43.5 GB. expandable_segments default fired without being set by hand.

BUG 1 — cmd_probe COULD NOT ARM THIS RUN, and M3_RUN_OF_SHOW.md §4 said it could. Three silent wrongs at once: ARM is hardcoded to A at pod.sh:382, so `ITERS=5856 DATA_DIR=data/orpo-ab probe` trains data/orpo-76k (the arm-A dataset) while every artifact is named m3-4b-ab; SAVE_EVERY pinned to 1000, the wrong ladder; and SAVE_TOTAL_LIMIT never passed — the G1 ladder-deletion bug, which would have landed a 63-hour run holding rungs 5000+5500 with the step-2928 decision point gone. Fixed by cmd_arm: defaults to the §1 config, prints the resolved set before spending, REFUSES when SAVE_TOTAL_LIMIT cannot hold the rungs the run will write, and takes the ARM->dataset mapping from `launch_arm.sh --print-data` so there is one decider (§10.6).

BUG 2 — A DETACHED LAUNCH CAN LEAVE THE SSH CLIENT HUNG, AND THE LIVENESS CHECK BEHIND IT UNREACHABLE. Measured live: the remote command printed `detached` and the trainer started, but the ssh CLIENT never exited — the channel stayed open behind a correctly setsid+nohup'd job. cmd_arm was waiting on it in the foreground, so the poll that turns "I sent a command" into "a trainer is running" was never reached (§18.1). Fixed: the launch client is backgrounded locally with its transcript kept at cloud/.last-launch-<id>.log, and the liveness poll — not the launch exit code — is what prints ARMED. Proven safe: killing the hung client left pgrep count 1, i.e. setsid detachment holds.

NEW SURFACES: `cloud/pod.sh arm|status|rung`. `status` = alive / step / median s-per-it / ETA / rungs on disk / accrued cost in one call (fetch is the wrong tool for a progress check on a 63-hour run). `rung <id> <step>` pulls a checkpoint's scorable half only — optimizer/scheduler/RNG stay on the pod, 496 MB of each 763 MB checkpoint that scoring cannot use.
