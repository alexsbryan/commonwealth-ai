A PARALLEL-WORKER MERGE FINDS DEFECTS NEITHER BRANCH CAN SEE, AND THE MERGE IS THE ONLY PLACE THEY EXIST. Four ontology-v1 phases merged 2026-09-02 (P0, then P3/P4/P5 built concurrently in three worktrees off one base). Three classes, each caught only by putting the branches in one tree:

1. TWO WRITERS, ONE OF THEM STALE. P4 added `write_atlas_atoms` (REPLACE — its classifier drops a prior run's reified merges, so it cannot append) and P3 added `append_atoms_and_edges`, at the same place in `corpus-engine/src/enrichment/atlas/writer.rs`. P3's doc states why it rebuilds `atoms.lance`: "writing only atoms.json would leave the read path missing atoms the export claims are there." P4's function did exactly that. Each branch had only its own writer, so neither could see it. Fixed at the merge: `write_atlas_atoms` rebuilds the v2 store too.

2. A PATH-KEYED GATE BROKEN BY A WHOLE-FILE MOVE — twice. P0's crate split moved `enrich_cmd/extract.rs` and `enrich_cmd/inference_client.rs` into `sovereign-enrichment-build`, and BOTH the F26 egress census (keyed on path, with per-file construction-site counts) and clock-gate (keyed on path) reported the moved code as NEW. Neither is new; `git show <base>:<old-path>` is the check that tells growth from a move, and it takes one command. The clock one was better fixed than accepted — the two hand-rolled `SystemTime::now()` blocks were byte-identical to `sovereign_core::time::unix_millis()`.

3. DUPLICATE SECTION NUMBERS IN A LEDGER. P3 and P5 each wrote a `SYSTEM_OVERVIEW §10.1f`; the merge auto-merged them into two adjacent sections with the same number, one of them physically before §10.1e. A markdown heading is not a symbol, so nothing complains.

THE PROTOCOL THAT WORKED, and is worth repeating: workers were told NOT to run `--update-baseline` on their own tree. `quality/baselines/` is one set of files; three workers re-pinning independently merge by silently reverting whichever lands first. Both P3 and P5 refused it, each wrote a ledger row with its own measured numbers, and each asked the merge to decide. The merger then re-pinned ONCE over the merged tree with the gate's own numbers (`SYSTEM_OVERVIEW §10.1h`). Result: all eight enforcing ratchets green, and an acceptance that is reviewable because the growth is separated from the cuts already banked.

ALSO: verify a worker's "this failure is inherited, not mine" claim before accepting it. P4's was true and UNDERSTATED — arch-gate was red on the base tree too, and P4 only saw it green because it had split four of its own files to hold it there.
