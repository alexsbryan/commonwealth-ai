AN OPAQUE SIGNED PAYLOAD MUST BE CANONICAL BY CONSTRUCTION, OR A CARGO FEATURE CAN INVALIDATE EVERY SIGNATURE ON THE MESH (found 2026-08-31 while making the ring rail generic).

THE HAZARD. A signature covers BYTES. `serde_json::Value` has no bytes — it has a serializer, and which bytes that serializer emits for an object depends on `serde_json/preserve_order`. That feature is ON in this workspace today (verified: `indexmap` appears in serde_json's dependency list in Cargo.lock), enabled transitively by something in the graph, and ANY crate added later can flip it. With it, an object round-trips in INSERTION order; without it, in SORTED order. Flip it and every signature in every ring stops verifying at once — and the symptom is not "a feature changed", it is a journal that has become entirely BadSignature.

WHY IT IS NEW. A TYPED body never had this problem: serde writes struct fields in declaration order regardless of the feature. Making a body opaque is what introduces it. So the fix belongs in the type that makes it opaque, not in a rule somebody has to remember.

THE FIX (rail/payload.rs). `Payload` wraps a `Value` and is canonical by construction: objects rebuilt with keys inserted in SORTED order, recursively, so an IndexMap-backed Map and a BTreeMap-backed Map iterate identically. Applied in `Deserialize` too, not only in `new()` — otherwise a line read off the journal or off the wire re-serializes to bytes other than the ones its signature covers, and reports as a mysterious BadSignature instead of what it is. Array order is left alone: that is data, not spelling.

FLOATS ARE REFUSED OUTRIGHT, and that is the same problem one level down. `1e2`, `100.0` and `100` are one value with three spellings and which one comes back is the library's formatting choice, not anything the data says. Integers have exactly one spelling. On a rail whose purpose is that N laptops derive identical bytes from identical facts for years across library upgrades, that is not a risk worth carrying for the convenience of writing 3.5. The refusal names the fix (cents, grams, micro-degrees, milliseconds) and it reaches an app author as a 422 sentence. Refusing floats also restores `Eq` on every type above `Payload`.

VERIFIED ON A LIVE DAEMON: a POST whose payload keys were deliberately scrambled lands on disk with keys sorted, and `payload_key_order_does_not_change_the_id_or_the_signature` pins that two spellings of one act derive the same OpId and the same signature.

THE SAME TRAP EXISTS ANYWHERE ELSE A `serde_json::Value` IS SIGNED, HASHED, OR CONTENT-ADDRESSED IN THIS TREE. A typed struct is safe; a Value is not.
