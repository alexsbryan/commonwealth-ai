Unguarded PyTorch MPS long-context sampling kernel-panicked the 64GB M2 Max (2026-07-07) — always cap MPS watermark + empty_cache per item + RSS guard

2026-07-07 15:36: the J-lens Phase 3 sampling run (`research/jlens/
phase3_bank_vector.py --sample`, Qwen3-8B bf16 on MPS, ~6.5k-token
prompts × 64 generate calls) grew to a ~94GB phys footprint on the 64GB
machine and caused a full kernel panic (watchdog timeout — watchdogd
starved 90s; compressor 100% of segments limit, 61 swapfiles, LOW swap
space with only ~66GB free disk). macOS jetsam does NOT save you; the
box swaps until userspace freezes, then the kernel panics.

Why: HF `generate` re-concatenates the dynamic KV cache every decode
step; PyTorch's MPS caching allocator retains every freed odd-sized
buffer and never returns it. Footprint ratchets monotonically across
long-context generate calls unless explicitly released.

How to apply — any long PyTorch/MPS generation loop on this machine:
- `PYTORCH_MPS_HIGH_WATERMARK_RATIO=1.0 PYTORCH_MPS_LOW_WATERMARK_RATIO=0.8`
  at launch → MPS raises OOM instead of swapping the machine to death.
- `gc.collect()` + `torch.mps.empty_cache()` between items.
- In-process RSS guard (`ps -o rss= -p $$`), abort ~40GB with state saved.
- Incremental checkpointing (save after each item) so a crash loses ≤1 item.
- External per-PID watchdog: kill at rss>45GB or disk avail<35GB. Never
  `pkill -f` patterns that can match the user's daemon (debug dispatcher trap).
- Check other residents first: the main daemon idles ~14GB and hits 33GB
  with the 35B judge loaded — don't run PyTorch sampling while the 35B is
  resident (see [[project-jlens-workspace-phase01-2026-07-07]]).

Hardened loop lives in `research/jlens/phase3_bank_vector.py`
(cmd_sample); incident writeup in `research/jlens/FINDINGS.md` third
incident note.
