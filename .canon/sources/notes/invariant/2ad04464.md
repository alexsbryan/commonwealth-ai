DESKTOP ATTACH MODE RUNS THE LEAST-COMPLETE INFERENCE PROVIDER, AND THE TEST SUITE NEVER EXERCISES IT (2026-07-27). This is the mechanism behind a recurring class of "works in CLI, silently dead in the desktop app" bugs — three confirmed instances so far.

THE STRUCTURAL CAUSE. Since the W1 flip (2026-07-18) supervised child-process mode is DEFAULT ON (supervisor_setup.rs:39). On a healthy child daemon the desktop REWRITES its own boot mode to Attach (supervisor_setup.rs:196-207). So essentially every shipped user runs Attach -> SplitInferenceProvider (oicp-client/src/lib.rs). Meanwhile SOVEREIGN_FORCE_LOCAL=1 appears ONLY in the e2e harnesses (first-launch-setup.journey.spec.ts:77, faults/spawn.ts:128), which forces the OTHER path: EmbeddedLlamaCpp + MeshInferenceProvider. Override counts: EmbeddedLlamaCpp 20/21, MeshInferenceProvider 19/21, SplitInferenceProvider 9/21. THE TESTED CONFIGURATION AND THE SHIPPED CONFIGURATION ARE DIFFERENT PROVIDERS.

THE AMPLIFIER. InferenceProvider (sovereign-contracts/src/traits.rs:344-746) has 25 methods: 4 required, 21 defaulted, and 16 of those defaults SILENTLY DEGRADE — they return Ok(()) / None / vec![] / "unknown", which are plausible answers, not errors. Rust emits no diagnostic when a wrapper inherits a default while the thing it wraps has a real impl. MeshInferenceProvider already survived this minefield and documents each forward ("without this forward /status.inference.resident would always be blank"); SplitInferenceProvider never got that pass.

THE THREE CONFIRMED INSTANCES (all same shape: wrapper fails to forward to self.chat):
1. primary_slot_status — fixed 5b73b342, SHIPPED WITH ZERO TESTS, still unprotected.
2. warmup_primary — TWO faults in series: the silent Ok(()) default AND the route mounted on internal_router (:9742) while every caller targets :9741. Proven live on the running daemon: POST :9741 -> 404, POST :9742 -> 200. Two faults were exactly as quiet as zero faults, because RemoteApiProvider::warmup_primary maps non-2xx to Ok(()).
3. complete_stream_with_finish — the trait default wraps the UNTYPED stream and appends a Finish{reason:Stop, usage:None} it never observed, so in Attach mode a max_tokens truncation rendered identically to a clean stop and token accounting was always None, on EVERY streaming turn.

THE TEST ANTI-PATTERN THAT HID IT. warmup_url_strips_v1_suffix asserted the URL STRING was correct — the one sound link in a three-link chain whose other two links were both broken. Pure-helper tests cannot catch inherited-default bugs. The only test shape that can is wire-behaviour assertion: see split_provider_actually_sends_the_warmup_request (oicp-client/src/lib.rs) — one-shot TcpListener, assert the request line. That covers 1 of 25 methods.

STILL OUTSTANDING (audited, not fixed): SplitInferenceProvider::count_tokens (chars/4 heuristic, so Attach and Local budget context differently), n_ctx_train_for_primary -> None, extras_inventory -> []. RemoteApiProvider::model_id_for -> "unknown" and effective_context_size -> None DESPITE the struct holding both values; its primary_slot_status never got the 5b73b342 fix. LandscapeDigestProvider::entity_inventory -> None in Attach (documented deferral) kills relationship-weighted memory decay. MeshInferenceProvider::rerank_batch not forwarded.

HIGHEST-LEVERAGE FIX IS NOT ANY SINGLE IMPL: run one CI job in Attach mode. Every bug here is invisible because the shipped path is never executed by a test.

ALSO: the /internal/ PATH PREFIX SAYS NOTHING ABOUT WHICH PORT A ROUTE IS ON. /internal/corpus/watch/* is on the client port; /internal/rpc-warm is on the internal port. Read the router, not the path. Relatedly routes_internal/mod.rs:2 claims "mTLS, port 9742" — there is NO TLS anywhere in server.rs.
