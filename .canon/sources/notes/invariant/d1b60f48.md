THE NAMED DISPATCH PATH NEVER CONSULTS `sharding`, SO A `LocalOnly` ENVELOPE CROSSES THE TRUST BOUNDARY. Measured 2026-08-06 (M6-B arm 5): a non-streaming named request stating `sharding == LocalOnly` was served by peer LittleMac, 200.

This contradicts TWO written contracts:
  - peer_inference.rs:18-19 rule 1 — "No OICP on the request, or `sharding == LocalOnly` -> local."
  - routes_inference.rs:242-268 — the forwarding-boundary gate written for exactly this, "LocalOnly requests must NOT cross the trust boundary."

NEITHER FIRES, for one structural reason: the privacy check lives in `offload_verdict`, and named dispatch DELIBERATELY never reaches it (peer_inference.rs:1795 says so in as many words). The routes_inference gate sits at Priority 1 — AFTER Priority-0 `local_inference`, which IS the mesh-routing provider that does the forwarding. So when the hop bound was hand-added to the named path, it did not bring the privacy half of what that path bypasses.

SAME SHAPE AS THE BUG M1 WAS WRITTEN FOR: a gate written into one call site instead of into the decider (ARCH_PRINCIPLES §10.6). The forward budget got fixed by extracting `resolve_named_dispatch` as THE decider; privacy did not get the same treatment.

MAGNITUDE — LATENT, NOT LIVE. Exposure needs a caller that sets LocalOnly AND pins a model name. Today nothing does both: the chat runtime sets LocalOnly for skills like `inner-work` (system_message.rs:58-64) but pins no name, so it takes the scored path where the privacy gate works; the thin-client shape (IDE, curl) pins a name but attaches no envelope at all. Nothing leaks today — but the defense is COINCIDENCE, not structure, which is what §7 forbids. One skill declaring `local_only` while also pinning the fast model makes it live.

Before adding any caller that pins a model id, check whether it also declares LocalOnly.
