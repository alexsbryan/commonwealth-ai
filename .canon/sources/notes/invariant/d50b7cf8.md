CORPUS STATUS `ready` DOES NOT MEAN SEARCHABLE, AND IT MISLED A WHOLE INVESTIGATION (2026-08-28).

`svrn corpus status <id>` reports state=ready for a corpus whose vector index was
never written. `wikipedia-newsworthy`: 26 data fragments, ZERO dirs under
chunks.lance/_indices — i.e. UnavailabilityReason::NoVectorIndex. Retrieval
returns 0 from it, permanently, while the status surface says ready.
`studio-nb-test` is the sibling case: embedding_model="workflow-embed" against a
loaded qwen3-embedding-0.6b. Compare `sep`: 5 index dirs, 2937 fragments.

Check that is actually decisive:
  ls ~/.svrnmesh/indexes/<id>/chunks.lance/_indices | wc -l   # 0 => unsearchable
  python3 -c "import json;d=json.load(open('.../_corpus_meta.json'));print(d['embedding_model'],d['embedding_dimensions'])"

WHY THIS IS AN INVARIANT AND NOT A NOTE-TO-SELF: during the 2026-08-28 chaos
soak triage I twice concluded the app was FABRICATING a system-status message
("the knowledge base is still building — rebuild in Settings → Knowledge"),
on the strength of `corpus status: ready`. Both times the app was telling the
truth and the UX judge was wrong to score it a hallucination. Do not use
`corpus status` to falsify a claim the retrieval path makes about availability.

Downstream consequence worth knowing: the chaos harness's read_get_chunk
succeeds on these corpora (chunks exist), so it happily generates questions from
a corpus that can never answer them. Passage-fetchable != retrievable.

Open, ranked, none of them done:
 1. the UX judge cannot tell a TRUE system-status statement from a fabricated
    one; it feeds `broke` -> POSITIVE EXPERIENCE, so tuning against it would
    push the app away from honest unavailability reporting (ARCH 18.6 change).
 2. `corpus status` should not print `ready` with zero vector indexes.
 3. unavailability_guidance's text leaked verbatim into a user-facing answer
    (soak step 69) — model recited its own instructions.
 4. chaos.mjs should verify retrievability, not just chunk-fetchability.
