"THE 122B DOES NOT FIT THIS BOX SOLO" IS NOT TRUE AS A STANDING PREMISE — operator correction 2026-08-06, and I had banked it in a strategic argument.

WHAT THE ORIGINAL READING WAS: C5 (2026-08-06) recorded a local-fit-gate refusal — 89 GB needed vs 73 GB usable — and I carried it forward as "the 122B no longer fits this box". That was ONE QUANT on ONE DAY with TWO RUST-ANALYZER PROCESSES holding 12.1 GB. An environmental reading, not a property of the machine or of the 122B class.

THE FACTS ON DISK (RuggedFox, 125 GB host RAM):
  sovereign/models/Qwen3.5-122B-A10B-MTP-GGUF/UD-Q5_K_S/  -> 3 shards, 1 + 47 + 36 = ~83 GB   <- the MTP one; FITS SOLO
  sovereign/models/Qwen3.5-122B-A10B-UD-Q5_K_XL/          -> merged single file 86 GB, plus a 3-shard split ~88 GB
The MTP variant is ~5 GB smaller than the Q5_K_XL that tripped the gate, and the gate reading also depended on transient RSS.

WHY IT MATTERS BEYOND THE FACT: it was the LAST STANDING JUSTIFICATION FOR MULTI-NODE on this fleet, and it cuts the opposite way from how a "correction" usually feels. C5 showed splitting costs ~71% of throughput; M3 showed nothing ever moves and local-first already holds (note abdb39fa). "Models too big for one box" was the one argument still alive — and it has NO INSTANCE on this fleet. So MESH_N4_TOPOLOGY.md's own exit clause ("not worth continuing if measurement shows one box serves the realistic fleet") is CLOSER, not further.

WHAT WOULD STILL JUSTIFY THE TOPOLOGY, so this is not over-rotated either: a model that genuinely exceeds one host (DeepSeek-V4-Flash work is referenced in the systemd drop-in comments), or several large models required RESIDENT SIMULTANEOUSLY. Neither is true on this fleet today, so neither should be assumed in either direction.

METHOD LESSON, and it is the same one as C1: a fit-gate refusal is a reading of the machine AT THAT MOMENT, including whatever else was resident. Do not promote it to a property. Before citing "X does not fit", check the file sizes and free memory, and say which quant.
