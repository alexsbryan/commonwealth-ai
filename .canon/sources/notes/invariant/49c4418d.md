# Flat-file daemon stores (lint_results.db, test_results.db, notes.db, features.db) live at sovereign_root, not sovereign_indexes — daemon…

Flat-file daemon stores (lint_results.db, test_results.db, notes.db, features.db) live at sovereign_root, not sovereign_indexes — daemon writes there, CLI must read there, or you get stale-orphan-DB symptoms

`~/.sovereign/lint_results.db` (and `test_results.db`, `notes.db`, `features.db`) is the canonical path. `sovereign daemon run` writes there via `config.data.dir = ~/.sovereign/`.

`~/.sovereign/indexes/` is only for per-project LanceDB SCIP indexes — `<corpus-id>/` subdirs.

Why: `sovereign tools call lint_status` was reading `~/.sovereign/indexes/lint_results.db`, an orphan DB from Apr 21 with NULL finished_at rows, so it reported `status: "running"` indefinitely while the daemon's actual store had fresh `exit_code=0` runs. The orphan never caught up because nothing writes to it. Fixed in `tools_cmd/registry.rs` by routing flat-file stores through `sovereign_root()` (= `~/.sovereign/`), keeping `data_dir` only for the LanceDB engine.

How to apply: when adding a new flat-file store to the standalone CLI registry, resolve via `crate::util::dirs::sovereign_root()` not `default_data_dir()`. If a sovereign-tool reports `running` indefinitely, check whether it's reading from the daemon's path — `lsof ~/.sovereign/lint_results.db` to see what process actually holds the live DB.
