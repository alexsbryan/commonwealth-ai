# A PER-NOTE AUTHOR MARKER RENDERS ONLY WHEN IT WOULD CHANGE THE READER'S MIND — use NodeAttribution::marker_compact(), never…

A PER-NOTE AUTHOR MARKER RENDERS ONLY WHEN IT WOULD CHANGE THE READER'S MIND — use `NodeAttribution::marker_compact()`, never `label_compact()`, on a per-note line (fixed 2026-08-07, regression shipped in a8e10be6).

WHAT SHIPPED BROKEN. `brief.rs::render_notes` printed `label_compact()` unconditionally, and `NoteStore::attribution()` returns `Unknown` for EVERY row when no roster is wired — not just for rows lacking an origin. `sovereign code brief` opens a bare store and `sovereign-cli` structurally cannot depend on `sovereign-mesh`, so no roster is ever wired on that path. Result: every note line read `- **[decision]** _?_ …`. MEASURED, not inferred: `sovereign code brief --hours 48` at a8e10be6 gave 15 of 15 lines marked `_?_`, including peer-written notes whose `origin_node_id` was populated and correct. After the fix, 0 of 15. That is the inverse of the feature — a marker on every line names nobody.

THE RULE, now encoded in `NodeAttribution::marker_compact() -> Option<String>`:
- `Peer` → render. This is the whole point: the note may be about a machine that is not yours.
- `Ambiguous` → render. Not missing provenance — a roster that cannot answer, which is a real warning.
- `SelfNode` → None. The boot hook already told the session which machine it is.
- `Unattributed` / `Unknown` → None. Nothing a reader can act on.
Same rule `.claude/hooks/inject-notes.py::author_tag` applies; it reads the `as_str()` discriminant rather than re-deciding, so the two densities cannot drift (§10.6).

`label_compact()` still exists and is still correct for surfaces that HAVE an id and must print something — a work-in-flight claim always carries a node, and `(?)` there is worse than the raw id. `Unknown` now keeps a truncated id for exactly that reason.

WHERE ATTRIBUTION ACTUALLY WORKS. The daemon wires the roster (`daemon_cmd/mod.rs:592`, next to `set_origin_node_id`), so the daemon-served brief and the MCP `notes` tool do name peers. The CLI brief never will. That is a structural gap, not a bug — and it means `sovereign code brief` gives no cross-machine signal at all. If that matters, the fix is to serve the brief from the daemon or to hoist the roster reader somewhere `sovereign-cli` can reach; neither is scoped yet.

PROCESS LESSON. The snapshot test `snapshot_small_feature_branch_with_notes` caught this at the moment of the change and was re-blessed with `UPDATE_SNAPSHOTS=1` instead of investigated. A snapshot diff that ADDS a marker to every line is the finding, not the noise.
