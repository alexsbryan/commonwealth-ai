# THE GIT INDEX IS SHARED MUTABLE STATE ACROSS CONCURRENT WORKER SESSIONS. Staging and committing must not straddle two shell invocations…

THE GIT INDEX IS SHARED MUTABLE STATE ACROSS CONCURRENT WORKER SESSIONS. Staging and committing must not straddle two shell invocations while peer workers are live, or your commit will sweep up whatever they staged in the window.

OBSERVED 2026-08-14, order gate-tombstone-ladder, commit 94a66d7e. Sequence:
  call 1: git reset; git add <my 5 files>; git apply --cached <filtered hunk>;
          git diff --cached --stat  -> verified EXACTLY 5 files / 310 insertions
  call 2: git commit -F msg          -> committed 16 files / 854 insertions
Between the two calls the drafter-attribution-discipline worker ran `git add` on its own slice into the same .git/index. `git commit` with no pathspec commits THE INDEX, so my commit carried its entire slice (formatters.rs, prompts.rs, corpus_search.rs, retrieval/mod.rs, raptor_grounding.rs, streaming.rs, types.rs, plus three bench/doc files) under my message. Its own follow-up commit then carried only the leftover doc hunk under a message describing everything I had already swallowed. Net content was complete and correct; both commit messages misdescribed their trees.

WHAT DID NOT CAUSE IT, so nobody re-diagnoses this: not a hook (.githooks/pre-commit is a warn-only rustfmt advisory that stages nothing), not the hunk-filtering (`git apply --cached` was correct and verified), not a bad pathspec. The verification was TRUE WHEN RUN and false 30 seconds later. A `git diff --cached` check is not a guarantee unless the commit is in the same atomic step.

THE FIX — use a PRIVATE INDEX whenever peers are live:
  export GIT_INDEX_FILE=/tmp/myindex
  git read-tree HEAD
  git add <paths>            # and/or git apply --cached <filtered.patch>
  git diff --cached --stat   # verify
  git commit -F msg          # commits the private index; .git/index untouched
This isolates you completely from sibling `git add`s AND leaves their staging intact. It is the only approach that also supports partial-hunk staging.
If you do NOT need partial-hunk staging, `git commit --only -- <paths>` is simpler and is race-proof against extra staged files (it commits only the named paths).

RELATED, and the reason the plain pathspec habit is not enough here: the workspace's pathspec-commit trap note (37f84703) covers a file whose WORKTREE holds more than your slice. This is the other axis — a file that is not yours at all, entering your commit through the INDEX. Both are live when multiple workers share one checkout; the private index closes both.

DETECTION: after committing, `git show --stat --format="" HEAD` and compare the file count to what you staged. A mismatch means you swept a peer. Do this before reporting a hash.
