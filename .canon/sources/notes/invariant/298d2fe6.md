# AN EMPTY RETRIEVED PASSAGE GRADES AS "NOT COVERED" AND READS AS "THE CORPUS DOES NOT HOLD IT" — A FALSE VERDICT THAT PASSED BOTH INSTRUMENT…

AN EMPTY RETRIEVED PASSAGE GRADES AS "NOT COVERED" AND READS AS "THE CORPUS DOES NOT HOLD IT" — A FALSE VERDICT THAT PASSED BOTH INSTRUMENT CONTROLS (2026-08-26). Extends e512e1b8 and 8e09ef75. The generalisable part is the last section; read that even if the lane is irrelevant to you.

=== THE FALSE RESULT ===
R1 coverage run 1 completed clean and reported: r = 0.0 on all 60 items, every domain 0.0, coverage 1.0, both controls PASS, verdict KILL_RETRIEVAL_TO_10, oi_ceiling -10.0. It looked like a decisive finding — wikipedia holds none of the AA bank — and it was wrong.

59 of 60 items had ZERO wikipedia chunks in the graded passage. The judge was reading an EMPTY STRING and answering B, correctly, sixty times.

=== ROOT CAUSE: TWO KNOBS, NOT ONE ===
`chat inspect` unscoped returns 38-40 corpora per query on this host. WIKIPEDIA IS USUALLY NOT AMONG THEM — measured, 1 of 60 queries. So the design assumption "one unscoped retrieval gives me the scoped cut for free by post-filtering `corpus_id == wikipedia`" is FALSE, and it fails silently, yielding an empty chunk list rather than an error.

`chat inspect --corpus wikipedia` returns wikipedia with 10 chunks every time. RETRIEVAL SCOPE AND SELECTION SCOPE ARE SEPARATE CONCERNS: you must ASK for the corpus (`--corpus`), not filter for it afterwards. coverage.py now has both knobs, `--inspect-scope` (what to ask for) and `--scope` (what to select within the answer), because they are genuinely different questions.

=== WHY BOTH CONTROLS MISSED IT ===
This is the part worth carrying elsewhere. The instrument had a negative control (shuffled context -> require NOT COVERED: 30/30 PASS) and a positive control (plant the fact -> require COVERED: 58/60 PASS). Both passed while the real grading measured nothing.

The negative control passed because an empty passage is a *correct* NOT_COVERED — it tests the judge's willingness to say B, and an empty passage makes that trivially right.

The positive control passed because it FELL BACK: `top_chunks(scoped) or top_chunks(unscoped)`. That one `or` meant the control planted its fact into a NON-EMPTY unscoped passage while real grading read an EMPTY scoped one. IT VALIDATED THE JUDGE ON CONTEXT THE MEASUREMENT NEVER SAW. A convenience fallback in a control is not a convenience — it silently decouples the control from the thing controlled. The fallback is now deleted; an empty scoped cut records `no_context` in the control too.

=== THE STRUCTURAL FIX, AND THE GENERAL RULE ===
NO_CONTEXT is now its own outcome, never NOT_COVERED. It is not graded, it drops `coverage` below 1.0, and `summarize` then refuses to emit r at all. Verified by regrading run 1's exact contexts through the fixed code: n_graded 1, no_context 59, coverage 0.017, r None, verdict COULD_NOT_JUDGE, exit 4. The false verdict becomes a refusal on identical input.

GENERAL RULE: A CONTROL PAIR TESTS THE JUDGE, NOT THE PIPELINE FEEDING IT. Passing both directions proves the grader discriminates; it proves nothing about whether the grader was handed the right input, or any input. Every measurement over assembled context needs a third, cheaper check that the ASSEMBLY is non-degenerate — passage non-empty, right source, plausible length — asserted before the judge is called and surfaced in the summary as its own count. Absence of input must be reported as absence (§18.3), never allowed to flow through a scoring function that has a defined output for it.

Corollary for review: any expression of the form `preferred or fallback` on the input path of an instrument deserves suspicion. Ask what it means when the fallback fires, and whether the number would still mean what its name says.
