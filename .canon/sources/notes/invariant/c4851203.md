# SEQ_LEN 1024 SILENTLY TRUNCATES 92.5% OF ORPO PROMPTS AND DIVERGES THE RUN TO NaN — THE GATE COMMAND IN HALO_HANDOFF §4 TRIPS THE TRAP ITS…

SEQ_LEN 1024 SILENTLY TRUNCATES 92.5% OF ORPO PROMPTS AND DIVERGES THE RUN TO NaN — THE GATE COMMAND IN HALO_HANDOFF §4 TRIPS THE TRAP ITS OWN §7 WARNS ABOUT. Root-caused 2026-08-02 on gfx1151, verifier-v0.

MECHANISM. `train_orpo_trl.py` sets `max_prompt_length = seq_len // 2` (TRL honours it; MLX had no such knob, which is why this was inert on the Mac). seq 1024 therefore caps prompts at 512 tokens. Measured against `data/orpo-probe` with the model's own tokenizer, n=400: p50 819, p90 1251, max 1758.
    prompt cap  512 (seq 1024): 370/400 = 92.5% TRUNCATED
    prompt cap 2048 (seq 4096):   0/400 =  0.0% truncated

FOUR RUNS, ONE VARIABLE:
    seq 1024, accum 1,  5 steps -> healthy, loss 1.63->0.81, gate PASS
    seq 1024, accum 1, 25 steps -> NaN at step 11, gate DIVERGED
    seq 1024, accum 8, 15 steps -> NaN at step  2, gate DIVERGED
    seq 4096, accum 1, 15 steps -> clean, grad_norm 1.9-5.8, gate PASS max|B| 8.005e-04

REFUTED HYPOTHESIS, RECORDED SO IT IS NOT RE-TRIED: I first blamed effective batch 1 (ORPO's log-odds term at its noisiest) and predicted a larger batch would stabilise it. Raising accum to 8 made it diverge SOONER — step 2 instead of 11 — because each optimizer step then averages eight truncated examples instead of one. Sequence length was the variable; batch size was not.

CONSEQUENCE. `launch_gradcheck.sh` now defaults to SEQ=4096, ITERS=15, `--grad-checkpointing` (free on this box, holds peak to 20.3 GB at 7.2 s/it). Never gate at seq 1024. A gate must not run a config the real training never uses — it can only produce failures the real run would not have, or pass on data the real run would not see.

SECOND INVARIANT: FIVE STEPS IS A LIVENESS CHECK, NOT A STABILITY TEST. The 5-step run passed one step before the identical config went NaN. Five steps proves B leaves zero. Default is now 15.

M0 AND THE MIX STUDY ARE UNAFFECTED — both run at seq 4096. `findings/truncation_report.json` already established 4096 as the safe cap (Stream A 0.017%, Stream B 0.000% over).
