# Symptom. Intermittent iroh bridge: dial failed … error 120: peer doesn't support any known protocol against a peer that is SIMULTANEOUSLY…

Symptom. Intermittent `iroh bridge: dial failed … error 120: peer doesn't support any known protocol` against a peer that is SIMULTANEOUSLY reachable (`gossip: reach ok` to the same node id, 50-600ms). Downstream: RPC-worker discovery ticks intermittently see zero workers, worker-eligibility flaps, the anchor profile quarantines on the first flap, `reload_primary` fires, and distributed placement collapses to `mode=local`. A reload can land mid-request and return an empty completion body.

Root cause (confirmed 2026-07-26 by instrumenting the dial site). `sovereign-cli-daemon` and `sovereign-server` running on the SAME machine both derive their iroh secret from `commonwealth_transport::identity::load_or_generate_node_key`, so both publish the SAME Ed25519 pubkey. Their ALPN sets differ:
- `sovereign-mesh/src/iroh_access.rs:270-273` — daemon advertises `cwth/http/0` + `cwth/client/0` (+ `cwth/rpc/0` when SOVEREIGN_RPC_SERVE is set).
- `sovereign-server/src/iroh_access.rs:87` — server advertises ONLY `vec![CLIENT_ALPN]` = `cwth/client/0`.

A dialer resolving that pubkey can land on either endpoint. Landing on the server rejects every `cwth/http/0` and `cwth/rpc/0` dial. It is a coin flip, which is why it presents as flakiness rather than a clean failure. Killing the server process made the error-120 rejects stop immediately.

Diagnosis requires the ALPN. The `iroh bridge: dial failed` warn in `commonwealth-transport/src/iroh.rs` (HttpBridge::spawn) did NOT log which ALPN was refused, so "peer lacks a ggml rpc-server" and "peer rejects internal HTTP" were indistinguishable — both read as a generic dial failure and sent us hunting the RPC path for an hour. Added `alpn = %String::from_utf8_lossy(alpn)` to that warn; it immediately printed `alpn=cwth/http/0`, disproving the RPC hypothesis in one line. KEEP THAT FIELD.

How to apply. Before debugging an ALPN reject as build skew or an RPC problem, run `ps -eo pid,command | grep -E "sovereign-server|svrnmesh|sovereign-cli-daemon"` on the PEER. More than one sovereign process sharing a data dir = identity collision. Either stop the extra process, or give it a distinct identity via `[iroh] key_path` (`key_dir_and_path`, `sovereign-server/src/iroh_access.rs:34`) — the loader owns the file name `node_key`, so it must be a different DIRECTORY, not a different file name.

Open. Nothing detects or refuses this at startup. Two same-key endpoints with different ALPN sets is always a bug; a startup check would turn a multi-hour flaky diagnosis into a loud one. Directly relevant to cloud/pod images that run both a daemon and a server.
