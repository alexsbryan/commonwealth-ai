ROTATING A JOIN KEY USED TO PARTITION THE MESH, AND THREE GREEN TESTS COULDN'T SEE IT. Root-caused + fixed 2026-08-26/27 on Alexs-MacBook-Pro-2 (branch `mesh-multi-membership`). Confirms the symptom RuggedFox filed in note 1310b225 ("rotate-clobber", symmetric [1/N online] on BOTH sides).

ROOT CAUSE, TWO LAYERS.

(1) `join_key_hash` did DOUBLE DUTY: the invite credential (`accept_join_with_identity`) AND the gossip auth predicate (`Mesh::merge_from` rejected on mismatch). So re-keying admission also re-keyed gossip. Every peer still holding the old hash rejected the rotator and was rejected by it — symmetric partition, no error anywhere.

(2) `persist::rotate_join_key` wrote the new hash to DISK ONLY and never touched the live `Mesh`. The gossip loop re-persists the in-memory mesh over `mesh.json` every round (gossip.rs, the `persist::save` call), so within ~10s the rotation was silently REVERTED while `join_key.secret` kept the NEW plaintext. The operator was left holding an invite that hashed to nothing the mesh accepts. Three callers each did a different partial job (CLI: disk only; HTTP: + plaintext cache + node-local TTL; desktop: bypassed EmbeddedDaemon entirely) — the §10.6 duplicated-decider failure.

WHY THE TESTS WERE GREEN. `rotate_after_create_changes_join_key_hash` and its two siblings all read `join_key` — the plaintext the handler ITSELF just returned, a verbatim echo of the value under test. None read `AppState.inner.mesh.invite_key_hash`, the state that actually gates admission. Textbook ARCH §18.1 "assert on something the subject cannot author" (same shape as the SSE `model` echo, a6ca12aa).

THE FIX. `Mesh` now carries `mesh_secret` (gossip auth, minted at creation, NEVER rotates — `rotate_invite_key` cannot name the field) and `invite_key_hash` (admission, rotates freely). Rotation is structurally incapable of partitioning. One implementation: `EmbeddedDaemon::rotate_invite`, which mutates the LIVE mesh first then persists from it, so disk and memory agree and no gossip round has anything to revert. Refuses 409 `PreSplitPeersOnline` while an un-upgraded peer is online (`--force` overrides) rather than dropping it quietly (§18.3).

MIGRATION IS DETERMINISTIC ON PURPOSE. `derive_legacy_mesh_secret` = blake3 derive_key("cwth-mesh-secret-v1", mesh_id || invite_key_hash). A RANDOM secret would need a gossip round to agree on, and during that round half the mesh rejects the other half — reintroducing the exact failure. Every node computes the same 32 bytes independently from state already on disk.

THE TRAP THAT ALMOST SHIPPED. There are FOUR `Mesh` wire mirrors: `commonwealth-api/routes_internal/mesh_admin.rs`, `sovereign-mesh/src/join.rs`, `sovereign-mesh/src/gossip.rs`, and the test mirror in `commonwealth-api/tests/gossip_route.rs`. I renamed the field and added `#[serde(rename = "join_key_hash")]` to three. Missing it on gossip.rs made every gossip round 422 — LOUD, caught by two round-trip tests. But that same mirror also DROPPED `mesh_secret`, and that half is SILENT: gossip keeps working while zeroing every peer's secret on arrival, pinning the whole fleet to the compat arm permanently with nothing red. A wire type that drops a security field is more dangerous than one that fails to parse.
