THE GR FAMILY'S 0-CANDIDATE YIELD WAS AN INSTRUMENT DEFECT, NOT ABSENT COVERAGE. Measured 2026-09-01, same 250 (requirement, test) pairs, generator v1 vs v2: 1 candidate -> 62, and 32 of 50 GR requirements reached vs 1.

WHAT THE FIRST PROBE ACTUALLY MEASURED. scripts/conformance-candidates.py v1 counted every rejection into ONE `skipped` counter and reported "0 of 250". A single counter cannot separate the honest finding (the model read the test and reports its assertion is not this clause) from the instrument failing to express a candidate at all -- and those two send the campaign in OPPOSITE directions: write coverage, or fix the extractor. The banked frame read it as the former. Bucketing the rejections (v1 trace, test-artifacts/gr-trace-v1-baseline.jsonl) showed it was half the latter:
  no-such-coverage 122 | test-code 88 | find-absent 14 | target-missing 10
  find-ambiguous 9 | no-json 3 | bad-json 2 | daemon-error 1
127 of 249 rejections were the pipeline, not the codebase.

THE CAUSE, AND IT WAS IN THE PROMPT'S INPUTS, NOT ITS WORDING. v1 showed the model ONLY the test source (42 lines) and then asked it to mutate "the code this test exercises" -- code it had never been shown. So it mutated what it could see (test-code, 35% of all rejections) or invented a snippet for a file it could not see (find-absent + target-missing, 10%). The prompt forbade both in words and was ignored, which is the §7.6 rule: never ask a model to guarantee what code can enforce.

THE FIX WAS ENTIRELY INVENTORY (principle 11). Resolve the production function under test and put its SOURCE in the prompt, with the one legal target enforced after the answer. v2 buckets on the identical 250 pairs: no-such-coverage 148, no-code-under-test 34, find-absent 2, find-ambiguous 1, no-json 1, bad-json 2. test-code and target-missing went to ZERO.

THREE TRAPS FOUND WHILE BUILDING IT, each of which would have read as "no coverage":
1. `callees` ANSWERS TODAY AND WILL REFUSE TOMORROW. routes_mcp handle_tools_call gates on is_mcp_exposed; `callees` left the surface on 2026-08-31 (uncommitted), so the RUNNING daemon still serves it and a rebuilt one will not. A generator built on it returns nothing after the next daemon build, and nothing is recorded as no-code-under-test. Dependency not taken: call sites come from a local regex over the test body, `symbols` (still exposed) resolves them.
2. THE `[kind]` MARKER IN symbols' HEADER IS NOT STABLE. The same symbol returned `[function]` and, minutes later while the index re-enriched, `[unknown]`. Gating on kind rejected every candidate and looked exactly like "nothing resolves". Gate on the SOURCE instead: a real definition contains `fn <name>(`.
3. "IS THE TARGET A DIFFERENT FILE FROM THE TEST?" IS THE WRONG QUESTION and rejected every correct target. Production code and its `#[cfg(test)] mod tests` share one .rs file here (quote_verification.rs holds both). Position in the file is the right question: the target is defined ABOVE the `#[cfg(test)]` line.

COST NOTE: `svrn tools call symbols` via the CLI dispatcher is ~37s per call; the same call over the daemon's /mcp tools/call is ~2s. 18x, and it is the difference between a viable generator and a 3-hour one.

STILL UNPROVEN: 62 candidates are PROPOSALS. scripts/sabotage.py is ground truth and has not adjudicated them; a wrong candidate SURVIVES its mutation and is discarded, which is why this stage needs recall and not precision.
