A HARNESS-REAPED RELEASE LEG LEAVES THE PODMAN CONTAINER RUNNING — COMPILE OUTPUT WITH NO PACKAGING, PROVENANCE OR UPLOAD (2026-08-29, v0.6.0 release, RuggedFox Linux x86_64).

WHAT HAPPENED. `scripts/release-cli-local.sh` was launched as a tracked background task and the harness reaped the wrapper ~2 min in, mid-compile of corpus-engine. Not an OOM: nothing in the journal for the kill window, and the operator confirmed they were not touching the machine. The podman build container OUTLIVED the wrapper and kept compiling for several minutes as an orphan — podman containers run under conmon, detached from the invoking shell, so killing the script does not kill the build.

WHY IT MATTERS. The orphan produces compile output and nothing else. Every step that makes a release leg a release leg — packaging, the .buildinfo sidecar, the provenance gate, the upload — lives in the wrapper and dies with it. The observable state afterwards is "a container ran and the target dir has fresh objects", which reads as "the leg ran" while shipping nothing. That is this codebase's characteristic failure (ARCH §18): a plausible, well-formed, exit-0-shaped result that is wrong.

THE FIX IS STRUCTURAL, NOT A RETRY. Launch under `setsid` so the script is its own session leader and survives the reap:

    setsid nohup ./scripts/release-cli-local.sh > ~/release-logs/<tag>.log 2>&1 < /dev/null &

Note `$!` is then the launcher PID, not the script's — setsid forks. Find the real one with `pgrep -af release-cli-local`, and wait on it with `tail --pid=<pid> -f /dev/null`. Nothing is lost by a reap either way: the container mounts the repo at /work, so compile progress persists in the target dir and a relaunch resumes warm. The second attempt built in 8m10s.

DIAGNOSIS ORDER THAT WORKED. `podman ps` FIRST — an "Up N seconds/minutes" container after a killed wrapper is the tell. Then rule OOM in or out (journalctl for the window, /proc/vmstat oom_kill) before assuming memory. `dmesg` needs privileges here and returns "Operation not permitted", so it is not the instrument to reach for.

THE SAME THING HIT THE MAC PEER about an hour later on its macOS desktop legs; it relaunched under a launchd one-shot. On that host the processes DID die with the wrapper — no orphan — so the orphan half is podman-specific, while the reap itself is not.

RELATED, SAME RELEASE: stop the resident daemon before a container leg (it held ~11GB; swap was fully exhausted at 8.0G/8.0G before the stop, 20GB free after). Operator authorization for that is standing per-release, not blanket.
