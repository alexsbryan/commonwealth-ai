# NEVER READ AN RPC DEVICE'S MEMORY FROM A REQUEST HANDLER — ggml_backend_dev_memory ROUND-TRIPS TO THE WORKER AND A BUSY WORKER NEVER…

NEVER READ AN RPC DEVICE'S MEMORY FROM A REQUEST HANDLER — `ggml_backend_dev_memory` ROUND-TRIPS TO THE WORKER AND A BUSY WORKER NEVER ANSWERS (introduced and fixed 2026-07-30, sovereign-inference `last_device_memory`).

WHAT I BROKE. To publish per-device free memory on `/v1/mesh/status`, I called a `live_device_memory()` that sampled every placed device via `ggml_backend_dev_memory`. For a LOCAL device that is a cheap register read. For an RPC device it is a synchronous network round-trip to the remote rpc-server. It tested fine — because I tested it while the worker was idle.

THE FAILURE. Once the distributed 122B child was serving, BeefyMac's rpc-server was busy decoding and stopped answering the parent's GET_DEVICE_MEMORY. `/v1/mesh/status` went from ~2 ms to hanging past 70 s (curl exit 124). That endpoint is how `svrn mesh bench` identifies the mesh, so the bench died with "daemon not reachable" while the daemon was perfectly healthy and answering `/status` 200. A blocking FFI call inside an async axum handler also starves the tokio worker thread, so the damage is not limited to the one request.

THE FIX — CACHE THE LOADER'S READING, NEVER SAMPLE ON DEMAND. `placed_devices()` already reads per-device memory on the load path, where the cost is already being paid and the worker is not yet busy. It now writes that reading into a process-global `DeviceMemorySnapshot { observed_unix, devices }`; `last_device_memory()` returns the cached snapshot and does ZERO FFI. Status handler latency under a resident 122B: 7.8 ms.

WHY THE CACHED VALUE IS ALSO MORE CORRECT, not a compromise: "the memory the loader saw when it chose this cut" is precisely what EXPLAINS the cut. A fresh sample describes a moment the load never saw. The snapshot carries `observed_unix` and `mesh plan` prints the age ("free-memory reading observed 393s ago, when the loader last planned a cut"), so a stale figure cannot pass as current.

THE GENERAL RULE: before putting a value on a status/health endpoint, ask whether producing it can block on a REMOTE or CONTENDED resource. If it can, publish a timestamped observation captured where the work already happens. A status endpoint that can hang is worse than one that omits the field — it takes down every consumer that reads it, and the failure names the wrong culprit ("daemon not reachable").

SMELL THAT WOULD HAVE CAUGHT IT: an `unsafe` FFI call in an async handler, guarded only by a comment claiming it is cheap. The comment said "Cheap FFI, no model touched. Safe to call per request." It was wrong about exactly one device class, and that class only misbehaves under load.
