# Pull-side merge leader emits on behalf of the peer; aggregator credits kind.from_node, not event.node_id

Pull-side merge leader emits on behalf of the peer; aggregator credits kind.from_node, not event.node_id

`LedgerEventKind::ShardTransferred` carries explicit `from_node` AND `to_node` fields (not just `to_node` like the other variants). The reason: the merge leader pulling shards from peers is the only side that observes the transfer completing, so the leader has to emit on the peer's behalf.

Aggregator special case (`commonwealth-core::contributions::aggregate`): for `ShardTransferred`, the emitter (`event.node_id`) is ignored for accounting. `bytes_served` lands on `kind.from_node` and `bytes_received` lands on `kind.to_node`. Every other variant credits the emitter.

Why: the legacy push path (`ShardManager::stream_index`) had emitter == sender; that semantics still works (just set `from_node = self_node_id` at emit time). The pull path emits with `from_node = peer.node_id` so the aggregator credits the actual sender.

Don't "simplify" by going back to `to_node`-only and using `event.node_id` as the sender. That would silently drop every pull-side emission's bytes_served onto the wrong node.

Test that pins this: `commonwealth-core::contributions::tests::pull_emitted_shard_transfer_credits_actual_sender`.
