QWEN3.5 ORPO TRAINING ON gfx1151 CANNOT BE SUSTAINED: GTT RATCHETS PAST 100 GB AND THE RUN IS OOM-KILLED AROUND STEP 63. Short probes CANNOT see this. Measured 2026-08-02, Strix Halo, sovereign-rocm-7.2.4.

Supersedes e643e089. Its causal-conv1d conclusion still holds verbatim (below); its "fla only ... ~25 GB GTT <- USE THIS" line was a SHORT-PROBE ARTIFACT and is corrected here.

THE NEW FINDING. The recommended fla-only config ran 61 clean steps at a rock-stable 176.71 s/it, then died at step 63 with PROBE_RC=137. GTT over the run: ~25 GB (steps 1-50) -> 51 GB (step 62) -> 99 GB -> 103 GB -> SIGKILL. On exit GTT fell to 21 GB, so the ~80 GB was the trainer's, not a co-tenant's (only pid 2741374 held GPU fds; verified via /proc/*/fd).

WHY SHORT PROBES MISSED IT: the earlier sweep measured 3-4 steps and the longest prior run was 25 steps. The ratchet does not become visible until ~step 50. Any future memory claim about this stack MUST be qualified by the step count it was measured over.

THE TENSOR WORKING SET NEVER GREW. torch's own gpu_peak_gb sat FLAT at 29.34 GB from step ~10 to death while GTT tripled. So this is allocator/driver RESERVE and fragmentation, not a tensor leak. `PYTORCH_ALLOC_CONF=expandable_segments:True` is set in launch_m0_probe.sh but torch logs "expandable_segments not supported on this platform" at startup on ROCm/gfx1151 — so the allocator cannot compact, and it ratchets as progressively longer sequences appear.

UNTESTED MITIGATION (the one experiment that could overturn the sustainability verdict): a TrainerCallback calling torch.cuda.empty_cache() every ~10 steps, to cap reserve growth. Costs a ~5 h run to test. NOTE it would NOT change the role assignment — the Halo is also 3.33x slower than the M2 Max (176.7 vs ~53 s/it), i.e. 4.8 days per orpo-76k epoch, so it is not the training box either way. Do not spend the 5 h unless someone specifically wants to train on the Halo.

A SIGKILL BYPASSES THE TRAINER'S try/except, so summary.json is NEVER written on an OOM even though the script is otherwise careful to write it on error/interrupt. steps.jsonl survives (flushed per step) and is sufficient to reconstruct everything. The dying step's step_s is PARTIAL (70.7s here vs a 176.7 median) and MUST be excluded.

CARRIED FORWARD FROM e643e089, UNCHANGED — INSTALL flash-linear-attention, NEVER causal-conv1d. transformers gates on `is_fast_path_available = all(...)` over four symbols. fla only -> three of four resolve -> SEQUENTIAL path. Add causal-conv1d -> all four -> CHUNKED path -> ~100 GB immediately, at step 1. Measured, eff batch 32 / seq 4096 / micro 1 / grad-ckpt:
- no fla ......................... 231.8 s/it   (eager torch deltanet)
- fla only ....................... 176.7 s/it   <- still the best available config
- fla + causal-conv1d ............ dies at step 1, ~100 GB
The chunked path is genuinely FASTER per step (144.1s vs 178.0 at step 1); it simply cannot fit. Ignore the "fast path is not available" warning — it fires if ANY of the four is missing and the expensive deltanet recurrence is already on fla's Triton kernels. The trainer now records `deltanet_path` in its env dump so this stops depending on a warning string.

ALSO CARRIED: causal-conv1d IS buildable here (ROCm 7.2.4 dnf repo configured; hipcc compiles it clean for gfx1151) — the old "no ROCm compiler" framing was wrong. `torch.cuda.max_memory_allocated()` does NOT see GTT reserved outside PyTorch's allocator; ALWAYS cross-check /sys/class/drm/card1/device/mem_info_gtt_used. `LD_PRELOAD=/opt/rocm/lib/libhsa-runtime64.so.1` or every GPU op SEGVs (note b18dacf9).
