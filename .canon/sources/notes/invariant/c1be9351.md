GOSSIP MUST REUSE ONE PROCESS-WIDE reqwest::Client — A PER-ROUND CLIENT COSTS A FULL QUIC HANDSHAKE PER PEER PER ROUND (fixed 2026-07-29, sovereign-mesh/src/gossip.rs `gossip_client`).

THE MECHANISM. A `reqwest::Client` owns its connection pool. `run_one_round` (and 2 sibling sites: the anti-entropy round and `broadcast_now`) built a client INSIDE the function, so the pool died with the round. Every round therefore opened a NEW TCP connection to the peer's local iroh bridge — and `HttpBridge::spawn` (commonwealth-transport/src/iroh.rs:376) dials a **fresh `endpoint.connect()` QUIC connection per accepted TCP connection**. Gossip paid a full QUIC handshake to every peer, every round, forever, and never benefited from an established path. Confirmed structurally (TIME-WAIT churn on the bridge port: 4 sockets per 60s TIME-WAIT window at a ~13.5s round cadence = exactly 1 new connection per round, 0 ESTABLISHED).

THE `dial failed … error=timed out` WARNING IS THIS. It is one round's handshake giving up — not a peer going away. That is how selection-independent staleness crept back in even after `select_round_peers` was made deterministic (see the staleness-ordering invariant): deterministic SELECTION does not help if the CONTACT itself is a coin flip on a fresh handshake.

MEASURED, concurrent A/B over one identical 3-minute window, RuggedFox → BeefyMac over iroh, healthy idle LAN (raw TCP RTT to the same host p50 6.9ms, zero loss over 30 probes; link idle at 11-31 KiB/s):
  fresh client per round (production): n=11 min=68  p50=189.0  p90=1327  max=2273 ms, 2 dial timeouts
  reused connection (warm probe):      n=18 min=6.4 p50=38.8   p90=391   max=1227 ms, 0 dial timeouts
A warm round reaches 6.4ms — the raw LAN RTT — because it does no handshake.

FIX: `gossip_client()` — a `OnceLock<Result<Client, String>>` shared by all three sites. Build failure is TLS-backend-deterministic, so caching the failure is correct, not a lost retry. Guarded by test `gossip_client_is_one_shared_pool_per_process` asserting POINTER identity (two Clients that compare equal would still be two pools).

MEASUREMENT CORRECTION worth keeping: an earlier probe of the same warm path reported p90 2316ms / p99 3967ms and "5% exceed PEER_TIMEOUT". That probe ran at 2 req/s — 20x production cadence — and the tail was substantially SELF-INDUCED. At true production cadence (10s) the warm tail is p90 391ms / max 1227ms with 0/18 over 3s. Do not cite the 2316/3967 figures.

STILL OPEN (residual, not fixed): 4/18 warm rounds still exceeded 300ms and the path to BeefyMac reports `mixed` — 2 active direct addrs AND an active relay (usw1-1.relay.n0.iroh.link) — for a peer 6.9ms away on the same LAN. Riding a US-West relay at all on a LAN peer is unexplained. `PeerTransportPath` (sovereign-mesh/src/iroh_access.rs) exposes only a COUNT of active direct addrs, so we CANNOT tell which addresses are active (LAN <lan-ip> vs Tailscale <tailnet-ip> vs public). That is the next glassbox gap. Tailscale is NOT the culprit for the link itself: TCP p50 was 6.9ms LAN / 9.9ms Tailscale, zero failures.
