THE CODE-INTEL ENRICHMENT IS NOT WHAT EXHAUSTS THE DAEMON'S FILE DESCRIPTORS. One corpus's resident Lance index is.

Measured 2026-08-31 on this host, daemon pid 62772, WITH THE ENRICHMENT STOPPED:
  244 of 256 descriptors held by the daemon alone
  185 of those are indexes/wikipedia/chunks.lance/_indices/*
  ~12 descriptors is therefore all a pass ever had to work in

Count descriptors with `lsof -p PID | awk 'NR>1 && $4 ~ /^[0-9]+[rwu]?/'`. A bare `lsof -p PID | wc -l` reads 268 against a 256 limit because it also counts mmap'd regions, txt and cwd — it is not an FD count and will make you think the limit is already breached.

WHY 256. launchd hands its jobs that soft limit (`launchctl limit maxfiles`) and com.svrnmesh.daemon.plist declares no SoftResourceLimits/NumberOfFiles, so the daemon inherits a budget sized for a shell script. The operator's interactive shell has 1048576, which is why the daemon runs fine in the foreground and dies under launchd — do not read a working foreground run as evidence the config is sound.

WHY THE INDEX STAYS. CorpusEngine::open_index's cache has NO eviction: whatever the query path admits is resident for the life of the process (engine/mod.rs, near open_index_transient). An LRU was considered and REJECTED — an hourly all-corpora sweep is a textbook LRU-flusher and would evict the hot set every tick. open_index_transient exists so background walkers do not populate the cache. So one query against wikipedia pins ~185 descriptors permanently.

LOWERING CONCURRENCY DOES NOT FIX IT. SOVEREIGN_CODE_INTEL_CONCURRENCY 8 -> 4 measured 249/256, no better placed than 8. scripts/code-intel-corpus-run.sh now sets 4 and says in-line that it is politeness, not a repair.

THE FAILURE IS SILENT. On exhaustion: `Too many open files (os error 24)` on installed_indexes and the gossip mesh.json persist, then listener-watch sees the client port stop accepting and exits 104 expecting a service-manager relaunch. The run reported `exit=0` with 3,565 of 4,454 symbols failed and +267 cache entries. Because the enrich plist's KeepAlive is SuccessfulExit=false, a "successful" run that failed 80% of its work is never retried.

RECOVERY GOTCHA. After repeated failed spawns launchd wedges the job in `state = spawn scheduled` with `last exit code = 78: EX_CONFIG` and further `kickstart -k` does nothing. `launchctl bootout gui/$UID/<label>` then `bootstrap gui/$UID <plist>` clears it. Do not diagnose this as a config error — the config is fine.

FIX, NOT YET APPLIED (needs operator): add SoftResourceLimits/NumberOfFiles to com.svrnmesh.daemon.plist, or detach the wikipedia corpus on hosts that never query it.
