# OICP provider.name must reflect the configured chat primary, not whichever advertised slot is largest on disk (2026-05-10 bug).

OICP provider.name must reflect the configured chat primary, not whichever advertised slot is largest on disk (2026-05-10 bug).

Root cause: sovereign-mesh::inference_adapter::build_self_manifest picked provider.name via `.max_by(|a,b| a.size_gb.partial_cmp(&b.size_gb))` across all advertised slots. When the user swapped the chat primary to FINAL-Bench_Darwin-36B-Opus-Q6_K (~28 GB) while keeping Qwopus3.6-35B-A3B-v1-Q8_0 (~34 GB) in the code slot, the max-by-size heuristic selected Qwopus3.6. Peers querying /oicp/v1/capabilities saw provider.name=Qwopus3.6, so mesh attribution and capability scoring routed/labelled requests against the code model identity.

Fix: replace the size-based heuristic with `resolve_primary_model_name(provider)` (defined ~60 lines above in the same file) which returns provider.model_id_for(Speed::Slow), falling back to Fast then 'sovereign-local'. The helper already existed for the response-attribution path; build_self_manifest was the lone outlier.

Regression test added: manifest_provider_name_is_chat_primary_not_largest_slot — uses SlotStub(primary='chat-primary.Q5_K_M', code='huge-code-specialist.Q8_0') and asserts manifest.provider.name == 'chat-primary.Q5_K_M'. Pre-fix this fails (returns the code id).

Applies to ALL future OICP manifest changes. Don't reintroduce 'biggest slot = primary' anywhere — size_gb is for capacity/VRAM comparisons, not primary identification.
