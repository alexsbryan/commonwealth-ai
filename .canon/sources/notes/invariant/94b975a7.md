# Reading memory on the Strix Halo host: three traps, all measured 2026-09-12.

Reading memory on the Strix Halo host: three traps, all measured 2026-09-12.

1. MODEL MEMORY IS NOT IN PROCESS RSS. It lives in amdgpu GTT — read `/sys/class/drm/card1/device/mem_info_gtt_used`. The daemon's RSS read 8.4 GB while GTT held 82.3 GB and the box sat at 116/128 GB used. `ps`, `free` and the daemon's own RSS all understate it by an order of magnitude.

2. `kv_ceiling_mib` IN THE `kv budget: slot context built` TRACE IS AN UPPER BOUND, NOT AN ALLOCATION. Primary (35B) at n_ctx=65536: ceiling 5,248 MiB, actual `llama_kv_cache: Vulkan0 KV buffer size = 1280.00 MiB`. Do not size `[models].context_size` off the ceiling — halving 65536 buys ~640 MiB against an 82 GB footprint, which is not the lever it looks like.

3. `sched_reserve: Vulkan0 compute buffer size = 1039.95 MiB` re-logs on every `mtp: built session at request boundary` (once per turn) and READS LIKE A PER-TURN LEAK. It is not: GTT measured flat at 82.3 GB across 5 turns, and a freshly booted daemon reaches 82.2 GB before load.

Measured boot table, all four slots: primary 36.0 GB, fast 9.4 GB, fast_short 3.1 GB (its 2,249 MiB compute buffer is the n_ubatch=2048 cost), embed 3.8 GB (KV 1,792 MiB at n_seq_max=16 — LARGER than the 35B primary's 1,280 MiB). Total 51.5 GB accounted against 82.2 GB observed; ~31 GB is UNEXPLAINED. The mmap-double-count hypothesis is dead — only 1.1 GB of .gguf appears in `/proc/<pid>/maps`. Open: take a GTT reading with the daemon fully stopped.
