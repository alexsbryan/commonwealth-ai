# Command::output() buffers stdout until child exits — fatal for 25+ minute LLM builds where the operator sees nothing for the full duration.…

**`Command::output()` buffers stdout until child exits — fatal for 25+ minute LLM builds where the operator sees nothing for the full duration. Mandatory pattern: pipe + reader threads + heartbeat.**

When an orchestrator captures a child process's stdout/stderr for
later inspection AND the child can run for more than ~10 seconds,
capture must be line-streaming, not buffered. `Command::output()`
collects everything and blocks until exit — the operator sees nothing
during the run.

Why: The first `sovereign drift detect` run (2026-05-11) sat
silently on "→ building narrative atlas (LLM, ~5-30 min)…" for
90 minutes because `run_step_capture` in
`drift_cmd_orchestrator.rs` used `Command::output()`. The orchestrator
needs the captured output for failure-signature matching (partial-
extract recovery), but the operator needs to see progress in real
time. Both requirements are met by streaming line-by-line into both
parent stdout AND a collection buffer.

How to apply:
- Spawn with `Stdio::piped()` on stdout + stderr.
- Two reader threads, each looping `for line in BufReader::lines()`,
  echo each line to parent's stdout/stderr (`println!` / `eprintln!`),
  send to an `mpsc::channel`. `std::io::stdout().flush()` after each
  print so terminal output isn't itself buffered.
- Main thread `rx.recv_timeout(Duration::from_secs(30))`. On output,
  append to combined buffer. On 30s timeout, print a heartbeat
  `⏱ still in subprocess (quiet for Ns, total Mm:SSs elapsed)` —
  distinguishes a hung child from a slow-but-alive one.
- Channel disconnects (both senders dropped when threads finish) ends
  the loop. Then `child.wait()` collects the exit status.

Reference: `sovereign/crates/sovereign-cli/src/drift_cmd_orchestrator.rs::run_step_capture`
(landed 2026-05-11).

ARCH_PRINCIPLES.md §9.1 is the principle this defends: every
non-obvious decision emits a tracing event. A 90-minute silent
subprocess is the canonical glassbox violation.
