# svrn corpus ingest produces corpora that chat retrieval REFUSES to search.

`svrn corpus ingest` produces corpora that chat retrieval REFUSES to search.

Found 2026-08-13 by the needle rig (order mesh-scale-t2-needle-rig, doc §8.6).

MECHANISM: the shipped `notebook` workflow's `tool:corpus_store` never stamps
`indexes_built`. `mark_indexes_built()` is called ONLY from the bespoke ingest
path (corpus-engine/src/engine/ingest.rs:1709) and from shard promotion
(sharding.rs:1407). So a corpus built by the documented folder-ingest command
lands with `indexes_built: false`.

`corpus_search.rs` Filter 2 (readiness) then drops every such corpus BEFORE the
fan-out — its own comment says "skip it on EVERY path so the model can't
fabricate over the void". Meanwhile `corpus ingest` prints
"✓ Notebook \"<id>\" is searchable — nothing left your machine."

WHY IT IS HARD TO SEE: nothing in the result looks wrong. At n=100 the glassbox
read `fanout_complete corpora=0` and a full 20-chunk evidence pool still came
back from another path, so an eval scored a plausible 11-14% instead of
refusing. Only the `retrieval_audit` fan-out line exposes it. Two full
baselines were computed and thrown away before this was caught.

CHECK BEFORE TRUSTING ANY RETRIEVAL NUMBER over a workflow-ingested corpus:
  grep 'retrieval_audit: fanout_complete' <trace> | grep KnowledgeQuery
and assert `corpora=` equals the installed count (ANSI-strip first — the field
name is colour-wrapped). scripts/needle-rig-baseline.sh does this and exits 4.

RIG WORKAROUND (not a fix): scripts/needle-rig-build.sh stamps the flag after
ingest and reports how many it had to repair, so a real fix shows up as
repaired=0. The real fix is a `mark_indexes_built()` call in the workflow store
path — NOT attempted here; this order was instrument-only, no production code.

Once repaired, selection at n=100 with 99 distinct distractors is 100/100 at
rank 1 — so this defect, not selection quality, was the whole of the first
(discarded) red.
