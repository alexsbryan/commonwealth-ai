lance-linalg 4.0.0 is vendored (patch.crates-io) because upstream build.rs links a never-compiled AVX-512 symbol on cross/emulated x86_64 builds

lance-linalg's upstream build.rs compiles two separate AVX-512 kernel files (f16.c with explicit `-march=sapphirerapids -mavx512fp16`, dist_table.c with `-march=native`) but keys ONE shared `kernel_support="avx512"` cfg off either success. On any build machine where the compiler supports AVX-512 but `-march=native` can't emit it (arm64→x86_64 cross-compile, Rosetta VMs, pre-Zen4 x86), f16 succeeds, dist_table fails, and the final link dies with `undefined symbol: sum_4bit_dist_table_32bytes_batch_avx512`.

Fix (2026-07-10, desktop-v0.1.19): vendored `vendor/lance-linalg` with dist_table pinned to `-march=x86-64-v4`, wired via `[patch.crates-io]` next to [[invariant-llama-cpp-4-vendored]]'s llama-cpp-4 entry in the workspace Cargo.toml. Runtime `SimdSupport` dispatch already gates execution, so the pin is safe on non-AVX-512 CPUs.

How to apply: when re-vendoring a newer lance-linalg, re-apply the one-flag divergence (grep for `x86-64-v4` in vendor/lance-linalg/build.rs). Upstream-proper fix would be separate cfgs per kernel.
