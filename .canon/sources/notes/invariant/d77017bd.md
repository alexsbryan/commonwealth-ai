Svelte 5 keyed {#each} with a duplicate key throws a FATAL each_key_duplicate that aborts the whole component render — looks like an infinite loading spinner

Svelte 5 treats a duplicate key in a keyed `{#each list as x (x.key)}` as a
FATAL error (`each_key_duplicate`) that aborts the ENTIRE component render, not
just the one row. Symptom: data loads fine but the view never paints — looks
like an infinite "Loading…" spinner or a blank pane. Only visible in the
browser/webview console, NOT in backend logs or command timing.

Concrete incident (2026-07-14): desktop Atlas Explore — clicking the
Wikipedia atom `entity-0255` ("2026 Negombo prison riot") hung on "Loading
atom…" for 1+ min. `atlas_get_atom_detail` returned in 492ms (confirmed via
command bridge AND frontend `performance.now()`), but `AtomDetail.svelte`'s
related-atoms list was keyed `{#each detail.related as r (r.atom_id)}` and this
atom has TWO edges to the same neighbour (`entity-37796` at indexes 102+103),
so `atom_id` wasn't unique → each_key_duplicate → render aborted → stuck
spinner. Only atoms with a repeated neighbour hit it, so it looked random.

Fix: key by index — `{#each detail.related as r, i (i)}` (and same for
`cross_corpus`). Correct here because the list is fully rebuilt per atom load,
so index-keying loses nothing. An atom legitimately relates to the same
neighbour via multiple edge_types, so `atom_id` is NOT a valid unique key.

Debugging lesson (load into future sessions): the command bridge
(`SOVEREIGN_COMMAND_BRIDGE=1`) measures the backend command's JSON result — it
CANNOT see render crashes or frontend cost. When the UI hangs but the backend
command is provably fast, instrument the FRONTEND first (console.log +
performance.now around the invoke, read the webview console via Cmd+Opt+I) —
don't keep optimizing the backend. This was the single fastest diagnostic and
should have been step 1. See [[invariant_atlas_edges_json_per_click_reparse]]
for the (separate, real) backend perf fixes found along the way.
