MESH GOSSIP REVERSES EVERY REMOTE NodeId — root cause is ONE line, and it is NOT an identity/precedence bug (diagnosed live on BeefyMac 2026-07-30, both directions confirmed).

SYMPTOM. A measurement record published by node A arrives at node B stamped with A's member id BYTE-REVERSED, so `origin_name` never resolves and `mesh plan` renders "Measured by node-0d83b6c0a0515f46" instead of "Measured by BeefyMac". Confirmed symmetric on the live Meshsonics mesh:
  BeefyMac  member b88252e4325bc377465f51a0c0b6830d -> RuggedFox saw 0d83b6c0a0515f4677c35b32e45282b8
  RuggedFox member 44ae76142b0c3c723051ff98f043104a -> BeefyMac  saw 4a1043f098ff5130723c0c2b1476ae44
Each is an exact 16-byte reversal of the other. Every node runs the same buggy receiver, hence the symmetry.

ROOT CAUSE. `hex_to_node_id` at commonwealth-api/src/routes_app_internal.rs:117 does
  NodeId::from_u128(u128::from_le_bytes(arr))
`NodeId` is a newtype over [u8;16] whose `from_u128` stores `to_be_bytes`, so an LE decode of a BE-encoded array yields exactly `arr.reverse()`. Its ONLY caller is line 63 inside `recv_app_state` (POST /internal/app/state), whose result goes straight into `StoreEntry.origin` and `mesh_store.merge_entry` at line 74 — the sole remote-entry-into-MeshStore write site. FIX = `from_be_bytes`.

This is the lone `from_le_bytes` NodeId decoder in the workspace; headers.rs:33, state/store.rs:205, state/peer_preferences.rs:247 and sovereign-mesh/pinned_transport.rs:156 all correctly use `from_be_bytes`. The encoders are correct (gossip.rs:624 and :786 both `hex::encode(origin.as_bytes())`, verbatim BE). The IDENTICAL bug was fixed in store.rs:191 in commit 3411d495 (2026-04-26) with a regression test (`origin_round_trips_for_realistic_node_id`) — the fix never propagated to this second decoder. Any new NodeId hex decoder must use `from_be_bytes` and be tested with an id whose halves differ; `node(1)` fixtures cannot catch a reversal because Display shows only the first 8 bytes.

DO NOT "repair" this by rewriting a node's `~/.sovereign/node_id` to the reversed value. That corrupts a genuine identity to make one buggy code path render correctly. On BeefyMac the node_id file, mesh.json `self_node_id`, and the member roster all agreed on b88252e4325bc377465f51a0c0b6830d, and the boot log showed `resumed mesh from persisted state` — nothing about local identity was wrong.

NO DATA MIGRATION AND NO RE-BENCH ARE NEEDED. The write side persists origin verbatim and `mesh-measurements.json` stores no origin field at all (origin is stamped at publish/read time), so only the decode was ever wrong. Fix the line, rebuild, restart both daemons, and attribution heals in both directions for records already in flight.

DIAGNOSTIC TRAP: `GET /v1/mesh/measurements?include_self=true` shows THIS node's own records with the correct origin even while the bug is fully live, because self-records never traverse the gossip decode path. Verify against a PEER's records — a peer record with `origin_node` set but `origin_name` missing is the real tell.
