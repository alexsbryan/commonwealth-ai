A `python3 -m http.server` transfer verifies NOTHING unless the payload is checked against an independent committed record. Bytes arriving is not data arriving.

The Halo->Mac Stream B move (2026-08-02) landed a 460-byte SimpleHTTP 404 page saved under `orpo_pairs.jsonl`. It looked like a real file: `ls` showed it, `wc -l` reported 18 lines. The dataset was 19,019 rows / 101 MB. Nothing errored.

CAUSE: `http.server`'s CWD is the URL root. MAC_MIGRATION.md §1 route 2 said `curl -O http://<halo>:8099/orpo_pairs.jsonl`, which only resolves if the server was launched inside `research/verifier-v0/data/stream_b/all/`. It was launched at the repo root, so the real path was `/research/verifier-v0/data/stream_b/all/orpo_pairs.jsonl`.

TWO GUARDS, both cheap:
1. `curl -sI` first and compare `Content-Length` to the bytes on disk. Catches truncation AND 404-as-file.
2. Cross-check content against a record committed from the SENDING box — here `findings/M2_STREAM_B_LABELING.json` (rows, per-corpus, per-kind, per-label all matched exactly). A checksum proves transport; an independent record proves you moved the right thing.

SECURITY: an `http.server` rooted at a repo serves `.git/`, `.sovereign/`, `.config/` to the whole tailnet unauthenticated. That is a far wider surface than the one file, and it is exactly what the `beefymac-ops` allowlist exists to prevent. Serve from the narrowest directory and stop it when the transfer ends.

RELATED: the same doc's §0 "verify you got the right build" check (`train == 74674`) was non-falsifying — the allegedly-stale build reported identical numbers. To compare two decontamination builds, diff the contamination reports' row-id SETS, not their counts.
