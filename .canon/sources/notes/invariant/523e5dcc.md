MACOS `available_memory()` RETURNS EXACTLY 0 UNDER MEMORY-COMPRESSOR PRESSURE — AND THAT 0 WAS BEING ADVERTISED TO THE MESH (found + fixed 2026-08-08 cutting cli-v0.5.0, BeefyMac).

SYMPTOM: `commonwealth-discovery hardware::tests::read_cpu_ram_state_returns_values` fails with
"expected nonzero free RAM" (hardware.rs:368) in a full `--workspace` run — 1 failure out of 9384,
at test 773/9384, in 0.011s. Reproduces in isolation IF run while the compressor is still saturated
from the preceding build/test run; PASSES in isolation once the compressor drains. That combination
is what makes it read like a flake when it is not.

ROOT CAUSE (measured, not inferred — probe printed the raw counters):
  sysinfo 0.35.2 `src/unix/apple/system.rs:200` computes
      mem_available = (free_count + inactive_count + purgeable_count - compressor_page_count)
                      .saturating_mul(page_size)
  The subtraction is on the PAGE COUNT, before scaling. When the compressor holds more pages than
  free+inactive+purgeable, it saturates to exactly 0. Probe on a 64GiB host:
      total=68719476736  available=0  free=3099033600  used=48233152512
  i.e. available==0 while ~30GiB was genuinely available. `total_memory()` and `free_memory()` are
  both fine; ONLY `available_memory()` collapses. Not load-in-the-scheduler-sense — compressor state.

WHY IT MATTERED BEYOND THE TEST: `read_cpu_ram_state()` feeds `build_local_capabilities()` and
`live_available_resources()` in sovereign-mesh (callers depth-2, 8 sites). That is what a node
ADVERTISES as its free RAM. So a Mac advertised 0GiB available precisely when it was busy — the
moment peers most need a real number.

FIX (commit on main, 2026-08-08): new pure fn `resolve_free_ram_gb(available, total, used) ->
(f32, RamSource)` in hardware.rs. Prefers `available` when > 0; when it is 0 on a running host
(an impossible reading, i.e. instrument failure) derives `total - used` and returns
`RamSource::DerivedFromUsed`, which `read_cpu_ram_state` logs at warn! so the substitution is NAMED,
not silent (ARCH §18.3). Both-sources-bad returns `Unmeasurable` rather than a plausible 0.
`total - used` is the durable cross-check because sysinfo counts compressor pages as USED, so the
compressor is accounted once rather than twice; it reaches 0 only on genuine exhaustion.

WHY THE OBVIOUS FIX IS WRONG: do NOT substitute `free_memory()`. free = unused pages only (3.1GiB
on a host with 17.8GiB inactive), so a 64GiB Mac would advertise ~3GiB. Truthful-ish but a large
understatement. `total - used` gave 31.4GiB on the same host.

The decision was extracted into a pure fn specifically because `available == 0` cannot be provoked
on demand from a live sysinfo handle — without that split the fallback would be a check nobody has
ever watched fail (ARCH §18.1). Test
`free_ram_falls_back_when_available_is_zero_under_compressor_pressure` pins it with this host's real
counters.
