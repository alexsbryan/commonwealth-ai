`project_registry::try_run` DISPATCHES — a test that passes it a subcommand the module owns does not fail an assertion, it EXECUTES the command.

Hit live 2026-08-07 (`b0edbe15`). `try_run_declines_subcommands_it_does_not_own` had listed `"init"` since the module was written, correctly, because init lived in the workbench. The moment `init` moved in-process the same unchanged test ran a REAL `svrn project init` against the checkout's own working directory: it rewrote this repo's `.sovereign/project.toml` and then hung 180 s on `cmd_init`'s stdin prompt (`confirm_write_config`). Only the nextest timeout surfaced it. It got as far as the observation write; a few steps further and it would have overwritten AGENTS.md and .claude/settings.json in the repo.

Rule: a name may go in that decline list ONLY if this module can never serve it in any build shape. The sibling tests are safe for the opposite reason — `owned_subcommands_are_claimed` passes `--help`, which short-circuits before any work.

Generalises beyond this file: any "assert X is not handled" test over a dispatch function becomes a live invocation the day X starts being handled. Prefer asserting on the routing table (`IN_PROCESS`) over calling the dispatcher, or pass `--help`.

Related: the same stdin-prompt shape is the known `sovereign-test.sh` deadlock — cargo must run `</dev/null`.
