SHARED CHECKOUT: a script that WRITES files must take an explicit path allowlist — never `git diff --name-only`.

Invariant 4dd9c7ab fired a fifth time on 2026-08-21 (nc-18), by a NEW mechanism. Not `git add -A` and not a bare commit: a helper script whose INPUT was the whole dirty set. In a shared checkout `git diff --name-only` is a peer-contaminated list. My import-repair pass iterated it and edited two files belonging to a live peer (nc-17): `sovereign-contracts/src/traits.rs` and `sovereign-inference/src/embedded/model_slot.rs`, hoisting one function-local `use std::sync::Arc;` into the file header in each. Both restored exactly; verified with `git diff | grep -c '^[+-].*use std::sync::Arc;'` returning 0.

Two further traps from the same session, both worth knowing:

1. `git update-ref refs/heads/<branch> <hardcoded-sha>` REWOUND A PEER'S COMMIT. Between reading the sha and using it, a peer landed `cdb57c83`; resetting to the sha I had read dropped it. Recovered from reflog. ALWAYS pass the expected old value as the third arg — `git update-ref <ref> <new> <old>` is compare-and-swap and would have refused.

2. After committing via temp index + `commit-tree`, the MAIN index is stale and `git diff --cached` shows the REVERSE of the new commit — a naive `git commit` by anyone would revert it. Fix is a plain `git reset` (mixed, no paths, no `--hard`): it refreshes the index to HEAD and does not touch the working tree. Check `git diff --cached --name-only` for peer-staged files first; if a peer has something staged, do not reset.

The temp index + `commit-tree` path itself worked correctly and is the right tool for "a file a peer also has dirty": build the blob as HEAD-content + only your own hunk, assert the peer's hunk is ABSENT from it before hashing, then verify after the commit that the peer's hunk is still present and uncommitted in the working tree.
