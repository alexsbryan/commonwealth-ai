THE DAEMON'S ANON INFLATION IS A 4 GiB VULKAN BUFFER CEILING, NOT A LEAK — ROOT-CAUSED 2026-08-27. CORRECTS the prime suspect in 05cbffed ("the host-memory fallback appears not to be freed"), which that note flagged as "NOT yet root-caused to a line. Next reader: this is the open bug."

THE DEVICE CEILING (vulkaninfo, in the sovereign-vulkan toolbox):
  AMD Radeon 8060S Graphics (RADV GFX1151), INTEGRATED
  maxMemoryAllocationSize = 0xfffffffc  (~4 GiB)
  maxBufferSize           = 0xfffffffc  (~4 GiB)
A single Vulkan buffer on this device cannot exceed ~4 GiB — the 32-bit cap.

THE MECHANISM, end to end:
1. A large prefill needs a buffer > 4 GiB.
2. Vulkan refuses -> `ggml_vulkan: Failed to allocate pinned memory (Requested buffer size exceeds device buffer size limit: ErrorOutOfDeviceMemory)`.
3. vendor/llama-cpp-sys-4/llama.cpp/ggml/src/ggml-vulkan/ggml-vulkan.cpp:16191, in `ggml_backend_vk_host_buffer_type_alloc_buffer`, catches vk::SystemError and returns `ggml_backend_buft_alloc_buffer(ggml_backend_cpu_buffer_type(), size)` — a HOST (anonymous) buffer.
4. That buffer is retained for the CONTEXT's lifetime and sized to the HIGH-WATER MARK.

THE FALLBACK IS NOT LEAKED. The CPU buffer carries the cpu buffer type and its own free_buffer, so it is released normally. MEASURED: 3 fallbacks in one daemon instance produced exactly 1 anon step. The first allocates; the rest reuse. "Leak" is the wrong model — RATCHET is the right one, which is why it only ever reclaims on restart and why coarse sampling reads it as ~1 GB/min.

MEASURED (research/deep-research/arms/mem-forensics/daemon-mem-20260827T1417.tsv, 20s sampling, RssAnon split from RssFile):
  14:19:02  anon  7.08 GiB   gtt 20.56
  14:19:22  anon 21.36 GiB   gtt 20.41   <- +14.3 GiB in ONE 20s window
  14:25:23  anon 23.29 GiB   gtt 20.41   <- flat for 6 min across 2 more fallbacks
The step coincides EXACTLY with the first large section draft: `inference.complete: call slot=fast prompt_chars=65904`. GTT DID NOT MOVE — the allocation is host anon, invisible to GPU accounting. This is why "the model is not in RSS" (0b7eb9f3) and the anon still explodes.

THE LEVER IS THE CONTEXT SIZE, and it reconciles b061819c with 21382c79 (which I had called irreconcilable). KV is exactly linear — 0.12890625 MiB/token, verified at TWO logged points (8448 MiB @ n_ctx 65536; 2112 MiB @ 16384):
  65536 -> 8448 MiB  OVER the 4 GiB cap -> host fallback
  32768 -> 4224 MiB  marginally over
  28672 -> 3696 MiB  UNDER -> pins in GPU
  16384 -> 2112 MiB  under, but BREAKS deep research
Deep research's round leg needs 21,014 tokens (measured, from the overflow error itself). `[models].fast_context_size = 28672` clears that with headroom AND keeps KV under the cap. "Unset it" was the wrong conclusion; "size it deliberately" is the right one.

DO NOT REACH FOR GGML_VK_FORCE_MAX_BUFFER_SIZE. 0xfffffffc is a real driver constraint, not a conservative report; forcing it higher moves the failure rather than removing it. (ggml-vulkan.cpp:6372. GGML_VK_SUBALLOCATION_BLOCK_SIZE defaults to 1 GiB and is clamped to max_memory_allocation_size at :6390.)

NOT YET VERIFIED, and it matters before shipping: whether the >4 GiB allocation is the KV cache or the prefill COMPUTE buffer. The step lands at first prefill, NOT at slot load, which is consistent with either or both. The settling experiment is one arm: set 28672, restart, and check whether the warning disappears and the plateau drops ~8 GiB.

FOR EXTERNAL DISTRIBUTION: the cap is device-specific, so a shipped default must be DERIVED from the queried maxBufferSize, never hardcoded to this box's 4 GiB. Restarting between workloads is a measurement workaround and is not shippable.
