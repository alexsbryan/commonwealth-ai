ORPHANED `sovereign-server` ROOT-CAUSED (2026-08-24, operator-reported "keeps happening"). Hazard 10 ("cleanup that never runs") with a live instance, and the reason `Launch` gained a `Server` variant the same day.

OBSERVED: PID 37039, PPID 1 (reparented to launchd), `./target/debug/sovereign-server --config ~/.svrnmesh/mobile-host-server.toml`, started Mon Aug 17 22:33, elapsed 6d17h, LISTENING on `0.0.0.0:8080`.

THE CHAIN, each link verified:
1. `mobile_host_setup.rs:11-14` documents the child's death mechanism as: abort the JoinHandle -> the run future drops -> the in-flight child's `kill_on_drop(true)` SIGKILLs it. Its own comment scopes that to "that's toggle-off".
2. `main.rs:829` exits the desktop via `fast_exit_skip_destructors(0)` — a raw `_exit`, chosen deliberately to dodge a ggml-metal `__cxa_finalize` SIGABRT that popped a crash dialog on every quit.
3. `_exit` runs NO destructors, so `kill_on_drop` never fires.
4. `main.rs:823` calls `stop_daemon_child(app_handle)` before that exit — there is NO `stop_mobile_host`. The ONLY abort of `mobile_host_supervisor` anywhere is `commands/config_setup.rs:42`, the Settings toggle-off path.
5. `sovereign-server/src/main.rs` has NO signal handler and NO parent-death check, so nothing reaps it from its own side.
=> Quit the desktop with mobile access on -> one orphan, every time.

THE CODEBASE ALREADY KNEW AND DID NOT GENERALIZE IT. `supervisor_setup.rs:200-204` states verbatim that the reasoning "process exit kills the child via kill_on_drop(true)" is "false for this app: the desktop exits through fast_exit_skip_destructors(0) (raw _exit), so no destructor ever runs and the child is orphaned rather than killed." That lesson was learned for the DAEMON child (2026-08-05, the "crash report on every quit" bug) and never applied to the mobile-host child, which still documents the falsified mechanism as its design. Two supervised children, one lesson, applied once.

WHY ONLY ONE ORPHAN EXISTS, and why that is WORSE than accumulation: the first orphan wins `0.0.0.0:8080`; every later spawn fails to bind and exits. The leak self-limits in COUNT while the OLDEST process squats the port — a stale binary from a 6-day-old build, running a config written Aug 14 with whatever pairing token it then held, serving on ALL interfaces, unsupervised (no health check, no restart policy, no crash reporting), while the desktop believes it started a fresh one.

TOP-DOWN RESOLUTION (operator steer 2026-08-24: "architecture is perfect and clean from the top and we work downwards" — do NOT hand-patch the leaf). The root is that `sovereign-server` was a resident process the closed set did not name, so `Launch::is_resident()` — the ONE predicate the run lock, the panic hook and the OOM watchdog key on — returned false for it. `Launch::Server` was added 2026-08-24 and `is_resident()` widened; the acceptance number moved 7 -> 3 -> 3 to 8 -> 3 -> 3. Naming it is the PRECONDITION; the lock and watchdog actually covering it lands when the assembler owns process lifecycle. A `stop_mobile_host` patch would have papered over the missing variant and been deleted later.

WHEN IT IS TIME, THE FIX IS LAYERED (§7.4) and layer 2 is the one that matters:
1. PARENT SIDE — `stop_mobile_host` on the quit path mirroring `stop_daemon_child`. Closes the common case. NOT sufficient alone.
2. CHILD SIDE, STRUCTURAL — the parent has DECLARED, by choosing `_exit`, that it will not run cleanup. Any mechanism depending on parent-side work also fails under SIGKILL, panic and power loss. The child must own its liveness: inherit a pipe fd and exit on EOF (survives even a SIGKILLed parent), or poll `getppid() == 1` — the latter is WRONG under systemd, where PPID 1 is legitimate, so prefer the pipe or an explicit `--exit-with-parent <pid>`. This makes the orphan UNREACHABLE rather than remembered (§7.1).
3. BIND REFUSAL — failing to bind 8080 must be a LOUD refusal naming the squatting pid (§18.3), never a silent exit. Today "mobile access is on" can mean "a stale process is serving".

NOT the cause of the memory exhaustion observed the same day — the orphan is 30MB RSS. That was the daemon (PID 10745) holding a 14.8GB resident model with swap at 31.9/32GB.
