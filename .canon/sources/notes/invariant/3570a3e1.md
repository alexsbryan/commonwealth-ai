WHY THE SCIP INDEX GOES STALE UNLESS MANUALLY BABYSAT (root-caused 2026-08-04, from daemon.err + live process env, not recalled).

The freshness loop is alive but every automatic rebuild fails silently. Chain:
1. The daemon's git_poll DOES detect HEAD moving and fires a SCIP rebuild (watcher healthy).
2. The daemon spawns SCIP exporters by PATH lookup. The service-installed daemon runs with the plist's hardcoded PATH `/usr/local/bin:/usr/bin:/bin:/opt/homebrew/bin` (verified via `ps eww` on pid). rust-analyzer lives in `~/.cargo/bin`, scip-typescript in the nvm bin dir — NEITHER resolves. daemon.err: "SCIP exporter not found in PATH ... No SCIP exporters available — call graph will be empty".
3. Rebuild yields 0 symbols; the empty-graph guard (correctly) refuses to rename over the live graph: "refusing to rename over the populated live graph — preserving 210917 symbols".
4. Net effect: index frozen at whatever the last MANUAL `svrn project refresh --local` built from a user shell (where cargo/nvm paths resolve). Hence "10 days stale" = 10 days since the operator last ran it by hand.

TRAP: `sovereign doctor`'s scip_exporters check probes DOCTOR'S OWN shell PATH, not the daemon's — it reports rust-analyzer/scip-typescript fine (only python missing) while the daemon can find none of the three. The check validates the wrong environment (§18 instrument-validation smell). `svrn status` shows Index ✓ / Watched ✓ throughout.

Repair now: run refresh from a user shell. Structural fix: daemon must resolve exporter ABSOLUTE paths at install/startup (probe ~/.cargo/bin via `rustup which rust-analyzer`, nvm dirs, or capture login-shell PATH into the plist at service_install.rs time), doctor's exporter check must ask the daemon to resolve, and N consecutive failed rebuilds must escalate from a WARN in daemon.err to a visible staleness flag on status/MCP responses.
