# installed_indexes() returns at most one IndexInfo per corpus_id. When 2+ on-disk directories advertise the same corpus_id,…

installed_indexes() returns at most one IndexInfo per corpus_id. When 2+ on-disk directories advertise the same corpus_id, dedupe_by_corpus_id() prefers the dir whose basename == corpus_id (the canonical that open_index_for_corpus opens) and warn!-logs the dropped paths.

WHY: (corpus_id, chunk_id) is the system's citation handle. chunk_id is a LanceDB row id scoped per physical index, so if two physical indexes both report corpus_id='wikipedia', retrieval can pull a chunk from one while the reading desk dereferences the same chunk_id against the other — silently rendering unrelated content. Reproduced live (2026-05-03): SEP-objectivism retrieval surfaced chunk_id=454732 corpus_id=wikipedia (sourced from a stranded partition shard); the reading desk opened ~/.sovereign/indexes/wikipedia/ and showed Garth Brooks at row 454732.

DO NOT remove the dedup unless retrieval is also changed to carry a per-physical-index instance id end-to-end. Tests pinning the invariant: engine::tests::installed_indexes_dedupes_corpus_id_collisions_preferring_canonical, corpora_with_colliding_indexes_finds_canonical_plus_lingering_partitions.

Operator escape hatch: rename a stale physical index to <name>.retired (or any name containing '.') so is_out_of_band_index_name filters it.
