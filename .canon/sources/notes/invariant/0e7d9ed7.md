# CorpusIndex::exists_at(path) — "is there an index here?" is answered by _corpus_meta.json, NEVER by path.exists().

`CorpusIndex::exists_at(path)` — "is there an index here?" is answered by `_corpus_meta.json`, NEVER by `path.exists()`.

Other subsystems write siblings into `<index_dir>/<corpus_id>/` before any index exists there — the generic enrichment-progress sink (commit 11846003) drops `_enrichment_state.json` in it. So the directory routinely exists with no index in it. Code that branches on `canonical.exists()` to decide create-vs-open sends that directory to `CorpusIndex::open`, which fails `IndexNotFound: Missing metadata at …/_corpus_meta.json`.

Fixed 2026-07-24 at both sites in corpus-engine/src/engine/ingest.rs: the watcher-driven branch (~line 212) and `ensure_empty_index` (~line 483). The latter is the sharper bug — that function exists precisely to repair a metadata-less index dir (commit 58dc03ab), and the directory check made it fail on the exact state it was written to fix. User-visible symptom: adding a folder whose files are all unsupported/unreadable (e.g. a `.md` folder registered as a `document_folder`, which allows only pdf+txt) 500s with "ensure empty index: Index not found" instead of creating a first-class empty corpus.

Regression test: `ensure_empty_index_succeeds_when_dir_exists_without_metadata` in corpus-engine/tests/ingest_failure_modes.rs. Found by the desktop real-mode e2e harness, which had been dead in global-setup since the governance fixture landed (2026-07-09).
