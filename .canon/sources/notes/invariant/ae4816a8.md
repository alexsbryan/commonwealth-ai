# WikipediaNewsworthyWatcher (and any future long-running watcher using watch::channel shutdown) must move the sender into the spawned task's…

WikipediaNewsworthyWatcher (and any future long-running watcher using watch::channel shutdown) must move the sender into the spawned task's async block, not bind it in the outer function (start_daemon) scope. Otherwise the sender drops the moment start_daemon returns and the watcher exits silently.

When a long-running tokio task uses `tokio::sync::watch::channel` for
graceful shutdown, the sender must be moved into the spawned
task's `async move {}` block — not bound to a local in the caller's
scope. The reference pattern is the storage-snapshot loop in
`sovereign-mesh/src/daemon.rs` (search for `_hold_shutdown_tx`).

Wrong (silently dies):
```rust
let (tx, rx) = tokio::sync::watch::channel(false);
let _hold = tx;          // bound in start_daemon, dropped when fn returns
let _h = watcher.spawn(rx);
```

Right (lives for daemon lifetime):
```rust
let (tx, rx) = tokio::sync::watch::channel(false);
tokio::spawn(async move {
    let _hold_shutdown_tx = tx;        // moved INSIDE the task
    let handle = watcher.spawn(rx);
    let _ = handle.await;
});
```

Why: if the sender drops while the receiver is still listening,
`shutdown_rx.changed().await` returns `Err`. In a `tokio::select!` arm
matching `_ = shutdown_rx.changed() => return,`, that triggers the
watcher to exit immediately. The watcher may have logged its
`*.watcher_starting` event before reaching the select — so logs
look "watcher is running" but no actual ticks ever fire.

How to apply: any new long-running daemon-side task that takes a
`watch::Receiver` for shutdown must put its corresponding sender
inside an `async move {}` that the runtime owns for the daemon's
lifetime (typically the wrapping `tokio::spawn`). Don't bind it as a
local in `start_daemon` or any other function that returns soon
after the spawn.

Observed 2026-05-10: WikipediaNewsworthyWatcher had this exact
bug — `_hold = sender` in start_daemon scope. Daemon was up for
~9 hours across 7 restarts; never a single `newsworthy.tick` event
fired. Surfaced only after adding `corpus_engine=info` to the
tracing filter (which made `newsworthy.watcher_starting` visible but
the absence of subsequent tick events screaming louder).

Cross-reference: `invariant_appstate_arc_get_mut_order.md` for
another silent-failure-mode bug rooted in scope/order semantics in
`start_daemon`.
