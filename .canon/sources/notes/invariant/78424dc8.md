# sovereign eval execs into sovereign-cli-llm binary, not sovereign-cli; debug-instrumenting changes requires building -p sovereign-cli-llm**

**`sovereign eval` execs into `sovereign-cli-llm` binary, not `sovereign-cli`; debug-instrumenting changes requires building -p sovereign-cli-llm**

`sovereign-cli/src/main.rs` is a routing wrapper. For `eval`, `bench`,
`chat`, `atlas`, `enrich`, `recipe`, `pipeline`, `mesh`, `claim` it
**execs into the sibling binary `sovereign-cli-llm`** (see
`llm_bin::exec` calls in main.rs).

Why: Compilation isolation. The sovereign-cli wrapper stays small
so common subcommands (setup, doctor, project) build fast; LLM-heavy
deps (llama-cpp-sys, lance, etc.) only get pulled when the user invokes
an LLM verb.

How to apply: When instrumenting any code path touched by
`eval`/`bench`/`chat`/`atlas`/etc., rebuild with:

```
cargo build --release -p sovereign-cli-llm --bin sovereign-cli-llm
```

`cargo build -p sovereign-cli --bin sovereign-cli` rebuilds the
routing wrapper, not the actual LLM binary. Symptoms: edits to
`sovereign-core` runtime code appear to do nothing — `tracing` and
`eprintln!` traces silently absent because the stale wrapper is fine
but the exec'd sibling binary has no new code.

Burned 30+ min on this during the 2026-05-26 retrieval-over-history
spike. The smoke check is `stat target/release/sovereign-cli-llm`
timestamp vs your edit time, NOT `target/release/sovereign-cli`.
