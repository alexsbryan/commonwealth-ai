# WATCHED-FOLDER INGEST CAN PERMANENTLY STRAND A CORPUS'S LANCE DATA IN ITS PARTITION DIR, AND ATTACH MODE RENDERS THE RESULT AS A SILENT…

WATCHED-FOLDER INGEST CAN PERMANENTLY STRAND A CORPUS'S LANCE DATA IN ITS PARTITION DIR, AND ATTACH MODE RENDERS THE RESULT AS A SILENT null (2026-07-27, proven by the real-mode e2e suite).

THE RACE. Ingest writes chunks to `<index_dir>/<corpus_id>-partition-<self_node_id>` (CorpusEngine::partition_path, corpus-engine/src/engine/mod.rs:570). The canonical `<index_dir>/<corpus_id>` is materialised ONLY by finalise_solo_ingest (engine/mod.rs:2245), called from engine/ingest.rs:342, which delegates to promote_single_shard. promote_single_shard REFUSES a non-empty destination. Meanwhile the watched-folder/enrichment writers drop `_enrichment_state.json` and `_watched_folder_state.json` into that SAME canonical dir. Whoever writes first wins:
  - promote first  -> canonical gets _corpus_meta.json + chunks.lance, corpus healthy.
  - state file first -> promote fails, partition stranded, canonical NEVER gets Lance data. PERMANENT.

Observed both outcomes on the same machine, same fixture, in one session: managed-daemon run LOST the race (daemon.out: 'ingest: finalise_solo_ingest failed - partition-of-self left in place ... promote_single_shard: cannot merge <id>-partition-node-<n> into <id> - destination already has an entry named "_enrichment_state.json"'); the attach run against the real daemon WON it.

WHY NOBODY NOTICED. (a) The ingest job still emits its Complete terminal event, so the UI reports success. (b) The failure is a WARN only. (c) SEARCH STILL WORKS: installed_indexes() enumerates directories and keys each one off its meta's corpus_id field, and the partition dir's _corpus_meta.json declares the BASE corpus_id - so retrieval finds the chunks in the partition. But the reading surface uses open_index_for_corpus (engine/mod.rs:2296-2298) and find_index_path (:2582), which BOTH resolve canonical BY DIRECTORY NAME ONLY. So retrieval and the reading surface resolve corpora by DIFFERENT strategies and disagree exactly when promotion failed. Every citation into such a corpus is a dangling citation: no chunk deref, no neighbors, no atom cards.

CONFIRMED IN THE OPERATOR'S REAL INSTALL: ~/.sovereign/indexes/enron-sample-tiny/ has assets/ + atlas/ but NO _corpus_meta.json, with enron-sample-tiny-partition-node-b88252e4325bc377 stranded beside it. (enron-sample-multi-tiny also has a stranded partition but DID promote, so it works - the stranded dir is just wasted disk.)

THE ATTACH-MODE AMPLIFIER. reading_http.rs:304 and :335 return not_found() (404) when open_index_for_corpus errors - an infrastructure fault reported as absence. commands/reading.rs:264-266 then maps ANY 404 to Ok(None) -> null. So in Attach (the SHIPPED mode) a structurally broken index is indistinguishable from a legitimately missing chunk and the real message never reaches the desktop, its logs, or the test output. In Local mode the same condition returns Err with the text (reading.rs:296-298). Same silent-degradation family as warmup_primary - see note 2ad04464.

FIXES: (1) make promote_single_shard tolerate/merge pre-existing state sidecars, or write them only post-promote; (2) split reading_http's 404 into 404-absent vs 503/500-cannot-open so the desktop stops swallowing it; (3) surface finalise failure on the ingest job's terminal event instead of a WARN. Diagnostic: 'svrn reading-diag query <q> --corpus <id>' shows retrievable chunks alongside a failing open_index in one output - that is the signature.
