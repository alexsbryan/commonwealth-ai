# Agent-tools/TDD tests that spawn python3/pytest flaked ONLY under full 50-crate suite load — a silent fail-open turned a subprocess hiccup…

Agent-tools/TDD tests that spawn python3/pytest flaked ONLY under full 50-crate suite load — a silent fail-open turned a subprocess hiccup into a wrong 'valid'/'no-progress' result. Fixed 2026-07-16 with retry + observability + generous timeouts.

FIXED 2026-07-16. Five tests failed in the full `sovereign-test.sh --workspace`
run (7691p/5f) but passed in isolation, combined, and under an 800-proc python3
storm — flaky ONLY under full 50-crate suite oversubscription. All five shared
one root-cause class: they spawn subprocesses (`python3` / `pytest`) and a
silent fail-open converted a transient subprocess hiccup into a wrong result.

- 3× `syntax::tests::python_validator_rejects_*` + `executor::tests::patch_file_pre_check_rejects_broken_result`
  (`commonwealth-agent-tools`): `PythonSyntaxValidator::check_file` fail-opened
  (returned empty errors) on any spawn/timeout/parse trouble → "must be rejected"
  panic; executor pre-write gate uses the SAME validator → broken patch applied
  (`ok:true`) → `unwrap_err()` panic. This is also a PRODUCTION defect: under load
  the pre-write gate would silently pass broken Python.
- `tasks::solve::tests::no_tests_repo_pins_by_import_error_then_goes_green`
  (`commonwealth-tdd`): confirmed mechanism — `run_tests` (shared/test_runner.rs)
  returns `TestRunResult::empty()` (parsed `0p/0f`) when the command exceeds
  `candidate_test_timeout`. Under load the `python3 -m pytest` spawn was starved
  past the 30s deadline → killed → empty `0p/0f` → no red pin → `Stalled` at
  `max_stall_rounds:1`. NB: `parse_pytest_text` DOES fold a collection/import
  ERROR into `0p/1f` correctly (verified) — the `0p/0f` came from the timeout
  kill, not the parser.

Fixes: (1) `check_file` retries the transient spawn/wait class 3× and `tracing::warn!`s
on EVERY fail-open branch (extracted `run_python_syntax_probe`); the validator flake
could NOT be reproduced, so the warn-logging — not the retry — is the real guarantee:
next full-suite flake names the exact branch. (2) `run_tests` warns on the timeout-kill
path. (3) The two pytest-spawning solve trajectory tests (`from_secs(30)`/`(20)`) →
`from_secs(120)` — the timeout is a hang-guard, not a perf assertion (pytest <0.1s in
isolation). Verified: full workspace 7701p/0f. [[feedback_run_tests_at_initiative_end]]
