QWEN3.8-FLASH-NEXT RUNS LOCALLY AT 22.4 tok/s, AND THE ENGRAM'S EVICTABILITY IS ACCIDENTAL (measured RuggedFox 2026-08-26). Model loads and generates coherently; 103.7 GiB = 79.6 GTT + 27.0 CPU RSS + ~3 compute/KV. Engram (per_layer_token_embd, 26.8 GiB) is NOT GPU-resident — resident would be ~104 GiB GTT, not ~80. Data + method in research/engram/RESULTS.md §6.

THREE CORRECTIONS TO THE PRIOR FRAME, all measured, all load-bearing:

1. `-ot per_layer_token_embd=CPU` IS A NO-OP. per_layer_token_embd is classified LLM_TENSOR_LAYER_INPUT/GGML_OP_GET_ROWS (llama-arch.cpp:887), same class as token_embd (:696), so it comes off the CPU buft list with or without the override. A/B is flat within noise: 79.62 vs 79.68 GiB GTT, 22.38 vs 22.45 tok/s. The shipped SOVEREIGN_TENSOR_BUFT_OVERRIDE mechanism is not what keeps the engram off the GPU.

2. "=CPU" RESOLVES TO Vulkan_Host (PINNED), NOT PAGEABLE CPU. make_cpu_buft_list (llama-model.cpp:1012) emplaces the device HOST buffer type FIRST (:1033), ahead of plain CPU. Watched it fire with -v on a forced override: "tensor blk.0.ffn_down_exps.weight (600 MiB q5_1) buffer type overridden to Vulkan_Host". Pinned host memory is the OPPOSITE of the evictability the design is built on — so applying the override to the engram would have defeated its own rationale.

3. THE ENGRAM LANDS ON PAGEABLE CPU ONLY BECAUSE iq4_nl IS UNSUPPORTED BY Vulkan_Host: "tensor 'per_layer_token_embd.weight' (iq4_nl) (and 30 others) cannot be used with preferred buffer type Vulkan_Host, using CPU instead". iq4_nl was forced by row width 160 (160 % 256 != 0 kills K-quants — RESULTS §5). So the property the whole design depends on is unguarded: change the engram quant to anything Vulkan_Host accepts and it silently becomes pinned. --no-host makes it structural at zero cost (22.42 vs 22.45 tok/s, GTT 79.05, RSS 27.62). USE --no-host, do not rely on the accident.

ALSO: IT IS NOT DEMAND-PAGED, IT IS PREFETCHED. llama-mmap.cpp:455 sets MAP_POPULATE and :463 posix_madvise(WILLNEED) whenever prefetch != 0 (llama-model-loader.cpp:1369 passes -1 under use_mmap). Whole 26.8 GiB is pulled into page cache at load: 7.08M MINOR faults (= 27 GiB / 4 KiB) and ~0 major, even after fadvise(DONTNEED) on all four shards. Generation itself costs 9 major faults over 127 tokens. The 376 us cold-gather figure (RESULTS §4) is real but is NOT paid on this path. Lazy paging, if ever wanted, is the prefetch=0 branch at llama-mmap.cpp:469.

BAR CHECK: 22.4 > 19.34 (122B solo) => worth continuing, +16%. But the frame PROJECTED ~33.5 tok/s; measured is 33% under. Do not carry the projection forward.
