# Cleaning target/debug while the launchd daemon runs orphans it (runs from deleted inode, leaks unbounded); on next restart launchd fails…

Cleaning target/debug while the launchd daemon runs orphans it (runs from deleted inode, leaks unbounded); on next restart launchd fails EX_CONFIG (78) 'cannot exec' because the binary file is gone — rebuild sovereign-cli-daemon to fix

The launchd job `com.sovereign.daemon` execs
`target/debug/sovereign-cli-daemon`. If `target/debug` is cleaned while the
daemon is running (release-all.sh reclaims target/debug; a `cargo clean`; a
disk sweep), the **running process keeps executing from the now-deleted
inode** — Unix doesn't kill a process when its binary is unlinked. Symptoms
that follow:

- The orphaned daemon can grow unbounded (observed: 44 GB RSS, ~30h,
  pegging a core) because nothing restarts/recycles it.
- When it finally dies or is killed, launchd tries to relaunch and fails with
  **`last exit code = 78: EX_CONFIG`, `job state = spawn failed`** — that code
  is "cannot exec program," i.e. the binary file no longer exists on disk.
- `:9741` is dead (connection refused → the desktop app shows
  `error sending request for url (http://localhost:9741/...)`).

Diagnosis path: `launchctl print gui/$(id -u)/com.sovereign.daemon`
(look for EX_CONFIG / spawn failed) → `ls target/debug/sovereign-cli-daemon`
(missing) → note the running pid is executing a deleted inode.

Fix: rebuild the binary launchd points at, then kickstart:
`cargo build -p sovereign-cli-daemon -p sovereign-cli` then
`launchctl kickstart -k gui/$(id -u)/com.sovereign.daemon`. Verify with
`curl :9741/v1/mesh/status` (there is NO `/health` route — it 404s even when
healthy; use a real endpoint as the liveness probe). Boot RSS ~12 GB with the
35B-Q6 primary + embed model loaded is normal; 40 GB+ is the leak.

Incident 2026-07-15: user left a mesh, desktop couldn't load mesh state. Root
cause was this deleted-binary trap (target/debug had been reclaimed during
v0.2.0 release work), compounded by [[invariant_mesh_leave_does_not_exit_standalone_daemon]].
