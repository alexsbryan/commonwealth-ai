# THREE INSTRUMENT FAILURES IN ONE SESSION, all the same shape: a verdict that did not mean what it appeared to mean. Order…

THREE INSTRUMENT FAILURES IN ONE SESSION, all the same shape: a verdict that did not mean what it appeared to mean. Order grounding-preventative-medicine (redirected), 2026-08-13, successor session. Written while fresh, at the seat's direction.

THE COMMON SHAPE, and it is the reason to read this note: in every case the number was REAL and belonged to the WRONG QUESTION. None of these was a bug in the gate. Each was a correct answer to a question nobody meant to ask. The fix in all three is the same and it is not "be careful": gate on a property of the ARTIFACT or the BANNER, never on an exit code alone.

═══ 1. THE EXIT CODE THAT BELONGED TO ANOTHER PROCESS ═══
Predecessor ran `./scripts/sovereign-test.sh --human 2>&1 | tail -22`. The pipeline's status is TAIL's (0), not the script's (5). The background-task notification then reported "exit code 0" and the handoff recorded the gate as never-ran-but-probably-fine. The gate had actually returned EXIT 5 — "NOT GREEN, no results could be attributed to this run", the documented nextest junit-attribution case (note ac8d3dd1 corrects it).
RULE: NEVER PIPE A GATE. Run it bare, or capture PIPESTATUS[0] / set -o pipefail. A gate piped into anything reports the last stage's success as the gate's.
REMEDY THAT WORKED, do not re-derive: `--engine cargo` bypasses the junit path entirely. Ran it this session; the attribution failure is gone and the gate returned a real verdict. The script prints this remedy itself.

═══ 2. THE EXIT CODE THAT SURVIVED ITS OWN LINKER DYING ═══
Twice this session cargo printed "Finished dev profile" AND exited 0 while the linker had died of ENOSPC ("LLVM ERROR: IO failure on output stream"), leaving 1.3KB non-executable stubs where 400-600MB binaries belonged.
RULE: GATE ON BINARY SIZE, NOT EXIT CODE, after any build. `stat -f%z target/debug/<bin>` must be >100MB and the file must be executable. I built this refusal into the harvest launcher rather than remembering it (#10, make it structural).
NOTE the coverage gap this exposes: sovereign-lint.sh's 2026-07-28 fix made it report build-script failures and bad feature flags as errors, but LINK-STAGE IO failure is not rustc diagnostics and still slips through. That is a real hole, not a hypothetical.

═══ 3. THE RED GATE THAT WAS TRUE AND MEANT SOMETHING ELSE ═══
`sovereign-test.sh --human --engine cargo` returned EXIT 101, pass 9608 / fail 2. Both failures were `pause_resume_round_trip_flips_status` and `register_then_list_then_status_round_trip` in sovereign-mesh/tests/corpus_watch_http_e2e.rs — ConnectionRefused on 127.0.0.1:53287, both in 0.16s. A router that never bound; not an assertion about behaviour.
THE CONTAMINANT, found by accident while polling: THREE CLI journey lanes were running concurrently (cli-journey-nightly.sh, cli-journey-sandbox.sh, cli-journey-verify.sh --mutating), 25 live `sovereign` processes, journeys started 09:41 and 09:56 — inside the gate's 09:31-10:00 window. The lanes RE-FIRE on a schedule (nightly restarted 15s after being reported), so killing processes is not the lever; pausing the schedule is.
THE TWO WRONG READINGS, both available and both tempting:
  (a) "red means revert" — wrong. f7bcf31e touches ZERO sovereign-mesh files and the tests exercise corpus_watch_router, not the grounding gate. Reverting grounding code cannot fix a mesh HTTP bind race.
  (b) "re-run until it passes" — wrong, and worse because it FEELS rigorous. My isolated re-run was running under the SAME contamination, so it could not exonerate the repairs even by passing. It did pass (657/0, exit 0). That is weak corroboration of the environmental reading and NOT clearance.
THE RULING (seat, 2026-08-13): the gate is RED and that verdict STANDS, unoverwritten. The REPAIRS are COULD-NOT-JUDGE, not failed. And could-not-judge is NOT clearance — they stay unjudged until ONE CLEAN RUN on a quiet box. That sharpening is the load-bearing half; "not failed" invites reading it as "fine".

═══ 4. THE BONUS ONE: MEASURING THE RIGHT NUMBER IN THE WRONG PLACE ═══
Recorded because it is the same disease at analysis altitude and it bit BOTH of us. I reported that my cargo build ate the disk (67 -> 24Gi). Wrong. The dominant consumer was 105 orphaned /private/tmp/cli-journey.* dirs totalling 137G. The seat had independently hunted the disk earlier, scanned /private/var, never /private/tmp, and told the operator there was nothing stale. Both of us produced a confident, evidence-shaped, wrong answer by looking in a place that did not contain the phenomenon. Seat then removed 98 dirs with a 120-minute mtime guard: 18Gi -> 150Gi.
NOTE `du -sh /tmp` reports 0B on macOS because /tmp is a symlink. Use /private/tmp.
