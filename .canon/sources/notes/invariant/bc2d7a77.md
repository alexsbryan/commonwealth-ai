# POST /v1/conversations (daemon turn_http AND sovereign-server, same wire form) accepts enabled_corpora: [ids];…

`POST /v1/conversations` (daemon turn_http AND sovereign-server, same wire form) accepts `enabled_corpora: [ids]`; `Runtime::seed_conversation(id, created_at, skill_id, enabled_corpora)` VALIDATES it against `corpus_engine.installed_indexes()` (corpus_id ∪ parent_corpus_id — the same set `apply_corpus_allow_list` matches) via the pure `corpus_allow_list_verdict`, then writes it with `set_conversation_enabled_corpora` BEFORE the first turn. Unknown id → Error::InvalidInput → HTTP 400 naming the id and the installed list; empty list → 400 (never stored as "search nothing"); no engine → "no corpus index installed". This is what `svrn chat ask/session --corpus <id>` (repeatable) rides on; `--corpus` with `--conversation` is refused at parse time (CORPUS_WITH_CONVERSATION) rather than silently dropped, because the reused row's allow-list is already set. Rationale: the retrieval filter silently INTERSECTS, so an unvalidated unknown id yields an empty fan-out that reads as "the corpus does not cover this" (§18.3). Added 2026-09-01 for issue #57; tests: turn_surface.rs create_conversation_{seeds_the_corpus_allow_list_it_was_given,refuses_an_unknown_corpus_and_lists_the_installed_ones}, http_tests.rs rest_create_conversation_refuses_an_unknown_corpus_with_400.
