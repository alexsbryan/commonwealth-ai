A GREEN GATE VALIDATES THE WORKING TREE; `git commit` DURING A MERGE COMMITS THE INDEX. Those are different trees, and a conflict-resolution workflow reliably splits them.

Hit for real on 2026-08-10 merging origin/main (120 commits) into local main. The merge was staged when conflicts were resolved. Five post-merge defect fixes were then made with Edit/python — six files, including the three `dirs::home_dir` reader/writer split-brains the path-SSOT deny caught. Those edits landed in the WORKING TREE, never re-added. The full cold gate chain (clippy 0, lint 0, 9419 tests 0 fail, layer-gate 0, env-gate 0) ran against the working tree and was correct. Then `git commit` wrote the INDEX — producing a merge commit whose own message described six fixes it did not contain, and whose tree would have FAILED the clippy deny that had just passed.

Caught only by reading `git status --short` after committing and finding six ` M` entries. Fixed with `git add -A && git commit --amend --no-edit` (amend preserves both parents — verified `%P` still listed e8c00bf5 + 4ca7298e).

RULE: after any post-resolution edit during a merge, `git status --short` must be EMPTY before you commit, and empty again after. A ` M` (worktree-modified, unstaged) line during a merge means the thing you validated is not the thing you are about to commit. `git add -A` before the commit, not before the fixes.

Why this shape recurs here: gates read the filesystem, `git commit` reads the index, and the merge workflow is the one place where staging happens LONG before committing. Normal single-commit work does not expose the gap because `git add` and `git commit` are adjacent.
