TORCH+ROCm TRAINING RUNS INSIDE `sovereign-vulkan` — NO /opt/rocm AND NO SECOND CONTAINER REQUIRED. Verified 2026-08-02 on gfx1151: bf16 matmul, autograd backward, a hand-written Triton kernel compiled and executed, and a full 5-step ORPO LoRA run that passed the adapter gate. Supersedes the assumption that training must happen in `sovereign-rocm-7.2.4`.

WHAT IS ACTUALLY REQUIRED is not a system ROCm install. It is (a) the kernel driver — `/dev/kfd`, host-level, present in every toolbox — and (b) SOME HSA runtime preloaded, because torch's bundled ROCm 7.0 runtime SIGSEGVs against this driver and torch's RPATH is searched before LD_LIBRARY_PATH, so only LD_PRELOAD wins (note b18dacf9). Without it the process dumps core with no traceback.

TWO RUNTIMES WORK IDENTICALLY:
  /opt/rocm/lib/libhsa-runtime64.so.1            (sovereign-rocm-7.2.4, 1.18.70204)
  /run/host/usr/lib64/libhsa-runtime64.so.1      (Fedora host's, 1.18.0 — visible from ANY toolbox)

Do NOT hardcode either. `~/dev/train-env/launch_gradcheck.sh` detects: first existing candidate wins, hard-fails if neither. The rocm container's libs are also readable from other toolboxes via `~/.local/share/containers/storage/overlay/*/diff/opt/rocm-7.2.4/lib/`, but that path embeds an overlay hash and is NOT stable — use /run/host.

WHY THIS MATTERS OPERATIONALLY: nested `toolbox run` is impossible from inside a toolbox (`Error: flatpak-spawn(1) not found`), and agent sessions boot inside `sovereign-vulkan`. Before this, driving training meant asking the operator for a second terminal. Now it does not.

COROLLARY FOR UNSLOTH: triton ships its own `libhsa-runtime64.so` and AMDGPU LLVM backend inside the wheel (triton_rocm 3.6.0, verified running a GPU kernel here), so Unsloth's "pip-packaged ROCm nightlies, no system-level ROCm" claim is consistent with what we measured. System ROCm was never the blocker for that path.
