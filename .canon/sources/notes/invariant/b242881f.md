# InferenceProvider CANNOT move to oicp-types while edit_slot_info() is on it. That method returns EditSlotInfo -> FimLane / FimStyle /…

`InferenceProvider` CANNOT move to `oicp-types` while `edit_slot_info()` is on it. That method returns `EditSlotInfo` -> FimLane / FimStyle / NextEditLane / NextEditFormat, and `NextEditFormat` names sovereign's OWN prompt strategies (`region_instruct`, `zeta2`, `sweep`). Moving it down would put sovereign's prompt taxonomy inside the protocol crate — the "publish concrete types to make the metric move" failure `nc-boundary` explicitly warns about.

Two exits, both PRICED on this tree (2026-08-20):
  - supertrait split (`SovereignProvider: InferenceProvider`): 488 `dyn InferenceProvider` sites, because every `Arc<dyn InferenceProvider>` in sovereign would have to change (sovereign-core 178, sovereign-tools 86, sovereign-cli-llm 71, sovereign-mesh 54, ...).
  - move `EditSlotInfo` down: 201 lines, and drags the prompt taxonomy with it.

ALSO TRIED AND REVERTED, do not repeat in isolation: switching the trait's error type to `oicp_types::InferenceError` WITHOUT moving the trait. Carried far enough for the compiler to price it — sovereign-core and oicp-client both went green — but the tail propagates into the engine's internal streaming plumbing (`StreamSink`, `generate_stream_dispatch` in sovereign-inference/src/embedded/engine.rs), i.e. the daemon's hot generation path, and it buys 2 types on an edge that still cannot reach zero. Do trait-move and error-switch as ONE change, after EditSlotInfo has a home.

Measured state after rung 2b's landed half: oicp -> sovereign is 1 type / 3 refs (was 12 / 103), and the 1 is `InferenceProvider` itself.
