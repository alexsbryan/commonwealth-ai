OPENCODE CONFIG: THE FILENAME AND THE SHAPE WERE BOTH WRONG, IN THREE GENERATORS (found + fixed 2026-07-28). Verified against the installed opencode 1.14.48 binary's own loader/schema and the vendored @opencode-ai/sdk 1.14.41 types — not guessed.

THE THREE RULES, each of which we violated:

1. FILENAME. Inside a project `.opencode/` dir opencode reads ONLY `opencode.json` / `opencode.jsonc`. It does NOT read `.opencode/config.json`. `config.json` is honoured only in the GLOBAL config dir. We shipped five checked-in `.opencode/config.json` files and `svrn project init` wrote a sixth — all inert.

2. SHAPE. `Config.mcp` is a FLAT map: `mcp.<name>` -> McpLocalConfig | McpRemoteConfig (types.gen.d.ts:1128). There is no `servers` level. We emitted `mcp.servers.<name>`, which parses as a server NAMED "servers" with no `type`.

3. DISCRIMINATOR. The only valid `type` literals are "local" and "remote" (binary: `V.Literal("remote")` / `V.Literal("local")`, identifiers McpRemoteConfig / McpLocalConfig). We emitted "http". There is no "http" variant.

Correct: {"mcp":{"sovereign":{"type":"remote","url":"http://localhost:9741/mcp"}}}

WHY IT SURVIVED SO LONG — three compounding blindnesses:
(a) Nine test assertions PINNED the wrong shape, so the suite defended the bug. Tests asserting 'the JSON matches what we intended' prove nothing when the intent is wrong; assert against a shape you can point at a source for.
(b) `sovereign doctor` checked only that an UNRELATED file (.opencode/oh-my-opencode.jsonc) EXISTED, and reported Passed. A check that cannot fail is not a check (ARCH §9).
(c) The maintainer's own machine worked, because ~/.config/opencode/opencode.json had been hand-written correctly at some point. A working dev box masked a broken generator for every new user. When 'it works for me' and the generator disagree, read the file the tool actually loads.

EVICTION IS PART OF THE FIX. Writing the correct key is NOT sufficient: a leftover `mcp.servers` entry still fails opencode's schema and takes the whole config down. Both generators now delete the legacy entry (surgically — a peer's unrelated entry parked under `servers` is left alone) and tests pin that.

SAME CLASS, STILL OPEN: `.claude/settings.json` `systemPrompt` and `mcpServers` are BOTH non-keys in Claude Code (confirmed against official docs) — settings.json defines no MCP servers; `.mcp.json` at the REPO ROOT does, and subdirectory `.claude/settings.json` / `.mcp.json` are never discovered at all.
