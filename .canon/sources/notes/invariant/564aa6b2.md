# ggml-rpc's LOG_DBG has TWO gates in series — RUST_LOG=…llama_cpp=debug ALONE IS NOT ENOUGH.

ggml-rpc's LOG_DBG has TWO gates in series — `RUST_LOG=…llama_cpp=debug` ALONE IS NOT ENOUGH.

ggml-rpc.cpp:21-24 (llama-cpp-sys-4 0.4.2 / llama.cpp 99f3dc3):
    static const char * RPC_DEBUG = std::getenv("GGML_RPC_DEBUG");
    #define LOG_DBG(...) do { if (RPC_DEBUG) GGML_LOG_DEBUG(__VA_ARGS__); } while (0)

So every RPC-layer diagnostic — including `alloc_buffer ... -> failed`, the ONLY signal that a
worker-side buffer allocation failed — is suppressed at the CALL SITE unless GGML_RPC_DEBUG is
set, no matter what RUST_LOG says. The tracing level is the second gate, not the first.

CORRECT INVOCATION (both, on whichever side you want to see):
    RUST_LOG=info,llama_cpp=debug GGML_RPC_DEBUG=1 sovereign daemon run

RPC_DEBUG is a `static const char *` resolved at STATIC-INIT time, so the env var must be in the
process environment BEFORE launch. It cannot be enabled on a running daemon.

COST OF NOT KNOWING THIS (2026-07-27): a full instrumented cross-machine repro on both nodes
produced ZERO RPC-layer lines and had to be re-run. My earlier instruction (note 300540a6's
"decisive next probe") named only RUST_LOG and was therefore incomplete — corrected here.
BeefyMac's operator-side agent found the gate by expanding the macro.

DIAGNOSTIC TRAP that wasted a check: the tracing fmt layer does NOT print the target name, so
`grep llama_cpp <logfile>` returns 0 matches EVEN WHEN routing works correctly. Verify the routing
by looking for ggml's own content instead (e.g. `ggml_vulkan:`, `ggml_metal_device_init`,
`Loaded model`), not by grepping for the target string.
