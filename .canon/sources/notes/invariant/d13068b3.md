Bundled rusqlite compiles SQLITE_DEFAULT_FOREIGN_KEYS=1 — DROP TABLE fires ON DELETE CASCADE into child tables; CHECK-change migrations must PRAGMA foreign_keys=OFF outside the transaction

Invariant (proven 2026-07-11 by the corpus-engine-notes MIGRATION_V11 test): this workspace's bundled rusqlite/libsqlite3-sys compiles with `SQLITE_DEFAULT_FOREIGN_KEYS=1`, so every connection opens with foreign keys ON. Under FK-ON, `DROP TABLE parent` performs an implicit `DELETE FROM parent` first, which fires `ON DELETE CASCADE` into child tables — a create-copy-drop-rename migration silently EMPTIES `note_embeddings`/`note_entities` (or any child) unless the script brackets itself with `PRAGMA foreign_keys=OFF; … PRAGMA foreign_keys=ON;` outside the BEGIN/COMMIT (the pragma is a no-op inside a transaction).

Why: the notes schema (v9+) carries `REFERENCES notes(id) ON DELETE CASCADE` children, and `kind` CHECK-constraint changes require table rebuilds. Two hazards stack: (1) the V8-era rename-first pattern lets SQLite ≥3.25 rewrite child REFERENCES to the renamed temp table (then dropped); (2) FK-ON cascade on DROP. MIGRATION_V11 (`corpus-engine-notes/src/notes_schema.rs`) is the canonical safe template: create-copy-drop-rename + FK pragmas + recreate the UNION of all index generations + FTS rebuild.

How to apply: any future `notes.kind` CHECK change (or any rebuild of a table with FK children anywhere in the workspace) copies MIGRATION_V11's structure verbatim and keeps the migration test's `pragma_foreign_key_check` + child-row-count assertions against a handcrafted prior-version DB with POPULATED child tables.
