SPLIT_FILE LEAKS ITS max_file_size LADDER INTO THE REAL WORKING TREE (found 2026-09-03, merge 8cd3b88d3).

`commonwealth-tdd::tasks::split_file` renders a `max_file_size` assertion ladder via `structural::render_max_file_size_ladder` and writes it into the TARGET PROJECT's test dir, so an agent driving a split has descending rungs to flip. During the grounding/mod.rs split (729cc728f / c364ebfc1 / 877704fec) two copies escaped into this repo instead of a trial dir:

  tests/max_file_size.rs                                  (root; workspace-only Cargo.toml, so NOT compiled)
  sovereign/crates/sovereign-core/tests/max_file_size.rs  (COMPILED — 4 failing tests)

WHY IT MATTERS AND WHY IT HIDES: both files are UNTRACKED, so `git status` shows them as noise and no diff review ever sees them — but cargo compiles anything under `<crate>/tests/`, so the sovereign-core copy became 4 real failures in the workspace suite (max_file_size_within_1200 / _2107 / _3015 / _3923, asserting sovereign-core has no file over those thresholds; it has streaming.rs 4616, mesh_measurements.rs 3023, judge.rs 3011). They are indistinguishable from genuine regressions in the failure list.

BEFORE CONCLUDING A max_file_size_* FAILURE IS REAL: check whether the file is tracked (`git ls-files <path>`). If untracked, it is leaked scaffold, not a repo test. Header gives it away: "Structural assertion ladder — generated by tasks::structural::max_file_size."

The two copies were moved (not deleted) to this session's scratchpad. The underlying bug is unfixed: split_file needs to render into a temp/trial workspace, or clean up after the trial. It WILL recur on the next god-file split.</content>
