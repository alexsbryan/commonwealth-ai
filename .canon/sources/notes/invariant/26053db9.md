# git mv STAGES the rename, and in this shared tree that means the next git commit from ANY session lands it under someone else's message.

`git mv` STAGES the rename, and in this shared tree that means the next `git commit` from ANY session lands it under someone else's message.

Happened 2026-09-12: I ran `git mv sovereign-mesh/src/media_fanout.rs origin_fanout.rs`, and a peer's a3bfc3968 ("feat(oplog): polarity, selectivity, counting checks") committed the index, so its two files were scripts/co-oplog.py and my renamed file — carrying the file's OLD content, because my edits came after the mv and were unstaged. Result: lib.rs declaring `pub mod media_fanout;` against a file that no longer existed, so `cargo check -p sovereign-mesh` failed at that commit and the next. No gate in this repo catches it; the working tree has 3+ concurrent writers most days.

Do this instead: cp + rm (unstaged, invisible to a peer's `git commit`), or `git mv` and commit the rename in the same minute.

The sharper half: the first hand-repair caused a second incident. A `git reset --soft HEAD~1` reasoned from the wrong HEAD dropped e8ee7c288 off the branch entirely and left its 301 lines sitting in the shared index, one unqualified `git commit` away from being swept into a third unrelated change. Recovered with `git reset --soft e8ee7c288` after reading `git reflog`. Forward repair — land the commit that completes the change — is correct on a shared HEAD; history surgery is not. Read the reflog before any reset, and stage with explicit pathspecs (`git add -- <paths>`), never `git add -A` or a bare directory.
