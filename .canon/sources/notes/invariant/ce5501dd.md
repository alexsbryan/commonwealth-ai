# FIXED 2026-07-15: POST /v1/mesh/leave now exits the standalone daemon (exit 103) so launchd relaunches into a fresh solo mesh; the…

FIXED 2026-07-15: POST /v1/mesh/leave now exits the standalone daemon (exit 103) so launchd relaunches into a fresh solo mesh; the mesh_leave HTTP handler fires a leave-relaunch signal that wait_for_shutdown selects on alongside SIGTERM. Mode-safe: NOT fired by join's auto-leave or the embedded desktop daemon.

FIXED 2026-07-15 (see "The fix" below). Original bug: the mesh-leave design
intends: `leave()` → daemon exits → launchd (`KeepAlive: SuccessfulExit=false`
+ `RunAtLoad`) relaunches it fresh into a no-mesh/solo state (see the doc
comment on `MeshDaemon::leave` at `sovereign-mesh/src/daemon.rs:1250`). The
**exit half is missing for the standalone `sovereign-cli-daemon daemon run`:**

- `POST /v1/mesh/leave` → `leave()` → `stop_inner(StopMode::Leave)` drops
  `_shutdown_tx` (`daemon.rs:1293`). That fires the `tokio::select!` arm at
  `daemon.rs:2270` ("Commonwealth daemon shutting down"), stopping BOTH axum
  servers — client `:9741` and internal `:9742`.
- BUT the process's main task is blocked in `shutdown_daemon` →
  `wait_for_shutdown()` (`sovereign-cli-daemon/src/daemon_cmd/lifecycle.rs:710`),
  which awaits only SIGINT/SIGTERM. Nothing wires the dropped `_shutdown_tx`
  back to it. So the servers die, the process keeps running (log proof: SCIP
  git-poll rebuilds continued 3 min after "shutting down"), launchd sees a live
  PID → no relaunch → `:9741` stays dead until a manual SIGTERM+restart.

Result: clicking "Leave" in the desktop UI kills the client API and it never
comes back on its own. The desktop then shows
`Failed to load mesh state: ... error sending request for url (...:9741/...)`.

The fix (shipped 2026-07-15). A `leave_relaunch_notify: Arc<Notify>` on
`EmbeddedDaemon` (daemon.rs) with `request_leave_relaunch()` /
`leave_relaunch_requested()`. Fired ONLY by the `mesh_leave` HTTP handler
(mesh_http.rs) on a successful leave — NOT inside `leave()`/`stop_inner`,
because `join_mesh`'s auto-leave and the deprecated `stop()` also call
`leave()` and must not restart the process. The standalone
`wait_for_shutdown()` (sovereign-cli-daemon/daemon_cmd/lifecycle.rs) now takes
the daemon and returns a `ShutdownTrigger` (Signal | LeaveRelaunch), selecting
on the leave signal alongside SIGINT/SIGTERM. `shutdown_daemon` (mod.rs) exits
103 on LeaveRelaunch (non-zero → launchd `SuccessfulExit=false` /
systemd `Restart=on-failure` relaunch → fresh solo mesh, since leave() cleared
persistence), after a 750ms grace so the HTTP 204 flushes. SIGTERM still exits
0 (stays down); memory-watch still 102. The embedded/desktop daemon never runs
`wait_for_shutdown`, so the notify is a harmless no-op there.

Tests: `mesh_http::tests::{http_leave_fires_relaunch_signal,
direct_leave_does_not_fire_relaunch_signal}` (mode-safety). Frontend
resilience shipped alongside — MeshSettings.svelte polls through the ~10-20s
daemon-bounce window ("restarting the daemon…") instead of flashing "Failed to
load mesh state"; guarded by `MeshSettings.test.ts` resilient-leave test.

Solo-mesh UX decision (2026-07-15). For a SOLO mesh (members_total <= 1 —
the node's default posture) MeshSettings now HIDES the Leave button and instead
promotes a "Join another mesh" affordance (an `isSolo` `$derived` gates both).
Rationale: leaving a solo mesh only bounces the daemon into another identical
solo mesh — pointless and jarring. Joining is the meaningful action AND uses
join_mesh's in-process auto-leave, so it doesn't bounce the daemon. Leave stays
for real groups (members_total > 1). Do NOT naively re-add Leave for solo — the
absence is deliberate. Guarded by MeshSettings.test.ts solo tests.
