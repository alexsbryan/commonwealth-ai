NEXT-EDIT DOES NOT FIRE ON REACT TS AT ALL, AND THE GOLDEN SET CANNOT TELL US WHY IT WOULD (measured 2026-08-06). This matters because the first users are Go + React TS (operator, 2026-08-06).

PER-LANGUAGE hunk-precision, baseline -> node-kind filter (depth 3):
  GO           n=181   26.3% (115/438) -> 39.5% (96/243)   junk -54%, good -17%, a 9.3:1 trade. CLEAN WIN.
  TS  (.ts)    n= 81   24.7% (107/434) -> 56.4% (62/110)   junk -85% but GOOD -42%. Far worse than the 14% aggregate loss.
  TSX (.tsx)   n= 31    0/4            ->  0/1              NO SIGNAL.
  rust (ref)   n=190   36.7%           -> 52.9%             good -10%.

THE REACT TS GAP IS NOT A FILTER PROBLEM, IT IS A FIRING PROBLEM. Of the 31 `.tsx` cases: 14 positives and 17 negatives, and ALL 14 POSITIVES ARE `missed` — the rule lane proposes nothing. The whole language contributes 4 proposed hunks to a 3,129-hunk bank, 0 of them good. There is nothing for a site filter to filter.
WHY: 9 of the 14 `.tsx` positives are `import_addition`, the shape established as bank-invalid (history is an import insert plus an UNRELATED body edit; the truth is downstream semantic work with no repeat to induce — note b36dfc12). The rest are param_insert x2, field_init x2, delete_propagation x1.

SO THE CORRECT READING IS "UNMEASURED", NOT "WORKS". Any claim that next-edit serves React TS is currently unsupported by evidence in either direction.

THIS IS THE FIRST JUSTIFIED THESIS FOR BANK WORK, and it supersedes the retracted "drop import_addition to flatter the denominator" idea (frame, retracted 2026-08-06). Harvest `.tsx` episodes whose shapes the lane can actually serve — literal_fanout, rename_casing, type_fanout, param_insert — from React repos. Today `.tsx` is 31 of 1,098 cases and half of them are negatives; the shapes that DO work (literal_fanout 96%, rename_casing 88%) have essentially no `.tsx` representation. Until that exists, React TS performance is a guess.

THE .ts GOOD-HUNK LOSS NEEDS A SECOND LOOK before the filter goes default-on for TypeScript: 42% of correct hunks dropped versus 10-17% for rust and go. n is small (20 fires, 107 good hunks) so the interval is wide, but it is the one language where the filter's cost looks materially different from the others — and it is a first-user language.

FIXED IN PASSING (commit bfaa1ea5): `.tsx` was mapped to LANGUAGE_TYPESCRIPT, which cannot parse JSX — 29 of 31 files parsed to trees containing ERROR nodes (997 errors); LANGUAGE_TSX gives zero. Silent: a derailed parse still yields some symbols, so React code indexed fine and came out wrong, losing every definition after the first JSX element. The proposed node-kind filter would have inherited this directly, since node kinds from an ERROR-riddled tree are meaningless.
