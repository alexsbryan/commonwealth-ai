# SPIKE CLOSED, NEGATIVE: n_rs_seq makes partial KV keep WORK on qwen35/qwen35moe and it is NOT SAFE. Do not raise it on chat contexts.…

**SPIKE CLOSED, NEGATIVE: `n_rs_seq` makes partial KV keep WORK on qwen35/qwen35moe and it is NOT SAFE. Do not raise it on chat contexts. `prefix_cache_gate` protects OUTPUT QUALITY, not just an error code.**

Instrument: `sovereign-inference/tests/rs_rollback_spike.rs` (two `#[ignore]` tests, `SPIKE_GGUF=<gguf> cargo test -p sovereign-inference --test rs_rollback_spike --release -- --ignored --nocapture`).

The premise that opened this. Reading `llama-memory-recurrent.cpp::seq_rm` shows partial rollback IS implemented — a per-token snapshot ring `n_rs_seq` deep; the removal succeeds when `rollback <= n_rs_seq` and returns false otherwise. `llm_arch_supports_rs_rollback` (`llama-arch.cpp`) lists exactly QWEN35, QWEN35MOE, DEEPSEEK4 — both our hybrids. `model_slot.rs` sets `with_n_rs_seq(4)` **only when `is_mtp_model`**; every non-MTP chat context gets the default 0, which disables rollback outright. So the capability was never absent — it was unconfigured, and `is_recurrent_arch` has been reading "hybrid" as "incapable".

**Measured on `Qwen3.5-2B.Q6_K` (`qwen35`), 1425-token prompt, 16-token rollback:**

| n_rs_seq | seq_rm | RS buffer | rollback correct? |
|---|---|---|---|
| 0 (today, non-MTP) | refused | 19.27 MiB | n/a |
| 4 (today, MTP) | refused (16 > 4) | 96.33 MiB | n/a |
| 64 | accepted | 1252.27 MiB | NO |
| 512 | accepted | 9883.27 MiB | NO |

Cost is linear in `(1 + n_rs_seq)` exactly as the source says (`n_rows = mem_size * (1 + n_rs_seq)`): 65x the recurrent buffer at depth 64, on a 2B. At 512 the arm was also slower in absolute terms (full prefill 1247ms -> 3947ms).

Three controls, because the first negative had two obvious confounds:
1. *Ring-presence control* — a NO-REUSE full prefill at each `n_rs_seq` vs the `n_rs_seq=0` baseline: `ring_perturbs_output=false` on every arm. Allocating the ring does not move the numbers, so the divergence is the rollback's.
2. *Pure-attention control* — same sweep on `gemma-4-E4B-it` (`gemma4`): `rollback_correct=YES` on every arm, 1250ms -> 480ms (2.6x). So generic batch-shape numerical drift is NOT the explanation; prefix reuse on attention is byte-exact.
3. *Rollback/replay identity* — remove D tokens, replay the SAME D tokens at the SAME positions, compare continuations. No prompt-divergence confound left.

THE LOCALISATION (the actual finding). Fidelity does not depend on depth. It depends on whether the rollback stays inside ONE decode pass:

```
gen_before=0 → faithful [1, 2, 4, 8, 16, 32] · corrupt []
gen_before=4 → faithful [4, 8, 32]           · corrupt [1, 2, 16]
```

With zero tokens generated first, rollback is faithful at every probed depth. Generate even 4 tokens first — so the rollback must unwind single-token decode passes before re-entering the prompt's multi-token ubatch — and replaying identical tokens yields a DIFFERENT continuation. Deterministic: byte-identical pattern across repeated runs, so it is not sampling noise. Treat the "clean" depths as luck, not safety — the state is wrong in all of them and greedy argmax merely absorbs the perturbation at some depths.

Why this settles it. Every real second request has generated tokens in the cache from the previous turn, so chat prefix caching lands squarely in the corrupt regime. An intermittent, depth-dependent, SILENT quality regression is strictly worse than the full prefill it replaces. And it explains why MTP has held: MTP rolls back <= n_draft(4) tokens within the draft/verify pass — the faithful regime — which is exactly what `n_rs_seq=4` was provisioned for.

Consequences:
- `prefix_cache_gate` stays, and its justification is upgraded: it prevents a silent WRONG-OUTPUT path, not merely `Decode Error -1`. The gate-repro's own standing warning ("verify OUTPUT CORRECTNESS too, not just absence of errors") was load-bearing and is now discharged with evidence.
- Do NOT raise `n_rs_seq` on chat contexts. The MTP value of 4 is correct and should not be tuned upward for cache reasons.
- Full-state save/restore (`prefix_state.rs`, default-ON) remains the ONLY sound prefix reuse on these arches — it replaces the whole memory module and issues no partial removal. See [[cartridge-step01-spike-2026-07-12]].
- One live lead not chased: the zero-generation regime is faithful, and the forced-choice grounding judge emits `completion_tokens=0` (`judge.rs` reads logits in one pass, no generation loop). If its cached state truly never contains generated tokens, that workload sits in the faithful regime — but this spike did NOT test a real judge sequence, and the 65x ring cost likely kills it regardless. Do not act on this without measuring both.
