Retrieval P0 — dominant-source/title expansion returned a document's OPENING chunks for single-large-document corpora; fixed with a neighbour-window anchored on relevant hits

Retrieval P0 (fixed 2026-06-08, commit e3d027b2). `Runtime::expand_from_dominant_source` (`sovereign-core/src/runtime/retrieval.rs`) fetched the top source's chunks via `CorpusIndex::fetch_chunks_by_title(title, N)` — which returns the title's first N chunks in chunk-id order, uniform score 1.0 ("cohesion pull, not query similarity"). Sound for ARTICLE-shaped sources (a Wikipedia/SEP article's lead is usually what a reader wants), but broken for a single large document chunked under ONE title (a whole book, a long report, one PDF): it returned the document's OPENING for *every* query.

Trigger: `decide_expansion_strategy` (`runtime/evidence.rs:422`) returns `ExpansionStrategy::DominantSource` ("fast_single_source") when `route==FastFocused && shape.top_source_repeat_count >= EVIDENCE_MIN_TOP_SOURCE_REPEAT`. A single-document corpus has every chunk under one `source_doc_id`/title, so that condition is ALWAYS met → most FastFocused queries got chunk_ids 1..12 (the opening) regardless of relevance. **Diagnosed via `sovereign.db` messages.metadata.retrieved_chunks**: the Professor/india-rubber question returned chunk_ids 1–12 score=1.0 (shop scenes); "Stevie" (which stayed NoExpansion) got varied real hits. Corollary: for such corpora, chaos-monkey "competence" was partly the model's PARAMETRIC memory of the book, not retrieval grounding — exposed by chaos v2 provenance questions (facts deeper in the book → abstained on junk chunks). NO existing bench caught it; all are multi-article.

Fix: centre the cohesion window on the ACTUALLY-RELEVANT chunks (the dominant-source hits from the initial RRF pool), widened with their same-document textual neighbours via `CorpusIndex::neighbors(chunk_id, radius)` (`index/read.rs:56`, constrained to source_doc_id), capped by `EXPANSION_MAX_FROM_TOP_SOURCE`. New const `EXPANSION_NEIGHBOR_RADIUS=3`. Build ScoredChunk neighbours by CLONING the hit + overwriting content/chunk_id/score (ScoredChunk has no Default + extra fields). Fallback to the old title-fetch only when no chunk_id'd dominant hit exists (legacy indexes). Verified live: chaos Professor 1–12→71–77+301–305 (real Professor passages), competence 0.54→0.67 abstain 6→0; wikipedia "fall of Rome" 25/25 on-topic from the right articles with neighbour clusters (blast-radius safe). 468 sovereign-core tests green. NOTE retrieval runs IN-PROCESS in the bench (`sovereign-cli-llm`); the DAEMON serves mobile/desktop/gyms → needs its own rebuild+restart to get the fix.

Daemon VRAM gotcha (same session): the recurring "daemon unreachable"/`Decode Error -3` crashes were VRAM OOM — `~/.sovereign/config.toml [models]` had primary=36B-Q6 (~28GB) AND fast=35B (~18GB) ≈48GB on a 64GB box → jetsam under load. Canonical fitting config: primary=`Qwen3.6-35B-A3B-UD-MTP-IQ4_NL.gguf` (~18GB), fast=`Qwopus3.5-4B-v3-MTP-Q8_0.gguf` (~4.5GB), embed=0.6b. Two 30B+ models DO NOT fit. (IQ4 primary is less honesty-calibrated than the Q6 was: chaos honesty 0.73→0.45 on absent questions.) Also: `Decode Error -3` can ALSO come from TWO concurrent `cli-daemon` procs sharing the Metal ctx — clean restart = `sovereign daemon stop` + `pkill -9 -f 'cli-daemon daemon run'` + `sovereign daemon start`.
