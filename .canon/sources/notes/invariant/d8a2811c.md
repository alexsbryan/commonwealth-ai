# RPC-worker discovery must never re-probe a KNOWN worker over the same link that worker's own tensor traffic rides. Gossip-Online membership…

RPC-worker discovery must never re-probe a KNOWN worker over the same link that worker's own tensor traffic rides. Gossip-Online membership is the liveness signal; a probe adds no evidence and is starved by exactly the load it's supposed to survive.

THE FLAP CHAIN (measured 2026-07-26, ~/.sovereign/logs/rpc-tunnel-e2e.log):
1. `discover_rpc_workers` gave stickiness only to `via == "direct-ip"` (StickyEndpoint::is_direct). A bridged worker therefore ran the FULL `/status` probe every tick.
2. That probe rides TrafficClass::StatusProbe over iroh — the same path as the RpcTensor tunnel. Under decode load it times out (`iroh bridge: dial failed alpn=cwth/http/0 error=timed out`, dozens of them).
3. Timeout -> `fresh = None` -> `sticky_endpoint(prev_non_direct, None, _)` returns None (only direct-ip gets held) -> the worker is dropped from the tick and its sticky entry removed.
4. `worker_eligibility` sees an absent node -> flap. Endpoint pinned at 127.0.0.1:40021 for six straight minutes while the tracker logged `Probationary -> Quarantined flaps=9 quarantine_count=5 cooldown_secs=300`, excluding a peer (BeefyMac b88252e4) that was serving throughout.

FIX: `daemon.rs::reaffirm_plan(prev, tunnel) -> Reaffirm::{Held, Rebridge, FullProbe}`. Known direct-ip -> Held (re-affirm from cache, as before). Known iroh-bridge -> Rebridge (re-mint from the transport's LOCAL bridge cache; loopback only, no WAN round-trip). Unknown / probe-host, or tunnel=never -> FullProbe.

DO NOT "fix" a future flap here by loosening the eligibility thresholds — the tracker was right; discovery was lying to it. Note also that eligibility has keyed on NodeId since fbbd9a8b, so an endpoint STRING change is NOT the flap source; absence from a tick is.

Stated trade-off, deliberately taken: a bridged worker is never re-probed for a direct IP, so under SOVEREIGN_RPC_TUNNEL=auto a peer that fell back to the tunnel stays on it until its next Offline->Online cycle. If someone adds the upgrade probe, it must be UPGRADE-ONLY — its failure may never drop the worker, or this flap re-opens.
