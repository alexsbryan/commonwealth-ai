A NAME IS NOT HARDWARE: every PlacementShard carries its own `hw: Option<u64>` fingerprint, folded into `placement_digest` (2026-07-29). Extends the link-in-the-key invariant a83a5fb6 one level down — that one covered how the tensor stream TRAVELS, this one covers WHAT IT TRAVELS TO.

THE BLIND SPOT IT CLOSED. `host_hw_fingerprint` pins only the machine that RAN the probe. The machines that held the rest of the model were described by `placement_digest`, whose shards were identified by mesh NAME alone. So a peer that swapped a GPU for a different one of the same capacity — or merely flipped Vulkan↔ROCm, which `hardware_fingerprint` already treats as different silicon because it shifts throughput materially — kept every key it had ever filed, and the old number answered for the new machine. The module doc had this written down as a "Known blind spot" with a suggested fix; the fix as suggested was a trap (below).

DO NOT fold the fingerprint into `node_key`, which is what the old module doc proposed ("node_key is an opaque caller-supplied string"). It is not opaque in practice: `peer_liveness` looks peers up with `mesh.online.get(&s.node_key)`, `placement_human` prints it as the human label, and several comparisons test `s.node_key != mesh.self_name`. Concatenating a fingerprint into it breaks peer liveness silently (every lookup misses → every peer reads offline) and prints "24 @beefymac#a1b2c3d4" at the operator. A separate field keeps identity-for-the-digest and identity-for-the-mesh distinct.

REFUSAL, NOT FALLBACK — on BOTH sides, and this is the load-bearing part. A machine that advertises no fingerprint is not keyed on its name alone:
- Consumer (`mesh plan`): new `NotMeasurable::PeerUnidentified { name }`, sibling of the existing `HostUnidentified`. It NAMES the peer, because the repair is on a different box than the one being asked. JSON reason is `peer-unidentified:<name>`.
- Producer (`mesh bench`): `NodeIdentity::shard()` is the ONE place a shard is built, so the host and every worker are held to the same standard by construction rather than by two call sites remembering to agree. It errors, and the bench files nothing.

This also DELETED the endpoint-host fallback (`resolve(ep).unwrap_or_else(|| endpoint_host(ep))`). That fallback looked forgiving and was not: `mesh plan` builds its shards by walking mesh MEMBERS, so it can never reconstruct a key naming a bare endpoint. Every record filed through it was write-only — stored, counted, and impossible to look up. A store that grows and never answers is worse than a refusal because it looks like it worked.

The refusal keys off CARRYING WEIGHT, not off appearing in the worker list — `carries_weight` is checked before identity is ever asked for. Otherwise one old peer idling on the mesh would block every measurement taken on it. Test: `an_idle_unidentified_peer_does_not_block_the_run`.

DIGEST GENERATION pd1 → pd2. The prefix is a generation, not decoration. GOTCHA, and it bit me: `placement_digest` writes the generation TWICE — `h.update(b"pd1")` into the hash AND `format!("pd1:{}")` for the label. I changed only the first, so for one build every digest was new bytes wearing the old name, which is precisely the confusion the prefix exists to prevent. Both full gates were GREEN on that build; the live `mesh plan --from-mesh --json` run is what exposed it (`"placement_digest": "pd1:73cbfaaa91e64cd5"` with a pd2 hash inside). An existing assertion in mesh_cmd's `an_identified_mesh_with_no_record_says_not_measured` did pin the prefix and caught it on the next full run. There is now also `the_digest_label_matches_the_generation_that_produced_it` in core, at the point of construction. When the construction changes again, change BOTH literals and both tests in the same commit.

LIVE VALIDATION on RuggedFox 2026-07-29: all four mesh members advertise `hw_fingerprint`, including BeefyMac (12407155487651042694), so the new peer-identity requirement does not spuriously dark this fleet. `mesh plan --from-mesh` resolves 2 devices (BeefyMac 51 GB worker + RuggedFox 124 GB host) and produces `pd2:73cbfaaa91e64cd5`, link `direct`, status `not_measured` — a real key, refused by nothing.
