## Agent Discovery and Task Lifecycle Mechanics

The official A2A specification version 1.0 defines a rigorous, stateful architecture for agent-to-agent communication centered on three distinct interaction patterns: discovery via the Agent Card, task delegation through explicit lifecycle states, and asynchronous result delivery. This structure replaces previous fragmented integration models with a standardized protocol binding layer that operates atop existing transport mechanisms like HTTP + SSE or JSON-RPC 2.0 [ev-15]. The core innovation lies in the decoupling of internal logic from external interoperability; agents publish capabilities without exposing proprietary memory or implementation details, allowing any compliant client to interact with an opaque service [ev-38].

### Discovery Through Standardized Agent Cards
The first pattern establishes a decentralized discovery mechanism where every A2A-compatible agent publishes a JSON-formatted `AgentCard` at a standard endpoint (`/.well-known/agent.json`) [ev-16]. This card functions as a machine-readable job listing, detailing identity metadata, supported modalities (text, audio, video), authentication requirements via OAuth 2.0 or OIDC, and specific protocol bindings such as gRPC or REST [ev-44]. Unlike centralized registries, this approach relies on direct HTTP queries for capability assessment, ensuring that an AI agent from one vendor can immediately determine if it possesses the necessary skills to handle a sub-task delegated by another framework's agent [ev-32]. The specification explicitly mandates that these cards declare `supportedInterfaces[]` with unique URLs and binding types, creating a universal address book for autonomous systems [ev-18].

### Stateful Task Lifecycle Management
The second pattern governs the execution flow through a defined lifecycle of task states: submitted, working, input-required, completed, failed, canceled, or rejected [ev-15]. This state machine ensures transparency in long-running operations where agents may need multiple exchanges (messages) between client and server before completion [ev-32]. Each task receives a unique ID assigned by the executor, enabling precise tracking and potential cancellation. Crucially, this design addresses the "fragmentation problem" previously faced by enterprise teams who required bespoke connectors for every agent pair; A2A standardizes these transitions so that a Salesforce agent can reliably delegate work to ServiceNow without custom glue code [ev-15].

### Asynchronous Streaming and Artifact Delivery
The third pattern facilitates complex data exchange through streaming capabilities or asynchronous webhooks, depending on task duration and complexity [ev-16]. While synchronous communication is supported via JSON-RPC 2.0 as the primary binding, the protocol accommodates fluid roles where agents act as both clients and servers dynamically [ev-18]. Upon completion, agents return structured `Artifacts` rather than simple text responses, allowing downstream systems to process specific outputs like generated reports or booked flights directly within the protocol payload [ev-32]. This tripartite structure—discovery, stateful delegation, and artifact delivery—forms a cohesive layer that solves vendor lock-in by providing a single open standard for multi-agent coordination across diverse ecosystems [ev-44].

## A2A Task Lifecycle States

The A2A protocol defines a granular, eight-state task lifecycle designed to manage the variability of LLM processing times and complex agent interactions. Unlike simplified four-state models (pending, running, failed, done) often used in conceptual sketches [Source: ev-8], the specification explicitly separates execution into three distinct groups: Running, Finished, and Paused. This architectural choice addresses the specific problem of long-running tasks that may require intermittent human intervention or credential verification without terminating prematurely. The "Running" group encompasses `submitted` and `working`, indicating initial receipt and active computation respectively. The "Finished" terminal states include `completed`, `failed`, `canceled`, and `rejected`. Crucially, the protocol introduces two additional paused states—`input-required` and `auth-required`—which allow a task to remain suspended indefinitely until the client provides clarification or refreshes credentials [Source: ev-10].

The distinction between these states is enforced through strict JSON-RPC operations and Server-Sent Events (SSE) streams. When a task enters an input requirement state, the server emits a specific event type (`TaskStatusUpdateEvent`) signaling that the agent needs additional context before proceeding [Source: ev-21]. This mechanism supports human-in-the-loop workflows where agents pause deliberately rather than failing due to missing data. Similarly, if authentication fails, the protocol returns a 401-style indication via the task object, prompting the caller to retry with refreshed tokens while preserving the original `taskId` for resumption later [Source: ev-10]. The strength of this design lies in its ability to decouple execution time from completion status; a task can sit in `input-required` for days and resume seamlessly once new input is sent via `tasks/sendSubscribe` or subsequent message calls [Source: ev-8].

Retrieving state transitions relies on two primary mechanisms: polling and streaming. While clients may poll using the `GetTask` method to retrieve full Task objects including history length parameters [Source: ev-40], the protocol prioritizes SSE streams for real-time updates, which are preferred for long-running interactions [Source: ev-41]. These streams emit discrete events such as `status_update`, `artifact_update`, or raw messages depending on agent capabilities advertised in their Agent Card [Source: ev-52]. The evidence confirms that v1.0 of the specification removed legacy fields like the `kind` discriminator and stream closure flags (`final: true`), standardizing event identification by JSON member names (e.g., distinguishing `statusUpdate` from `artifactUpdate`) to reduce parsing overhead [Source: ev-10].

## Transport Efficiency in Agent Communication

The median size of context window payloads transmitted over MCP stdio versus HTTP streaming reveals a fundamental architectural divergence driven by state management. Evidence indicates that while both protocols aim to standardize agent interactions, their underlying transport mechanisms result in drastically different bandwidth profiles during multi-turn tasks. Specifically, HTTP-based communication exhibits linear payload growth as conversation depth increases, whereas WebSocket-based transmission maintains a near-constant payload size regardless of turn count [ev-29]. This distinction is not merely theoretical; benchmark data from GPT-5.4 processing a typical 10-turn coding task demonstrates an average total client-to-server byte transfer of 176 KB for HTTP requests compared to only 32 KB for WebSocket streams [ev-29].

### The Linear Cost of Statelessness
The inefficiency inherent in the standard HTTP model stems directly from its stateless design, which forces clients to reconstruct full context history on every request. In this paradigm, each subsequent turn requires the retransmission of system instructions (~2 KB), tool definitions, and all prior user prompts and model outputs [ev-29]. Consequently, payload sizes escalate rapidly: starting at approximately 2 KB per turn, the data volume swells to nearly 38 KB by the ninth turn of a conversation [ev-29]. This linear accumulation creates significant overhead, as the client must send nearly ten times more data per request compared to WebSocket modes after just nine turns [ev-29]. The protocol tax here is clear; while HTTP remains the de facto standard for API compatibility across tools like OpenAI's Responses API, its lack of persistent server-side memory necessitates redundant transmission that compounds with every interaction step [ev-47][ev-29].

### Constant Payloads via Stateful Continuation
In contrast, protocols utilizing stateful continuations, such as those supported natively in Google Gemini and Anthropic Claude APIs (though not universally adopted by coding agents), eliminate this redundancy. By maintaining connection-local memory where servers cache responses from previous turns, these systems allow clients to transmit only a reference ID (~60 bytes) plus new tool outputs (typically 1–3 KB) for each subsequent turn [ev-29]. This mechanism results in a flat bandwidth profile, keeping per-turn data transfer between 2 and 4 KB throughout the entire session [ev-29]. The aggregate impact is substantial: benchmarks show an average reduction of 82% in client-sent bytes across tasks, equating to approximately 144 KB saved per task when scaling across thousands of concurrent sessions [ev-29].

### Protocol Implications
The divergence suggests that while MCP stdio may prioritize interoperability through its own transport specifications, the efficiency gains observed with WebSocket-based stateful architectures highlight a critical performance bottleneck for HTTP-centric designs. As agents engage in complex workflows requiring deep context retention, the choice of transport layer becomes as vital as the protocol definition itself. The evidence supports the conclusion that eliminating redundant data transmission via persistent connections offers superior scalability and reduced latency compared to retransmitting full histories on every request [ev-29][ev-47].
