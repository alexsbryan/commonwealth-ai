## Agent Role Architecture and Capability Definitions

The A2A architecture specification establishes a rigid yet flexible framework for defining agent roles, moving beyond simple binary classifications to a granular taxonomy of six distinct task lifecycle states: submitted, working, input-required, completed, failed, and canceled [4]. This state machine approach fundamentally alters how agents interact with users; rather than merely executing commands, the protocol explicitly manages the temporal progression of an interaction. The significance lies in its ability to surface exactly where an agent is stuck or waiting, such as during "input-required" phases, thereby reducing ambiguity in multi-turn dialogues. While this provides strong structural clarity regarding workflow execution, it does not inherently define *what* skills an agent possesses without additional metadata layers within the specification itself.

The definition of capability types relies heavily on the Agent Card structure, which serves as the primary container for role descriptions. Crucially, the `skills[]` array within this card mandates a rich set of attributes: id, name, description, tags, examples, inputModes, and outputModes [6]. This design choice indicates that A2A treats capabilities not just as static lists but as contextualized objects with defined interaction modes (e.g., text vs. tool use). The inclusion of "examples" and specific mode definitions suggests a move toward few-shot prompting integration directly into the protocol's core data model. However, the specification does not elaborate further on how these skills are dynamically discovered or negotiated during runtime; it assumes they are pre-defined in the Agent Card.

The canonical data model for A2A v1.0 consolidates this complexity into six specific types: AgentCard, AgentSkill, Task, Message, Part, and Artifact [6] [18]. This limited set of primitives creates a highly constrained environment where every interaction must map back to one of these entities. The separation of "Task" from "Message" implies that an agent can perform work (a task) independently of conversational turns (messages), allowing for parallel processing of long-running operations without cluttering the chat history with intermediate steps represented as artifacts or parts. While some might argue that limiting the schema to six types reduces flexibility compared to more open-ended protocols like MCP, the evidence suggests this is intentional to ensure interoperability across diverse implementations by enforcing a strict standardization on how roles and skills are serialized and transmitted [18].

## Architectural Asymmetry in Communication Patterns

The A2A protocol core design establishes a deliberate architectural asymmetry, prioritizing asynchronous event-driven patterns while retaining robust synchronous capabilities. Contrary to the assumption that modern agent protocols default strictly to blocking interactions, the v1.0 specification explicitly defines support for four distinct communication patterns: synchronous request/response, asynchronous polling, Server-Sent Events (SSE), and webhooks [22]. This multi-pattern approach is not merely additive but fundamental; it allows agents to operate effectively across both real-time transactional environments and long-running background processes without requiring external middleware adaptation. The strength of this evidence lies in its explicit enumeration within the primary source documents, leaving no ambiguity regarding the protocol's native flexibility [20], [6].

### Synchronous Blocking vs. Asynchronous Streaming
The synchronous pattern operates as a strict callback mechanism where the client agent invokes methods such as `sendTask` and enters a blocked state until receiving a single, complete response from the server agent [22]. While effective for immediate data retrieval or short transactions, this model presents inherent limitations for complex workflows involving extended durations. In contrast, the asynchronous design is engineered specifically to resolve these bottlenecks by supporting long-running operations and handling connectivity interruptions through mechanisms like SSE for streaming updates [23], [4]. This distinction matters significantly because it shifts the burden of status tracking from an active polling loop (which consumes resources) to passive reception of events via client-provided webhooks when needed [16], [4].

### Binding Flexibility as a Force Multiplier
The protocol's ability to support diverse transport bindings further reinforces its capacity to handle both pattern types efficiently. By defining three distinct protocol bindings—JSON-RPC 2.0, gRPC, and HTTP+JSON/REST—the A2A specification ensures that synchronous requests can utilize low-latency binary transports like gRPC where appropriate, while asynchronous streams can leverage standard RESTful endpoints or SSE channels depending on the network topology [20]–[ev-29]. This binding flexibility means the choice between synchronous blocking and asynchronous streaming is not constrained by a single underlying implementation but rather dictated by operational requirements and latency constraints. Consequently, the A2A core design successfully decouples communication semantics from transport mechanisms, allowing agents to dynamically select the most efficient pattern for any given task lifecycle.

Ultimately, demanding readers should view A2A not as an immediate replacement for existing stacks, but as a necessary coordination layer whose value scales with system complexity rather than individual agent capability.
